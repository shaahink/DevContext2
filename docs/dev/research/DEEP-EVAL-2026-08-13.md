# Deep evaluation — DevContext before release

_2026-08-13 · written after the agent-probe program closed (12/12 checkpoints, `feat/agent-probe` @ 157420b) · sources: `eval-results/agent-probe/RESULTS.md`, `eval/agent-probe/DESIGN.md` + `DEVIATIONS.md`, `docs/dev/research/BUG-BACKLOG.md`, `docs/product/PRODUCT-DIRECTION.md`, `docs/dev/research/OWNER-TODO.md`, plus source checks made today and cited inline._

---

## Verdict in three sentences

The probe did not kill the lens thesis — it measured a tool surface that was **known-broken in exactly the two dimensions the experiment stressed**: adoption (the tools shipped with empty descriptions on the wire — backlog #5, verified still unfixed in source today) and sufficiency (impact analysis failed on the graph-completeness bugs filed as #7/#8/#11/#12). The correct reading is not "the MCP doesn't help agents" but "the MCP was tested before its filed defects were fixed, and it failed the way those defects predict." The path to release is therefore unusually clear: fix the filed agent-surface and edge-completeness bugs, re-run the cheap adoption gate before spending on the 360-run study, and hold the README's agent claim until a measurement earns it — while the human faces (CLI + desktop), which are in the best shape they have ever been, carry the release.

---

## 1. Where the program actually is

**Shipped and solid.** The engine went through Batch A–E plus G1–G10: structural symbol identity, member-origin edges, one compilation, inverse edges, a 47-pole truth matrix, one TracePolicy, a dead-field contract sweep that is now a gate. v1.0.5 is cut, CI is green on `develop` and `main`, the full gate battery was green on the merged tree. The desktop app survived the R3 redesign through D-E; S11 (D-F insight dedup, D-G Studio, D-H) is the remaining owner-interactive UI work.

**Not shipped.** `DevContext.Cli` is unclaimed on nuget.org (`OWNER-TODO.md` §1 — the package is ready, the id is free, the workflow works; it needs an account and a key). So "not released yet" concretely means: no public install path, and a README whose central agent claim — *"let AI agents query your codebase instead of grepping it"* — has now been tested once and did not survive contact.

**Filed and waiting.** 24 measured-but-unfixed findings in `BUG-BACKLOG.md`, 7 high. These were deliberately banked as product decisions. The probe has now retroactively priced several of them — that is the heart of this evaluation.

## 2. What the probe actually established

The pilot: 6 pre-registered eShop questions × 3 arms × 3 reps = 54 runs, `claude-opus-5`, ~$28 of runs plus $3.48 of judging, $51.74 of conductor total. Arms: **G** = Read/Grep/Glob only, **M** = MCP only, **B** = both (the real-world configuration). Pre-registered decision rule, blind judge, arm isolation proven from transcripts. As an *instrument*, it worked: the grep-favouring control (class F) went against the MCP exactly as the design said it must if the harness is honest, isolation held 54/54, the judge leak-scan came back clean.

### 2.1 The headline, and the confound underneath it

Arm B's median `mcp_call_share` was **0.015** — 17 of 18 runs below the pre-registered 0.20 floor. Per DESIGN §3.1 that disqualifies the B-vs-G contrast: an agent offered 22 connected DevContext tools **chose grep**, on every question class, including the attribution trap the member-origin fix was built for. RESULTS.md correctly reports this as a product finding about tool adoption, and quotes the design's two candidate causes: *"either the tool descriptions need work or the surface is wrong — this pilot does not distinguish between them."*

**The backlog already distinguishes them, and the answer is brutal.** Bug #5 (filed high, 2026-07-29): every one of the 22 tools ships with `description: ""` on the wire. The 31 XML doc summaries written for agents never reach it — `DevContext.Mcp.csproj` sets no `GenerateDocumentationFile`, there are zero `[Description]` attributes, and `Directory.Build.props` actively suppresses the missing-doc warning (`NoWarn: EnableGenerateDocumentationFile`). **Verified again today, 2026-08-13, on the probe branch: nothing touched `src/DevContext.Mcp` between the bug filing and the probe runs.** The P1.2 tax measurement corroborates it from the wire side: ~115 tokens per tool schema is the size of a bare schema, not a documented one.

So arm B was asked: given `Read`/`Grep` — tools the model has used millions of times — or 22 **unexplained verbs**, which do you reach for? Non-adoption was overdetermined. The most consequential number in the probe program was substantially generated by a known, filed, unfixed bug whose fix text already exists in the source. This does not make the pilot worthless — it makes it a $52 measurement of what backlog #5 costs. But it means **no adoption conclusion is valid until #5 is fixed**, and the pre-registered pre-run gate in RESULTS §10.1 (re-demonstrate `mcp_call_share ≥ 0.2` before spending on the full study) is exactly right.

Honesty requires the caveat both ways: fixing #5 may not be *sufficient*. Agents are grep-biased even against well-described tools, and 22 of them is a lot of menu. That is why the cheap adoption re-run comes before the full study — it is the discriminating experiment between "descriptions" and "surface", and it costs about $10.

### 2.2 Arm M's negative, decomposed

Arm M — MCP as sole source of truth — is the only configuration that actually exercised the product, and it lost: **12/18 correct vs G's 18/18, at 1.508× the cost** (Wilcoxon p = 0.0313), median 23 turns vs 13. The failures were total, not scattered: class F 0/3 (by design — the harness sanity check passing) and **class C impact 0/3** (one run into the $1.50 budget cap). Fabrication flagged in 11.1% of M runs, 0% elsewhere — though M's citations were the *most* resolvable, so the fabrication is at claim level, filling gaps the graph left.

Class C — "what breaks if I change `CheckoutBasketCommandHandler`" — is the set-valued, cross-project question the graph exists to answer, and its failure maps directly onto the filed edge-completeness family:

- **#11 (high):** static calls with a type-name receiver produce **no edge** — DevContext's own body-fact walker has zero in-edges in DevContext's own graph; 80% of the engine's own call edges are `approx` (1103/1383).
- **#12 (high):** the semantic receiver-type upgrade misses **every invocation whose statement fits on one line** — the overwhelmingly common case — because `TryBindReceiverType` relocates by line span and searches ancestors.
- **#8 (high):** calls inside lambda arguments drop edges (to be re-measured — #11 refutes its stated mechanism).
- **#7 (high):** a method mis-registered as a Type node absorbing 26 BCL `System.Type` references — 4.2% of Hangfire's call graph is phantom.

An impact query over a graph with those holes returns a confidently incomplete set. And the MCP-only agent gets hit hardest by the **confident-partial-truth family** — #6 (`trace` on a nodeId returns `found:true` with an empty tree, while the error envelope tells agents to pass nodeIds), #9 (`fillNote` asserts completeness while eliding the body), #10 (`read_source mode:"full"` silently returns a 20-line window), #2 (`entrypoints` names an entry a way `get_context` can't resolve) — because it has no file tools to cross-check with. M's 23-turn median is the shape of an agent fighting its instrument. The 6 wrong answers and the 1.5× cost are, in large part, the backlog's price tag.

### 2.3 The asterisks that stand regardless

- **Contamination.** Every number comes from eShop, a famous repo the model has plausibly memorised. Arm G's perfect 18/18 at low cost is partly a memory result, not only a grep result. DESIGN §6.1 calls the unseen repo "the one that could invalidate everything" — and it is also where the product's value case actually lives (an agent re-exploring an *unfamiliar* repo from cold). It has never been measured.
- **Two pre-registered gates are degenerate at pilot n** (and one is degenerate per-repo at full-run n): the −0.05 non-inferiority bar is arithmetically unreachable at 18 and at 30 pairs, and κ ≥ 0.8 requires perfect 11/11 agreement. RESULTS §10.4–5 names the decisions that must be written into DESIGN *before* the next run. These are design debts, not findings.
- **The judge is unvalidated.** Every correctness figure — including M's 12/18 — hangs on the un-graded 11-item human sample sitting in `eval/agent-probe/results/r1.2-human-sample/`. Roughly an hour of owner time gates the credibility of the whole correctness endpoint.
- **The standing "primer, not accelerator" verdict is untouched.** The pilot neither confirms nor refutes it; `PRODUCT-DIRECTION.md` §9 is correctly left unrewritten.

### 2.4 What the probe genuinely bought

Beyond the negative result: a reusable, pre-registered instrument (runner, question sets with keys, deterministic grading, blind judge, leak scan, analysis with bootstrap CIs) that converts "are we done?" from a feeling into a gate. That is the missing piece the program has needed since the README claim was written. The $52 was mostly spent building the scale, not weighing the object.

## 3. The strategic reading

**The MCP competes with grep on grep's home turf, and the probe drew the map of the winnable ground.** Read/Grep are free (no schema tax), trained-in, and trustworthy. The lens can only win where grep structurally fails: cross-project indirection (class B), reverse edges and impact sets (class C), and honest orientation on unfamiliar code (class A, unseen repos). Those are precisely the classes that need the graph to be *complete* and the surface to be *trusted* — the two things the backlog says are not yet true. On a small or memorised repo, grep wins and should win; DESIGN §3.2 said as much about TodoApi in advance.

**The agent face drifted from its own design.** `PRODUCT-DIRECTION.md` §7 specified the MCP as ~6 operations over the query layer (`list_entrypoints, trace, map, stats, get_node, find_usages`). What shipped is **22 tools with empty descriptions** — the "catalog soup" rot that §2 principle 1 warns about, reborn on the agent face, where its cost is measured in schema tokens (~2,535/session) and in choice paralysis. The pilot's only adoption signal points the same way: arm B touched the MCP mostly for orientation (`overview`-shaped calls, share 0.17) and ignored the long tail. Curation is not cosmetic here; for an agent, the tool list *is* the UX.

**The program's signature defect class has a name, and it decides trust.** Empty descriptions behind a working menu; `found:true` with an empty tree; a fill note asserting completeness during elision; an invalid mode silently accepted; a release that shipped green without its installers; a tab cap returning a plausible id. The recurring shape is **a confident surface over absent substance**. For a human, this costs a wasted click. For an agent — which cannot raise an eyebrow — it is fatal: it either destroys trust (agent stops calling, arm B) or manufactures false confidence (agent believes the empty answer, arm M's fabrications). The honest-envelope work (G1–G3) fixed many instances; #2, #6, #9, #10 are the live remainder on the agent path. This class deserves a standing wire-truth gate, not case-by-case fixes: every tool described, every enum-ish parameter validated or rejected, every `found:true` non-vacuous, every elision named.

**The README claim is currently unearned, and the project's own principles say what to do about that.** Principle 2: "Never show what the kernel can't honestly answer — a universal tool that lies loses trust faster." That applies to the README as much as to a trace. Until a re-probe earns it, the agent story the product can honestly tell is the standing one: a *primer* (one `get_context`/`overview` call priming a session) — not a grep replacement.

## 4. Where to take it — the pre-release plan

Ordered by information-per-dollar. W1 before any re-measurement; the adoption gate before any full study; W2 in parallel once W1 lands; W4 runs alongside throughout.

### W1 — the agent-surface trust pack (server-local, days, no matrix rerun)

1. **Fix #5 by measurement.** Add `<GenerateDocumentationFile>` (or `[Description]` attributes carried from the existing 31 XML summaries — whichever the ModelContextProtocol SDK actually reads; the backlog rightly says *measure via `tools/list`, don't assume*). Re-measure the schema tax after — it will grow, and the trade is deliberate: paying ~2× tax for tools that get *used* beats paying 1× for tools that don't.
2. **Curate the menu.** Decide the core agent surface (candidate: `analyze`, `overview/map`, `entrypoints`, `find/resolve`, `trace`, `impact`+`usages`, `read_source`, `get_context` — roughly §7's set plus the navigation primitives) and demote or fold the rest. Fewer, richer, described tools: both tax and adoption move in the right direction.
3. **Close the confident-partial-truth family on the agent path:** #6 (trace × nodeId — route through the resolver `get_context` already uses), #10 (reject invalid enum values with the existing good error envelope), #9 (fillNote must name elision and the `budgetTokens` lever), #2 (entrypoint names must round-trip into `get_context`/`trace`).
4. **Gate it.** One wire-truth check in the battery: every tool in `tools/list` has a non-empty description; invalid `mode`/`direction`/`format` return envelopes; a `found:true` trace has steps or says why not. Each of these would have been red from the day it was written.

### W2 — graph completeness for the impact claim (engine, riskier, batch discipline)

5. **#11** static type-name-receiver calls (the dogfood invariant is beautiful and cheap: *DevContext's own helper layer must have in-edges in DevContext's own graph*). **#12** one-line-statement receiver binding — the backlog already names the fix shape (descend from the statement node, or better, record the invocation's own `TextSpan` on the op) and warns it moves every pole: this is a batch-with-a-matrix-run change. Then **re-measure #8** (its lambda mechanism is refuted by #11) and **#7** (plus the free invariant: no node may carry kind `Type` and a `::name(arity)` member id). Acceptance: the probe's class-C question resolves the true impact set on eShop; `approx` share on the engine's own graph drops measurably from 80%.

### W3 — re-probe, staged, cheap-first

6. **Owner, now (~1 hour):** grade the 11 sample items, run `node eval/agent-probe/kappa.mjs`. This gates trusting every correctness number already collected.
7. **After W1 (~$10):** the pre-registered adoption gate — re-run arm B alone on eShop, 18 runs, unchanged prompt. Share ≥ 0.2 → the full study is worth running. Still < 0.2 with described, curated tools → that is a *real* product finding, and the design's honest fallback fires: the study becomes M-vs-G sufficiency, and the product story becomes primer + human lens (§5 below).
8. **After W2: the full run, with the amendments RESULTS §10 demands written into DESIGN first** — unseen repo (a mechanically identifier-renamed public repo is the affordable version) reported first; §3.3's question mix (2× class B, E/F at half); the non-inferiority bar re-specified at a level the n can reach (pooled, or a widened per-repo margin — decided in writing, in advance); κ on 20% of 360 with the degenerate-marginal rule stated. **One arm worth adding at pre-registration: B-instructed** — arm B plus the one CLAUDE.md line every real deployment will ship ("use DevContext for orientation/trace/impact"). Unprompted adoption is the purist's bar; instructed use is the product's actual deployment shape, and knowing both separates "agents won't reach for it" from "agents won't benefit from it".

### W4 — the human faces carry the release (parallel throughout)

9. **S11** (D-F insight dedup, D-G Studio, D-H) — the owner-interactive UI remainder.
10. **NuGet** (OWNER-TODO §1): claim `DevContext.*`, set the key, exercise the fixed release path with the next tag and confirm all three artifacts attach (§2's lesson).
11. **README honesty pass:** state the agent story as measured (primer; probe results linked), not as aspired.

### The release gate, made concrete

"Happy before release" is currently a feeling; here is a checkable version:

| # | Gate | Instrument |
|---|---|---|
| 1 | Ripgrep test passes on the five shapes of PRODUCT-DIRECTION §9 | existing eval matrix + a manual pass |
| 2 | Wire-truth gate green (descriptions, enums, non-vacuous answers) | W1.4, in the battery |
| 3 | Arm-B adoption ≥ 0.2 with described+curated surface | W3.7, ~$10 |
| 4 | On the unseen repo: M or B-instructed non-inferior on classes A/B/C at a stated cost band | W3.8 full run |
| 5 | README claims ⊆ measurements | reading |

Gates 1–3 are achievable within the current iteration loop. Gate 4 is the honest bar for the agent *claim* — and it is allowed to fail: if it does, the release is the human lens + agent primer, which is a real product with a true README, and the accelerator claim waits for the graph to earn it. What is *not* on the table, per the project's own principles, is releasing the claim untested a second time.

---

## 5. The one-paragraph summary for a cold reader

DevContext's engine and human surfaces have been rebuilt, measured on a 47-repo matrix, and released internally as v1.0.5; the product is unreleased publicly mainly for want of a NuGet key and an earned README. The first controlled test of its agent claim came back negative on both counts — agents offered the tools ignored them, and the MCP alone was slower and wronger than grep — but both failures were substantially pre-written in the project's own bug backlog: the tools shipped undescribed (#5, still unfixed at probe time and today), and the graph's edge gaps (#7/#8/#11/#12) are exactly where the MCP-only arm failed. The evaluation's conclusion is to treat the pilot as the price tag of the filed bugs, fix the trust pack and the edge family, re-run the $10 adoption gate before the $200 study, add the unseen repo the design always required, and let the human lens carry the release while the agent claim is earned — or honestly downgraded to the primer the evidence already supports.
