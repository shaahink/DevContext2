## 1. #14 — a generic command attribute is invisible  → CLOSED (commit 796843f)

**Measured at the source, not read off the backlog.** `CliCommandExtractor.FindCommandAttributeVerb`
did `attribute.Name.ToString()` then sliced after the last dot, so a generic attribute's leaf was the
literal text `Command<ConfigCommand>` and the arm was skipped. GitVersion declares its four
sub-commands exactly that way — 5 verbs rendered where 9 ship.

RED FIRST — `bug14-red-run.txt`, pre-fix engine, the one fixture whose only declaration is generic:

```
[xUnit.net] CliCommandExtractorTests.GenericCommandAttribute_IsDetected_AndCarriesTheParentCommandType [FAIL]
Failed!  - Failed: 1, Passed: 9, Total: 10
```

FIX — the leaf now comes off the NAME SYNTAX (`SplitAttributeName`: AliasQualified → Qualified.Right
→ `GenericNameSyntax.Identifier`), and the type argument is not noise to strip: it names the PARENT
command and rides out as `CliCommandDetection.ParentCommandType`.

RENDER HALF, which is the point of the parent link (R-T1: detection lands with render):
`CliCommandEntryPointBuilder.VerbPath` walks the parent chain across projects — GitVersion's
`ConfigCommand` lives in a different project from its `init`/`show` children, so only the whole
detection set knows both ends — and titles the entry `config init (ConfigInitCommand)`. That is what
makes `CliArchetypeSource`'s first-word grouping print ONE group of three instead of the flat tree of
three it was asserting at confidence 0.8.

## 2. Blazor UI-vs-HTTP  → CLOSED (commit 0a614cc)

The catalog was the stale side, and D1.1's own instrument had already measured it: the blazor
consumer project produces `UiEntry` while the descriptor declared `HttpEndpoint`/"HTTP".
`HttpEntryPointBuilder.cs:196-203` has emitted `UiEntry` for a `.razor` `@page` since T1.7 — that is
what stopped Blazor pages counting as anonymous HTTP endpoints in the security insight.

The descriptor now declares `UiEntry`, and `kind:HttpEndpoint@blazor` is DELETED from
`eval/expectations/catalog-reachability-allow.txt` in the same commit. The allow-list ratchets in
both directions, so a closed hole left listed fails the sweep: the green sweep with the line gone IS
the proof.

```
Passed CatalogReachabilityTests.Every_catalog_kind_has_a_producing_path
Passed CatalogReachabilityTests.Every_catalog_signal_is_reachable_from_a_consumer_app
```

`RenderLabel` stays "UI" deliberately: `MapRenderer.KindLabels` groups by Kind and takes the FIRST
descriptor, and blazor is the first `UiEntry` one in file order — any other string there would have
silently relabelled every desktop entry too. 4 allow-list lines remain (was 5).

## 3. #20 + #19 — one source of truth for "what is a service"  → CLOSED

Two independent second opinions, both reproduced in a fixture before either was fixed
(`bug19-bug20-red-run.txt`):

```
Failed ServiceVocabularyTests.An_auxiliary_demo_executable_is_not_a_service_on_either_surface
  Assert.Empty() Failure: Collection was not empty
  Collection: ["TestApp"]                       <- #20, AutoMapper's exact symptom

Failed ServiceVocabularyTests.The_style_evidence_count_is_a_subset_of_the_drawn_services
  String: "4 runnable web services with message bus "...   <- #19, above a breakdown of 3
```

- **#20** — `ArchetypeDetector` had already judged that exe auxiliary (that judgement is WHY the repo
  reads Library) and `ServiceBoundaryInference` never asked. The verdict is now exposed once, as
  `ArchetypeDetector.ExecutablesAreAuxiliaryToALibrary(model)`, and `RunnableProjects` reads it.
  **It is deliberately the COMPOSITE, repo-level verdict, never its per-project half**: "a non-WinExe
  exe that transitively references a library" is true of every eShop service, so a per-project reading
  of the same evidence would empty a real microservices canvas. `Packable` means an EXPLICIT
  `IsPackable`/`GeneratePackageOnBuild` — which is why eShop, whose libraries declare none, is
  untouched (`A_real_apps_services_survive_the_auxiliary_executable_rule` pins that).
- **#19** — the microservices rung's evidence line counted a THIRD population with no production
  filter at all. `CountRunnableWebProjects` now iterates `RunnableProjects`, so the quoted count is a
  subset of the drawn services by construction; only the WEB question stays local (a console worker is
  a service without being a web one).
