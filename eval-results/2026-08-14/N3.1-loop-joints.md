## What was measured, not assumed

1. **A raw node id is a legal card entry id, end to end.**
   `ContextPackBuilder.ResolveCardFocuses` tries the declared-entry inventory first, then
   `NormalizeSymbolFocus` strips the `NodeKind` prefix (`Type:Acme.OrderService` →
   `Acme.OrderService`, `Member:X::Handle` → `X:Handle`) and hands the rest to
   `GraphQuery.ResolveEntry` — the same path `get_context` uses (N2.1). So NodeCard and Insights
   send their target verbatim and no client-side symbol lookup exists anywhere in this checkpoint.
   `EntryPointResolver.Resolve` on its own would NOT have taken the `Type:` form (its `::` split
   would read the kind prefix as the type name) — the normalizer is what makes it work, which is
   why nothing here calls the resolver directly.

2. **The router recreates Studio on every navigation.** No `RouteReuseStrategy` is registered
   (`grep` over `shell/` + `app.config.ts`: a plain `<router-outlet />`). That is why the handoff
   is a ONE-SHOT channel taken in an effect rather than a second copy of the pack state: a signal
   that stayed set would re-seed the same cards the next time the user walked into the room.
   Pinned by `studio-handoff.store.spec.ts` — `take()` returns the proposal once and null after.

3. **Zero `state/ → features/` imports existed before this checkpoint** (`grep -rn "from '\.\./features" state/`
   → empty). Rather than make the handoff store the first one, the shared vocabulary
   (`ContextCardSeed`/`ContextCardType`/`ContextIntent`/`OutputFormat` + the new `PackProposal`)
   moved down to `models/context-card.ts`. Five files re-pointed; no re-export left behind, so
   there is still exactly one import path for these types.

4. **The proposal fires once per graph, not once per change.** Everything the effect reads outside
   its trigger is read `untracked`, and a `proposedHandle` guard makes "Clear" stick. Pinned by
   *clearing a proposal stays cleared — the proposer does not re-seed it*.

## The joints, and what each sends

| Surface | Affordance | What it sends | Source sentence rendered |
|---|---|---|---|
| Explore — trail bar | `→ Studio (N pinned)` button, `data-testid="trail-send-to-studio"` | pins if any, else the whole trail | `3 pinned steps` / `your trail (5 steps)` |
| Explore — keyboard | `Ctrl+E` (was a bare navigate to empty panes) | the current selection | `“POST /checkout”` |
| Insights | `Compose context →`, `data-testid="insight-send-to-studio"` | the insight's `Focus`/`Node` target | `the insight target GET /orders` |
| NodeCard | `→ Studio`, `data-testid="node-card-send-to-studio"` | that node id, flow + bodies + usage | `the node “OrderService”` |
| Studio (no sender) | — | pins → trail → archetype preset | `2 pinned steps` / `this repo's top 3 flows` / `this library's 2 widest public types` |

A `Filter` insight action targets an entry KIND, not a symbol, so it gets no button — a pack
cannot be rooted at it. Same test as the routed action, so the two affordances can never disagree
about whether a target exists.

## Honesty properties this checkpoint had to keep

- **A proposed pack is never dressed as a composed one.** The banner
  (`data-testid="studio-proposal-banner"`) says `Proposed from <source> — edit it, or start over.`
  and disappears on the first edit (add / remove / reorder / body toggle). Pinned by *an edit makes
  the pack the reader's — the banner goes away*.
- **Nothing silently picks between two sources.** The trail-bar button's LABEL says whether it will
  send pins or the trail; Explore's toast names the source and the count, and reports the steps that
  no longer resolve rather than dropping them.
- **Ctrl+E still opens Studio when there is nothing to carry** — it lands on the archetype preset
  instead of telling the reader to go back and explore first.
- **A refused navigation is reported.** `open()` returns the router's own verdict and the senders
  toast an error rather than assuming the room opened.
