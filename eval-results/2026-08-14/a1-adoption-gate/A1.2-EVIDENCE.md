## What was held fixed, and how that was established

The pilot's B-vs-G contrast was disqualified because adoption was 0.015 - the treatment arm barely
touched the thing under test. A1.2 asks the one question that decides whether the study is worth
running: with the trust pack's curated, described surface, does an agent reach for the tools on
its own? For that to be an answer and not an artefact, everything except the surface had to be
identical to the pilot, and each of these was measured, not asserted:

- **Prompt byte-unchanged.** `system.txt` untouched since b951f60 and `questions/eShop.json` since
  e210f51, both 2026-08-10 pilot commits. The only argv-adjacent change to `run-probe.mjs` since
  the pilot (8807f48) is arm BI's derivation guard, the derived `mcp.json`, and `--results-dir`;
  arm B's own argv is untouched.
- **The surface really did change.** `wire-surface/wire-truth.json` in this directory: 14 tools,
  14/14 with a non-empty description, 52/52 params described. The pilot ran against 22 tools with
  **empty** descriptions. The gate's own pre-flight line confirms it from the rows themselves -
  `mcpToolsOffered` 14 (pilot: 22).
- **One binary under test.** The 18 rows carry two `devcontextSha` values (e15e5769, 98b0dc96)
  because the batch was relaunched across sessions. `git diff --stat e15e576 98b0dc9` is
  `.conductor/REPORT.md` (generated) + `adoption-gate.mjs` (the reporting script) - **no engine or
  Core change**, so the DevContext build the agent talked to is the same in every row.
- **Separate ledger.** Rows land in `results/a1.2-adoption-gate/runs.jsonl`, not the pilot's 54-row
  `results/runs.jsonl`; mixing old-surface and new-surface arm-B rows would silently rewrite
  RESULTS.md's published numbers.
- **The estimator is the pilot's.** Median of per-run (mcp calls / executed calls), `analyse.mjs`
  L30/L401 - the statistic that produced the published 0.015. Recomputing it over the pilot's rows
  returns 0.0147 and 17/18 below floor, matching RESULTS.md §2 exactly. Pooled (0.354) and mean
  (0.335) are printed beside it and are **not** substituted; here all three clear the floor, so the
  verdict does not depend on that choice.

## What the number does not say

Reported because a clearing gate is exactly when it is tempting to stop looking:

- **5 of 18 runs are still below the floor, and 4 made no MCP call at all.** Three of those four are
  all three reps of **eshop-f1**, which every time answered with 2 non-MCP calls for ~$0.05. f1 is
  a question the agent does not think needs the tools; it contributes 0.00 three times. The fourth
  is eshop-a1/rep2, which executed 15 calls and chose Read/Grep for all of them.
- **Adoption is not dominance.** Across the batch: 80 MCP calls vs 146 native calls (66 Read,
  45 Grep, 30 Bash, 5 Glob). The agent now *reaches for* the tools; it has not switched to them.
- **11 of the 14 curated tools were used at least once** - `read_source` 18, `analyze` 14,
  `overview` 8, `resolve` 8, `usages` 7, `trace` 6, `find` 5, `impact` 5, `entrypoints` 4,
  `neighbors` 4, `map` 1. Adoption is spread across the surface, not one tool carrying it.
- **This is adoption, not usefulness.** The gate is a manipulation check: it licenses the study,
  it does not say the tools produced better answers. That is W3's job.
- **eShop only.** Per-repo generalisation is not claimed; the unseen repo (Driewie, A1.1) is where
  that gets tested.

## Consequence for W3

Sizing for the full run should come from these rows, not the pilot's: cost per run is bimodal
(~$0.85 for the call-heavy c1/b1/a1 questions, ~$0.05-0.12 for d1/e1/f1), averaging $0.36/run.
f1's three zero-adoption reps are a live input to the question mix pinned in A1.1 - a question that
never touches the tools carries no information about the MCP in a B-vs-G contrast.
