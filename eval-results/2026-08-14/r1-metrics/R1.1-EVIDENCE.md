## 3. #22 `graph.orphans` — **RETIRED**. It inverted, and it fires 0/10 true.

Dormant on 11/11 poles in 2026-08-02 because the Semantic-share floor (0.5) was unreachable. Post-E1
the floor is cleared on **seven of twelve** poles and the full five-clause gate passes on two — and
on both of those the insight emits a `Notable` card naming five types.

The claims, hand-verified in the target repos (this is the measurement, not a reading of the card):

**eshop-microservices** — card basis: *"58% of 199 Calls edges verified, 30/34 entries wired"*

| claimed dead | truth | evidence in the repo |
|---|---|---|
| `CheckoutBasketEndpoints` | **FALSE** | `public class CheckoutBasketEndpoints : ICarterModule` — a live HTTP endpoint, registered by Carter's assembly scan |
| `DeleteBasketEndpoints` | **FALSE** | `: ICarterModule` (same) |
| `GetBasketEndpoints` | **FALSE** | `: ICarterModule` (same) |
| `StoreBasketEndpoints` | **FALSE** | `: ICarterModule` (same) |
| `CachedBasketRepository` | **FALSE** | `Basket.API/Program.cs:28` — `builder.Services.Decorate<IBasketRepository, CachedBasketRepository>();` |

**5/5 false.** The insight named the Basket service's entire HTTP surface as possible dead code.

**VerticalSlice** — card basis: *"69% of 42 Calls edges verified, 5/7 entries wired"*

| claimed dead | truth | evidence in the repo |
|---|---|---|
| `DataSchemaConstants` | **FALSE** | read by `GuestUserConfiguration.cs:17`, `OrderConfiguration.cs:26`, `Update.UpdateContributorValidator.cs:17` |
| `EventDispatchInterceptor` | **FALSE** | `InfrastructureServiceExtensions.cs:19` `services.AddScoped<EventDispatchInterceptor>()` + `:24` `GetRequiredService<EventDispatchInterceptor>()` |
| `FakeListContributorsQueryService` | **FALSE** | `InfrastructureServiceExtensions.cs:71` `services.AddScoped<IListContributorsQueryService, FakeListContributorsQueryService>()` |
| `VogenEfCoreConverters` | ambiguous | only reference is a commented-out `RegisterAllInVogenEfCoreConverters()`; source-generated Vogen infrastructure |
| `FakeEmailSender` | ambiguous | the registration found is commented out (`ServiceConfigs.cs:21`) |

**3/5 false outright, 2 unresolvable, 0 confirmed true. Measured precision across both poles: 0/10.**

### Why no value of the floor fixes this

Every false claim is live by **registration**, not by a call edge:

- `diTypes` excludes `d.ServiceType` — the SERVICE type of `AddScoped<TService, TImpl>`. The
  **implementation** is never excluded, which is precisely what `FakeListContributorsQueryService`
  was accused of being.
- Assembly-scan registration (`ICarterModule`) is invisible by construction. The `implemented`
  exclusion protects the *interface*, never the *implementer*.
- Decorator registration (`Decorate<,>`) is not a DI verb the detector reads.

The coverage floor was a proxy for "the graph saw all inbound references". The measurement shows the
proxy fails in the wrong direction: at 58% and 69% verified — comfortably above the bar — precision
is still zero, because the reason these types are live is not something a call-edge share can
observe. Raising the floor would re-suppress the claim without making it true, and would break again
on the next graph improvement. **eShop (0.438), self (0.457) and CleanArchitecture (0.452) sit one
E1-sized step below the floor**, so the alternative to acting is shipping this claim on the flagship
pole next.

### What was done

- `src/DevContext.Core/Insights/GraphOrphansSource.cs` — **deleted**.
- `tests/DevContext.Core.Tests/GraphOrphansSourceTests.cs` — deleted (its subject died).
- `DiscoveryPipeline.ComputeInsights` — registration removed, with the reason and the revival
  condition at the site.
- `eval/lens-audit.ps1` — the P7 `orphans-validity` liveness grep is now a **retirement ratchet**:
  if any insight with id `graph.orphans` is ever emitted again, the audit fails. That grep would
  **not** have caught this either — its liveness patterns are `new X(`, `: … X` and `DbSet<X>`, and
  every false claim above is live by registration, which matches none of them. A revival must bring
  a registration-aware liveness model and its own probe.

## 4. #23 L3.4 hub-scope broadening — **HELD; the "never fires" premise is REFUTED**

`GraphBuilder.Seams.cs:200` asserted **"THIS BROADENING NEVER FIRES"** on the strength of 11 poles
that all read `sparseGraph=false`. Measured on this build: **Hangfire reports `sparseGraph=true`,
`hubScopeNodes=34`.** The broadening is live, shipped behaviour that binds up to 500 synthesised
Calls edges on library-shaped repos, and this is the first measurement of it firing. The old comment
was not stale about a number — it was wrong about a fact, because the G10 pole set never contained a
repo that clears both gates.

The rest of the old comment's puzzle now has arithmetic. Four poles satisfy the gate (`MediatR`,
`FluentValidation`, `AutoMapper`, `Hangfire` — 0–2 entries); only Hangfire reaches the hub stage.
With 0 entries the first gate cannot return, so the other three **must** exit at `k < 5`, i.e.
`model.CallEdges` spans fewer than ten distinct types on each. AutoMapper carries 259 Calls edges in
the finished graph — so those edges are not coming from `model.CallEdges`, and this method sizes its
hubs off a channel that is no longer the graph's main call source (the BodyFacts path is). Filed as
**conductor bug #18**; not fixed here, because making it fire on three more repos adds synthesised
edges to the product and needs a matrix, not a threshold edit.

The gate is **unchanged** and the comment now states the 2026-08-14 measurement and its calibration
commit.

## 5. #24 deep-spine ratio — **RETIRED**

Saturated then, saturated now, and E1's 8x Semantic lift moved it **not at all**:

- `1.000` on eight of twelve poles (TodoApi, VerticalSlice, CleanArchitecture, MediatR,
  dotnet-podcasts, eshop-microservices, Hangfire, self)
- `0.982` on eShop and `0.994` on FastEndpoints
- `0` only on FluentValidation and AutoMapper, which have **zero entries** — a divide-by-zero
  artifact, not a measurement

Every one of the five before/after poles reads the same value it read on 2026-08-02. "≥2 steps"
means "the entry reaches one thing", which is now true of essentially every entry that exists, so
the row the report shipped as coverage (`| Deep spine (>=2) | 107/109 (98%) |`) reads the same on
every repo and separates none of them. Its design origin (`proposal-loom.md:312`, *"entries with
≥2-deep spine ≥70% on non-CQRS repos"*) was a build-time acceptance bar, met with room to spare on
every pole measured since.

**The bar was not raised.** Where a useful one sits is a question about the step *distribution*,
which no surface exposes; inventing a 3 or a 4 by eye is not a calibration. Removed:
`GraphStats.Compute` / `GraphQuery.Stats` tuple members, the `ReportRenderer` row, and the
`entriesWithDeepSpine` / `deepSpineRatio` fields of the CLI `query stats` payload. No proto field
carried it (no contract change) and no golden or expectation file pinned the row — checked before
deleting.
