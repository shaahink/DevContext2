## 1. The binary ships

`pnpm publish:mcp` publishes `DevContext.Mcp` into the **same** `src-tauri/resources/server`
directory as the server, and `beforeBuildCommand` now runs `pnpm publish:sidecars`
(`publish:server && publish:mcp`). `bundle.resources` already globs `resources/server/**/*`, so
the installer picks it up with no manifest change.

That directory is where `McpBinaryLocator` probes **first**, so the shipped shell resolves the
shipped copy. Proven by starting the published server out of that directory — the byte-for-byte
layout an installer lays down — on a spare port and asking it (`n42-verify-bundle.mts`, 5/5 PASS):

```
PASS  the published server starts out of the bundle directory — …\resources\server\DevContext.Server.exe on :5183
PASS  the bundled server finds a devcontext-mcp — …\resources\server\devcontext-mcp.exe
PASS  and reports it as source "bundle", not dev-build — source=bundle
PASS  the path it found is the copy inside the bundle directory — …\resources\server\devcontext-mcp.exe
PASS  every host snippet an installed user copies names that bundled path
```

The page's old sentence — "ships with the desktop installer" — was false when N0.2 deleted it.
It is now true, and the probe is what says so.

## 2. The snippets stopped inventing a path

The three host snippets were a `const` in `mcp-page.ts` built around
`C:/path/to/DevContext2/src/DevContext.Mcp/bin/Debug/net10.0/devcontext-mcp.exe` — a string that
reads like a real machine's path and exists on none.

They are now composed **server-side**, by the same code that writes the config file
(`McpConfigWriter.Snippet`), around the same probe result the status card renders, and arrive on
`GetMcpStatusResponse.hosts`. The page renders them; it owns no template. Live, against the dev
server (`n42-verify-setup.mts`):

```
PASS  every host snippet names the ABSOLUTE path the probe resolved —
      probe: C:\Code\DevContext2-desktop\src\DevContext.Mcp\bin\Debug\net10.0\devcontext-mcp.exe
      snippets: {"claude":"…devcontext-mcp.exe","cursor":"…devcontext-mcp.exe","vscode":"…devcontext-mcp.exe"}
PASS  no page-side placeholder survives
```

When nothing is found the snippet carries `<absolute path to devcontext-mcp.exe>` — bracketed so
it cannot be mistaken for a path anyone has — and the setup note says to build it.

## 3. Write the config for me

New RPC `WriteMcpConfig(handle, host)` writes the **project-scoped** config into the analyzed
repo: `.mcp.json` (Claude Code), `.cursor/mcp.json` (Cursor), `.vscode/mcp.json` (VS Code, keyed
`servers`, entry typed `stdio`).

Project-scoped, not user-global, on purpose: `~/.claude.json` is a file this server cannot verify
it edited correctly and that carries every other project's servers, and decision 3 (N3.2's pack
hand-off) already set the repo-file-first precedent. It is also reviewable with `git status`.

It **merges**. Live, into a temp copy of `tests/fixtures/ControllerApp` pre-seeded with a
`github` MCP server, analyzed by a real agent over stdio:

```
PASS  the page targets the repo the agent just analyzed
PASS  the config was written into the analyzed repo, naming the probed binary
      …\devcontext-n42-RWoNAz\.mcp.json -> …\devcontext-mcp.exe
PASS  the MCP server that was already registered there survived the merge
      {"github":{"command":"gh-mcp","args":["--stdio"]},"devcontext":{…}}
PASS  the page reported an UPDATE, because a config was already there — Updated .mcp.json
PASS  the written command is a file that exists
PASS  a host with its own file layout and key gets that layout — Wrote .vscode/mcp.json -> {"servers":{"devcontext":{"type":"stdio",…
PASS  a second click reports UNCHANGED instead of claiming another write — .mcp.json already points here
```

A file it cannot parse is **refused**, not overwritten; a `servers` key that is not an object is
refused; a machine with no binary is refused rather than handed a config naming nothing.

## 5. Two findings worth not re-deriving

**The default `System.Text.Json` encoder escapes the HTML-sensitive set**, so the placeholder's
angle brackets — and any non-ASCII repo path — came out as escape sequences in both the written
config and the snippet on screen. `McpConfigWriter` pins
`JavaScriptEncoder.UnsafeRelaxedJsonEscaping`; this output is a config file and a human-read
snippet, never HTML. Related: on Windows the command is a backslash path and JSON escapes every
separator, so `Assert.Contains(binaryPath, snippet)` fails for reasons unrelated to meaning —
parse the snippet and compare the `command` value.

**`resources/server` is a third binary copy, and it goes stale like the other two.** The first
bundle probe FAILED its snippet check because the published server predated the proto change by
four minutes: it answered `GetMcpStatus` without `hosts`, and an installed machine would have
rendered no host cards at all. Re-run `pnpm publish:sidecars` after any proto/server edit before
believing a bundle measurement. The dev probe cannot catch this — it runs out of `bin/Debug` and
reports `dev-build`, which is why there are two probe scripts and not one.
