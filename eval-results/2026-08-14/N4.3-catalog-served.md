## 1. The catalog, served — `ListMcpTools` (commit 6c2501e)

BUG-BACKLOG **#4**: the page carried its own literal array of eight tool names. It offered
`search`, which the MCP has never exposed (it is `find`), and `insights`, folded into `stats` by
G2.1. The failure mode is a *label*, so nothing errored, and `eval/contract-sweep.ps1` cannot see
it either — the sweep asks whether a proto field has a reader, and this was a hand-written string
with no field involved.

The fix is structural. `ListMcpTools` spawns the resolved `devcontext-mcp`, runs a real
`tools/list`, and **also calls one name that does not exist** so the unknown-tool envelope yields
the unlisted specialists and the folded aliases. There is no protocol call for "what did you not
advertise" — by design (T1.2) — so we ask the question an agent asks by accident.

| Fact rendered | Where it came from |
|---|---|
| tool names + descriptions | `tools/list` reply |
| parameter names, types, required-ness, descriptions | each tool's `inputSchema` |
| the 8 unlisted specialists + what each answers | unknown-tool envelope, `specialistTools` |
| the retired/folded names + replacement call | unknown-tool envelope, `retiredTools` (new) |

`retiredTools` is new on the envelope, read off the same `Folded` table the per-name hint uses.
It makes the agent's reply better too — an agent carrying an older prompt now gets the whole map
in one answer instead of only the row matching the name it happened to guess.

**Design notes** (so the next reader does not re-derive them):

- `McpHandshakeProbe.ConverseAsync` gained an **optional** `includeUnlisted` flag rather than a
  second conversation. N4.1's existing fake-reader tests still drive the 3-argument overload
  unchanged, and the handshake card's behaviour is untouched (it passes `false`).
- Specialists carry `why` and an **empty** `description` on purpose. `tools/list` never described
  them — they are not on it — so putting the envelope's sentence in the field that means "off the
  wire" would fake a wire fact.
- The Try-a-Tool select **is** the served menu. What this page can drive over gRPC is a smaller
  set, so the rest are rendered *disabled with a reason* rather than hidden: an omission is
  exactly how the old literal array read as complete.

## 2. The feed in the agent's vocabulary

The feed was keyed on the gRPC method the server ran, because that is the only name the server
ever knew. An agent asked for `trace` and watched `GetTrace` go past, and one MCP verb can be
several RPCs.

The audit offered two mechanisms: map server-side, or wrap at the tool layer. **Mapping
server-side would be a table of gRPC-method → MCP-name kept next to, and drifting from, the real
tools — the exact defect #4 was.** So the name travels *from* the tool layer:

- `ScopedMcpServerTool` wraps every tool `McpToolMenu.Build` produces (both halves, so an unlisted
  specialist tags its calls exactly like an advertised one) and opens an `AsyncLocal` scope for
  the whole invocation.
- `McpCallHeaderInterceptor` on the channel copies that scope onto every outgoing gRPC call. One
  place, so no tool can forget; a tool that makes three RPCs tags all three.
- The header names live in `DevContext.Contracts/McpCallHeaders.cs` — the one project the sidecar
  and the server both reference. Two literals in two projects is how a header quietly stops
  matching after a rename.
- The two free-text values travel **base64 of UTF-8** (`-b64` in the name). gRPC metadata on a
  non-binary key is ASCII by spec, and a focus is whatever a user typed in whatever script their
  codebase uses.

`args_digest` is **revived with a producer**. S9's contract sweep removed it because it was dead
on both ends; it now carries the arguments the agent sent, minus the session handle, truncated to
a row's width — and it is rendered.

`mcp_tool` is empty for UI-origin calls and the row keeps the RPC name: the app is not an agent
and must not be dressed as one.

Two riders that fell out of this:

- **`analyze` is finally in the feed.** It is the first thing an agent does and it was the one
  call this server never recorded — `WrapT` records on session *access*, and `analyze` is what
  creates the session, so a watcher saw an agent's whole opening move as silence. Recorded after
  the work succeeds, so a failed analysis does not log as one that happened.
- **The origin tag gets a proof.** `x-mcp-tool` is only ever sent by the sidecar, so its presence
  now decides `origin = agent` outright; N4.1's header heuristic stays as the fallback for
  everything that does not send it.

## 4. What is NOT proven here

`ListMcpTools` was exercised through its unit-level surface and the page against a stubbed API.
**It has not been driven against a live `devcontext-mcp` process in this session** — that is a
Playwright/live probe, and the session's token budget ran out before it. The pieces it depends on
were each measured live in N4.1/N4.2 (the spawn, the handshake, the binary probe), and the new
code path is the same spawn with two more JSON-RPC lines. Treat the live catalog read as
*unmeasured* until the next session runs it.

## 5. Open — the deep links

The fourth sub-item of N4.3, *rows deep-link: `trace` → Explore at that focus, `get_context` →
replay-in-Studio*, did **not** land.

The producing half is already in place: `McpCallScope` computes a `PrimaryArg` (first of
`nodeId`, `focus`, `query`, `symbol`, `key`, `path`) and the sidecar sends it as
`x-mcp-arg1-b64` on every call. What is missing is the field and the navigation.

`ToolCallEvent` field **11 is reserved, deliberately not declared**. R-T1 says a field lands with
its reader, and `eval/contract-sweep.ps1` enforces exactly that — declaring `primary_arg` with no
navigation reading it would have been a gate failure dressed as progress. The next session
declares field 11, reads the header in `RecordToolCall` (one line, beside `argsDigest`), and
wires the two routes.
