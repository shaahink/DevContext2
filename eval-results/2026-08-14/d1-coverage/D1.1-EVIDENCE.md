Kind has a producing path (descriptor→signal→extractor→builder→entry); proven RED on the Orleans and

**Session:** s21, 2026-08-14. Branch `feat/pre-release-engine`.

---

## 1. What was built

`tests/DevContext.Core.Tests/CatalogReachabilityTests.cs` — a live sweep, not a static audit.

It generates a **consumer-app repo** (42 projects, one per `EntrySurfaceCatalog.All` descriptor) into
`%TEMP%/dc2-catalog-coverage`, analyses it **once** through the real `TestPipeline`, and measures two
properties per descriptor:

| | property | how it is measured |
|---|---|---|
| **P1** | the signal is reachable | the descriptor's own project fires it → `model.Architecture.Has(key)` |
| **P2** | the Kind has a producing path | that project produces ≥1 `EntryPoint` of the declared Kind |

Three fixture rules make the measurement honest, and weakening any of them weakens the gate:

1. **Packages and SDK hints come from the catalog, never from the test.** The csproj is generated from
   `descriptor.Packages` / `descriptor.SdkHints`, so a green can only come from the catalog's own
   declaration. Only the *source shape* lives in the test.
2. **Projects are named `Consumer01…Consumer42`.** `SelfNamePatterns` is a **self-source** map — it
   keys on the analysed repo's own project names and means "this repo IS the framework". A consumer
   app cannot use it. Naming a fixture project `OrleansHost` would have made the Orleans hole
   invisible.
3. **Each shape is what a consumer app naturally writes**, not the one path known to work. This is
   what caught the TimedJob find (see §2, row 3).

Known limit, stated rather than hidden: signals are repo-wide, so P2's *extractor gate* can be
satisfied by a sibling project's signal. P1 is the per-descriptor half of the pair and is not
maskable that way, because every project declares only its own descriptor's packages.

## 3. The allow-list is a ratchet, not a mute

`eval/expectations/catalog-reachability-allow.txt` — one line per hole, `<id> = <measured reason>`.
The sweep fails in **both** directions:

* an unlisted hole fails ("add it with the measured reason");
* a **listed hole that has become reachable also fails** ("delete this line — the file only ratchets
  down"), so D1.2/D1.3 must delete the line in the same commit that closes the hole.
