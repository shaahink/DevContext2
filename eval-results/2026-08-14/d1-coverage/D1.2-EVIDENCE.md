## 1. Orleans packages on the descriptor — commit `a6360e4`

`Packages: []` left `SelfNamePatterns` as the only mechanism, and that map is a **self-source** map
keyed on the analysed repo's own project names. No consumer app could fire the signal, so
`OrleansGrainExtractor` never ran and `GrainMethod` entries could not exist outside Orleans' own repo
— which self-sources to Library and renders no grains either.

Fixed with one family key, `"Microsoft.Orleans"` — the idiom `"AspNetCore.HealthChecks"` already uses
in this catalog. I tried the four leaf ids (`.Server/.Client/.Sdk/.Core`) first and **measured** that a
provider-only project (`Microsoft.Orleans.Persistence.AzureStorage`) misses them, because
`TryMatchSignal`'s fallback is `StartsWith`, not "same family".

* **ratchet fired** ([`orleans-ratchet-run.txt`](orleans-ratchet-run.txt)) — with the descriptor fixed
  and the allow-list untouched, the sweep failed with *"these are now REACHABLE — delete their lines"*
  for `signal:orleans` and `kind:GrainMethod@orleans`. The closure proving itself.
* both lines deleted; sweep green.
* **seals** ([`orleans-green-run.txt`](orleans-green-run.txt), 71 tests): a consumer app fires the
  signal from each of five real package shapes, **and** Orleans' own repo still self-sources at
  `0.7 / "ProjectName"` even though its satellite carries `Microsoft.Orleans.Core` as a NuGet
  reference — the guard `ArchetypeDetector.IsSelfSourcedFrameworkSignal` depends on to keep calling
  the framework's own repo a Library.

## 2. Avalonia descriptor + WinForms `Exe` case — commit `fa1d57f`

Both are **signal-side only**: `DesktopEntryExtractor` already handled `Form`, `Window` and
`UserControl`; nothing ever told it to run.

* **WinForms declared `Exe` rather than `WinExe` fired nothing** — no package, no WindowsDesktop SDK,
  no WinExe. `<UseWPF>`/`<UseWindowsForms>` is the property that *makes* a project a desktop app and it
  is independent of `OutputType`; the flags were already parsed onto `ProjectInfo` and already read by
  `ArchitectureStyleDetector.IsDesktopUiProject` — the signal simply never looked at them. Fixed in
  place with the same shape and guard as the `UseMaui` probe four lines below it.
* **Avalonia** was documented in `DesktopEntryExtractor` and undetectable: no Avalonia package or SDK
  in the catalog. Added as a family key, so `Avalonia.Desktop`/`.Themes.*`/`.ReactiveUI` come with it.

This is where the instrument grew the half D1.2 needs — **named consumer-app shapes, each analysed in
its own one-project repo**. The isolation is load-bearing: signals are repo-wide, so putting these in
the 42-project sweep would let a sibling project's signal satisfy the extractor gate and hide the hole.

* **red first** ([`shapes-red-run.txt`](shapes-red-run.txt)): both shapes reported
  `signal desktop-ui: MISSING / kind UiEntry: MISSING / entries produced: (none)`.
* **green after** ([`shapes-green-run.txt`](shapes-green-run.txt)): 73 tests.
* Honesty note recorded in the fixture itself: a **WinExe**-declared Avalonia app was *already*
  detected by the generic `Microsoft.NET.Sdk + WinExe` rule, so the fixture is deliberately the
  `Exe`-declared cross-platform head — the shape that got nothing.

## 3. BackgroundService / IHostedService base-type detector — commit `7aa80ee`

Hosted services were detected **only** through `AddHostedService<T>` appearing in scanned
Program/Startup flow. Registration happens out of sight constantly — Scrutor assembly scanning, a
library's own `AddXxx()` extension, the Worker SDK's generated host, a host composed outside the scan
scope — and every one of those workers produced no entry at all.

`WorkerEntryPointBuilder` now also walks `model.Types` for direct `BackgroundService` /
`IHostedService` / `IHostedLifecycleService` implementations. Two deliberate limits, both in the code:

* it reads `BaseTypes`, which `SyntaxStructureExtractor` fills in **every** mode — unlike `SourceBody`,
  which exists only under `BuildFullGraph`/`Debug`/`Full`. An entry's existence must not depend on the
  extraction profile.
* the base list **as written**, so an intermediate abstract base (`class MyWorker : WorkerBase`) is not
  matched. That needs the type hierarchy, not a name, and a wrong guess mints entries for classes that
  are not workers.

The registered path is untouched — the detection loop runs first and its `seen` set wins.

* **red first** ([`hostedservice-red-run.txt`](hostedservice-red-run.txt)): with the builder stashed,
  the `hosted-service-unregistered` shape (a `BackgroundService` plus a Scrutor scan, no
  `AddHostedService` anywhere) reported `kind HostedService: MISSING / entries produced: (none)`.
* **green** ([`hostedservice-green-run.txt`](hostedservice-green-run.txt)): the **whole non-eval Core
  suite** — 806 passed, 0 failed, 2 pre-existing golden skips — so no existing worker, entry or golden
  expectation moved.

## 4. TimedJob — measured, and it belongs to D1.4

The checkpoint offers "a TimedJob producer **or** an honest deletion of the kind". The measurement says
**neither, yet** — and names the session that can close it:

* The only evidence that a worker is timer-driven is its **body**, and both carriers of a body —
  `TypeDiscovery.SourceBody` and BodyFacts — are populated only under `BuildFullGraph`/`Debug`/`Full`
  (`SourceBodyExtractor.cs:27-29`). A builder-side timer rule would therefore make an entry's **KIND**
  depend on the extraction profile: the same repo would report Background in Map mode and Scheduled in
  Full mode. That is a worse defect than the one it fixes, so I did not write it.
* Deleting the kind would also delete the one path that genuinely works today (DNTScheduler's
  `AddJob<T>` / `AddScheduledTask<T>`, which `ProgramCsFlowExtractor.ExtractSchedulerJobs` reads).
* **The honest producer is D1.4's.** Hangfire's `RecurringJob.AddOrUpdate<T>` and Quartz's
  `ScheduleJob<T>` are *registration syntax in Program.cs* — visible in every mode, in exactly the
  place `ExtractSchedulerJobs` already walks. Setting `BackgroundWorkerKind.TimedJob` there gives the
  never-set enum member its first producer and deletes the `kind:ScheduledJob@-` allow-list line.

That reasoning is now the allow-list line's own text, so the next session reads it without re-deriving
it, and the card carries a matching amendment.
