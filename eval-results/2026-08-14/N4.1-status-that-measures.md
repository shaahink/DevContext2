## Two defects the live probe found (both fixed here, neither was in the audit)

**1. The ui/agent origin tag has been wrong since the sidecar switched to gRPC-Web.**
`OriginTag.FromContentType` classified on the premise that the app speaks gRPC-web and the MCP
sidecar speaks native gRPC. `DevContext.Mcp/Program.cs` wraps its channel in `GrpcWebHandler`, so
**both** arrive as gRPC-web and every agent call was tagged `ui`. The MCP feed default-filters to
agents only — so real agent traffic had been rendering as an empty feed, and N4.1's last-agent-call
could never fire. Headers captured off the wire:

```
app      ct=application/grpc-web+proto  ua=Mozilla/5.0 … HeadlessChrome/149
                                        x-user-agent=connect-es/2.1.2  origin=http://localhost:4200
sidecar  ct=application/grpc-web        ua=grpc-dotnet/2.83.0 (.NET 10.0.9; …)
                                        x-user-agent=(none)            origin=(none)
```

`OriginTag.FromRequest(userAgent, xUserAgent, origin)` replaces it: `ui` when Origin is present, or
`x-user-agent` names connect-es, or the UA says Mozilla — three independent browser signals, any one
decisive, defaulting to `ui` so a stranger cannot inflate the agent numbers. Proven end to end: the
probe drives the real `devcontext-mcp` binary over stdio (`analyze ControllerApp` → `stats <handle>`),
and the card flips from "No agent has called this server yet" to
"Last agent call: GetStats, 0s ago — 1 agent call(s) served".

**2. The card claimed "0 watcher(s) attached" while the page itself was watching.** The status read
was fired in the same tick as the stream subscription, and the subscription lands over the network
after the unary read returns. One delayed re-read (cleared on destroy) settles it; the number still
comes from the server. Live: `1 watcher(s) attached`.
