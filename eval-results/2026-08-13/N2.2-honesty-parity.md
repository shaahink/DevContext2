## What the checkpoint claimed and what was measured

**Claim 1 — honesty-note parity.** `get_context` has never let the ≥85%-fill promise fail silently
for an agent: since D5.1 an under-filled pack says WHY (the budget cut content, or the focus's
connected subgraph is small) and offers better-connected focuses. `GetContextPack` returned the same
sections with none of it, so the *human's* pack was the less honest of the two faces.

It is computed **once, in the kernel** — `ContextPackBuilder.BuildFillNote` — and carried on the wire
(`ContextPackResponse.fill_note` + `repeated SuggestedFocus suggested_focuses`, proto fields 10/11).
The Studio renders it; it derives nothing. That is what stops the Studio becoming a third opinion.

**Claim 2 — one budget number.** It was 8000 in the MCP tool signature, 8000 in three server
fallbacks, 8000 in the app's API client — and **4000** in `prefs.store.ts`, which is the number the
Studio actually opened with. The human's pack was priced at half the agent's and nothing said so.
Now: `ContextPackBuilder.DefaultBudgetTokens = 8000` is read by every C# site, `DEFAULT_STUDIO_BUDGET`
states the same number in the app, and the slider marks it and offers a one-click reset.
It is **not** `TracePolicy.DefaultBudgetTokens` (4000) — that budgets a single TRACE, not a whole
PACK spread over N focuses, and is the most likely origin of the 4000. Both constants now say what
they budget, and a test pins that they are different numbers on purpose.

## ACCEPTANCE — a FluentValidation pack composed from types, with usage and verified counts

`tests/DevContext.Core.Tests/LibraryPackEvalTests.cs` (`[Trait("Category","Eval")]`, skips silently
when the clone is absent). Real clone: `eval-repos/FluentValidation/src/FluentValidation` (sha
94397908). Focus strings are namespace-qualified type names taken off `Map.Surface` — the exact
source and exact key the Studio's Types tab uses (`typeFocus(namespace, name)` in scope-picker.ts).

```
surface: 90 public types, 32 with in-repo usages
focuses: FluentValidation.IRuleBuilder (28 usages), FluentValidation.IValidator (9 usages),
         FluentValidation.ValidationContext (14 usages)
cards=2 sections=2 tokens=1888/8000 (fill 23%) verified=10 approx=37
usage section: 1517 tok, 20 source locations
fillNote: fill 23%: the pack already contains everything reachable from these focuses — their
          connected subgraph is small (not an error; a smaller budget fits it).
suggested focuses: (none — a library has no ranked multi-step flows to offer)
```

Every part of the acceptance is in that block: a pack **composed from types** (bare
namespace-qualified type names, never declared entry points — the input that returned an empty pack
before N2.1), carrying **usage** (1517 tokens, 20 source locations) and **verified counts**
(10 verified / 37 approx). The fill note is the real arithmetic over the pack's own totals
(1888/8000 = 23%), and the content-exhausted branch correctly offers no focuses on a library.

## A product fact this turned up (bug #5, filed not fixed)

The first run of this test **failed**, and the failure was real. Ranking the surface by member count
— the obvious proxy for "important type" — picks `DefaultValidatorExtensions`,
`DefaultValidatorOptions`, `TestHelper.ValidationTestExtension`, and **all three have zero in-repo
usages**: `usage` is the INBOUND direction, and a library's outermost public types are consumed from
outside the repo. `BuildUsageSection` returns `""` (ContextPackBuilder.cs:404), the usage card then
contributes no sections and is dropped from `pack.Cards` entirely. 58 of the 90 public types on this
surface behave that way. The Studio's Types tab ranks nothing, so it points a user straight at them.
Filed as **bug #5**; the test now selects by in-repo usage count and prints the count, so the choice
is visible rather than assumed.

## What was found broken in the resumed tree (and fixed)

Session #7 was killed by an account-level 429 before it could commit, and its tree was **incomplete**,
not merely uncommitted:

1. `budget-panel.ts` emitted `focusSuggestionPicked` from the template with **no `output()` declared**
   and used `defaultBudget` with no member — the Angular build would have failed. Both added; the
   panel's own `model(4000)` was still the old number and is now `DEFAULT_STUDIO_BUDGET`.
2. `context-studio.ts` **never bound** `[fillNote]` / `[suggestedFocuses]`, so the new wire fields
   reached nothing. Since gates Step 1a is a contract sweep that fails on a proto field no client
   reads, that would have turned the battery red as well as shipping a dead field.
3. The spec's `packResponse()` fake omitted the two new fields; `pack.fillNote.length` on `undefined`
   threw inside `repack`, which the catch turned into "server unavailable" on every card —
   **21 studio specs red**. proto3 scalars are never absent on the wire, so the fake now carries them
   rather than the client defending against a shape the server cannot send.
