## The defect, measured not read

`BodyFactExtractor.Extract(root, …)` has a receiver that is a TYPE, not a value. It is no field,
parameter or local, so `BodyFactExtractor.ResolveFromScope` yields nothing, `InvocationOp.ReceiverType`
is null, and every consumer keyed on receiver type dropped the invocation.

**THE GRAPH HAS TWO CALL-EDGE PRODUCERS, AND #11 HAD TO BE FIXED IN BOTH:**

| producer | edge shape | scope |
|---|---|---|
| `CallGraphBinder.ResolveCallee` → `model.CallEdges` → `GraphBuilder.AddCallEdges` | **member→member** | only files in the entry-seeded closure |
| `PlainCallDetector` (seam) | **member→TYPE** | every in-scope production body, no closure |

Fixing only the binder moved the member spine and left the TYPE nodes at zero: the CLI graphdump after
that first attempt read `RazorCodeVirtualizer totalIn=15, typeNodeIn=0`, and `BodyFactExtractor` /
`ExtractorHelpers` stayed 0/0 — their callers (`BodyFactsExtractor.cs`, `AntiPatternDetector.cs`) are
reached through `IDiscoveryExtractor` dispatch, so no resolved callee type ever leads the closure to
their files.

Corollary worth carrying: the audit's note that `BodyFactsExtractor` "has 3 OUT-edges resolved
Semantic" describes PlainCallDetector member→TYPE edges (`SharedAnalysisContext`, `IAnalysisCache`,
`DiscoveryContext`), not call-spine edges. A measurement that asks a TYPE node for call in-edges is
asking the seam producer, not the binder.

## The fix — one rule, two consumers

`SymbolTable.ResolveStaticReceiverType(inv, containingFile)` (new): tries the receiver's trailing
segment then its root, and returns a type only when it resolves **unambiguously** (`ResolveName`
returns its input unchanged when unknown or ambiguous, so `IsKnownFqn` IS the Law-R1 gate) to an
in-solution type that **declares the called method** — the same honesty gate as the bare-identifier
self-call arm. Consumed by `CallGraphBinder.ResolveCallee` and `PlainCallDetector.Detect`, so the two
producers cannot disagree about what a static call is. Resolution tier: `Syntactic` (approx) — a
name-resolved receiver is not semantic evidence and is not labelled as such.

## The one negative, measured and filed rather than hidden

Diffing the DevContext dumps pair-by-pair (`.conductor/self-dump-before.json` vs `self-dump-e11.json`):

```
Calls pairs   before=1380   after=2404
DISAPPEARED = 0        DOWNGRADED (Semantic → Syntactic) = 14
  e.g. Member:…LibraryArchetypeSource::Compute | Type:…Insights.Insight
```

Nothing was lost — the change is purely additive at the pair level. But `CodeGraphBuilder.AddEdge`
dedupes `(From, To, Kind)` **first-wins**, so when a member both instance-calls and static-calls the
same type, the new static match can arrive first and its Syntactic tier wins the pair. 14 of 1380
pairs (1%) now read approx although one of their call sites is semantically bound. The honest fix is
that a merged edge should carry the BEST resolution of its call sites, not the first — the audit's
call-site-multiplicity item. **Filed as a conductor bug; not fixed inside this checkpoint**, because
changing the dedupe policy moves verified counts on every pole and belongs with E1.4/R1's matrix.
