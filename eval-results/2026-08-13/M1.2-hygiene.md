## Item 1 — `MapResponse.stack`: populate (bug #7, filed and fixed)

**Measured before:** `grep Stack src/DevContext.Server/Mapping/ProtoMapper.cs` returns three hits and
**none of them is `resp.Stack`** — they are `ServiceStyle.Stack`, `OutsideScopeApp.Stack` and
`ServiceCard.Stack`. `MapModel` had no `Stack` member at all. The readers, all three of them, are
real: `identity-strip.ts:260` (`this.map()?.stack ?? []`), `atlas-page.ts:361`, and MCP `overview`
(`DevContextTools.cs:400`, plus the JSON envelope at :731). A field with three consumers and no
writer.

**Why the contract sweep missed it:** `eval/contract-sweep.ps1` fails a response field that no client
READS. This field had three readers and no writer — the opposite direction, and the sweep does not
look there. Worth knowing before trusting it as coverage.

**Verdict — POPULATE, not delete.** The fact was not missing: `MapRenderer.AppendStack` computed
exactly this list (TFM summary → web framework → CQRS → EF Core → FluentValidation → messaging →
DDD aggregates) and emitted it as the markdown `STACK  a · b · c` line. The CLI has shipped it since
E5. Only the wire dropped it. Deleting three consumers to match an empty field would have deleted a
fact the engine already had.

**Fix:** `MapModel.Stack` is built once in `MapBuilder.Build` (which already holds the
`DiscoveryModel` and the aggregates); `SummarizeTfms`/`TfmRank` moved down with it; `AppendStack` is
now four lines that JOIN `ctx.Map.Stack`; `ProtoMapper` does `resp.Stack.AddRange(map.Stack)`.

**Proof the refactor preserved behaviour:** the architecture goldens
(`tests/goldens/clean-arch-architecture.md`, `minimal-api-architecture.md`, both line 3:
`STACK  net10.0 · Minimal APIs · MediatR (CQRS) · EF Core`) did **not** move. `GoldenExtractionTests`
passes unchanged. No golden was re-declared.

**Gates added:** `MapStackTests` (4) — the model carries the tags in render order; the markdown line
is a join of that same list; no signals ⇒ empty list AND no `STACK` header; the DDD tag agrees with
`map.Aggregates`. `ProtoMapperStackTests` (2) — the wire carries it; empty stays empty.

No proto change was needed (field 13 already existed), so no `gen:proto` / Contracts rebuild.

**Two traps paid for, recorded in the ledger:**
1. `Assert.Equal(collectionExpression, someImmutableArray)` **never passes**. `ImmutableArray<T>` is
   `IEquatable<ImmutableArray<T>>` by REFERENCE, so xUnit takes the `IEquatable` path; the two
   collections print identical in the failure message while comparing false. Call `.ToArray()` on the
   actual.
2. The CQRS stack tag comes off the **MediatR signal** (or hand-rolled handler evidence), never off a
   `PackageReferenceInfo` named MediatR — `ArchitectureStyleDetector.GetMediatREvidence`.

## Item 2 — Layer/Feature lens slots hidden until the data exists

**Measured before:** `LensDef.unavailable` existed on the interface and was **never set on any lens**,
so both the `[class.opacity-50]` hint and the `if (lens.unavailable) return;` guard were dead code and
both chips were fully live. Clicking Layer ran `nodeBorderColor` → `LAYER_COLORS[l] ?? p.inkMuted`
over nodes whose `layer` is `p.layer ?? ''`; Feature's legend is literally `withStore([])`. On a repo
without the facets that is a flat grey repaint and an empty legend.

**Fix:** `LensDef.facet` names the facet a lens colours by; `LensSwitcher.lenses` is a computed that
filters on a new `facets` input, defaulting to `{layer: false, feature: false}` so an unmeasured
caller gets the honest subset. `stage.ts` measures it from the two places the canvas actually reads —
`mapResponse().topology[].layer/.feature` and `graphFacets().serviceMap.services[].layer/.feature` —
and an effect falls the lens back to Service if the selected one loses its facet (a `?lens=layer`
deep link, the archetype default at `workbench-page.ts:190`, or a re-analyze).

**Gates added:** `lens-switcher.spec.ts` (5) — neither facet ⇒ `[service, flow]`; layer only; feature
only; both ⇒ all four; and the default input is the honest one.

This is the honesty gate in front of D9, not D9 itself.

## Item 3 — the `createTab` MAX_TABS lie

**Measured before:** `createTab` returned `this._activeId() ?? existing[0]?.id ?? ''` at the cap —
indistinguishable from success. Three of five callers guarded with `atCap()` first and were fine.
**`single-instance.service.ts:37` did not**, and it is the one where it hurts: dropping a repo on the
app (Explorer "Open with…", a second CLI launch) at six tabs called `createTab`, got an id back, and
ran `session.analyze(spec)` — **into the tab the user was already looking at**, replacing that
session, with no message.

The existing spec blessed it: `expect(ids).not.toContain(overflow === activeBeforeOverflow ? 'never' : overflow)`
always checks the literal `'never'`, so it passed regardless of the return value.

**Fix:** `createTab(): string | null`. `single-instance` toasts the limit and returns without
analyzing; `tab-strip.newTab()` (also the Ctrl+T path) toasts instead of no-opping; `session.analyze`
guards its `?? createTab(...)` fallback. `setActive`/`tabById`/`closeTab` widened to `string | null`
so a refused create can be passed straight through as a no-op rather than a type error.

**Gate strengthened (not weakened):** the cap test now asserts `overflow` is `null`, the active tab is
unchanged, every id in the successful batch is non-null, and no tab with the overflow path exists.

## Item 4 — dock resizer (closes the W4 remainder TODO)

**Measured before:** `TODO(W4 remainder): dock drag handles (Ctrl+Shift+L is the only control today)`
— the inspector was 0/30/40/100% and nothing between.

**Fix:** a `role="separator"` handle between Stage and Inspector (`data-testid="dock-resizer"`), with
pointer-capture drag, keyboard nudge (Left/Right ±2%, Home resets), double-click reset, `aria-valuenow`
= the live width, clamped 20–70%, persisted as `prefs.dockWidth` (null = "use the level's width", so
the three Ctrl+Shift+L stops stay meaningful and a level change clears a stale drag). No handle at
level 3 — there is nothing to its left to resize.

**Gates added:** `workbench-page.spec.ts` "dock resizer (M1.2)" (6) — starts at the level width;
±2% steps persist; clamps at both ends; Home restores; Ctrl+Shift+L clears the override; non-resize
keys ignored.

## Item 5 — high-contrast theme selectable

**Measured before:** `styles.css:235` carries a **complete** `[data-vibe="modern"][data-theme="high-contrast"]`
palette (#000/#fff, 2px borders), `modern.ts` declares `themes: ['dark','light','high-contrast']`, and
`ThemeService.setTheme` would have accepted it. The Settings appearance row hardcoded a Dark button
and an `@if (…includes('light'))` Light button — **no button ever offered high-contrast**. The theme
was implemented and unreachable.

**Verdict — SELECTABLE, not removed.** Deleting a working accessibility theme before release would be
the wrong call, and the substance was already there.

**Fix:** the appearance row is now `@for (t of theme.vibeDef().themes; track t)` with a
title-casing label helper, so anything a vibe declares is offered and a future theme cannot ship
invisible. Buttons carry `data-testid="theme-<id>"`.
