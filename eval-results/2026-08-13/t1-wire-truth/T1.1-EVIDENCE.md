## 1. The question the checkpoint asked, and the answer

BUG-BACKLOG #5 named a *candidate* root cause — `<GenerateDocumentationFile>` missing from
`DevContext.Mcp.csproj` — and explicitly forbade fixing by reading that paragraph. So it was
measured, in three builds, with the same instrument and the same binary path.

| build | tools | described | params described | `tools/list` payload |
|---|---|---|---|---|
| **pre-fix** (`pre-fix/`) | 22 | **0** | **0 / 68** | 6055 chars (~1514 tok) |
| **`<GenerateDocumentationFile>true</GenerateDocumentationFile>`** (`mech-xmldoc/`) | 22 | **0** | **0 / 68** | 6055 chars — byte-identical |
| **`[Description]` on `Analyze` only** (`mech-spike/`) | 22 | 1 | 2 / 68 | 6478 chars |
| **post-fix** (`post-fix/`) | 22 | **22** | **68 / 68** | 16730 chars (~4183 tok) |

**The verdict: ModelContextProtocol 1.4.0 does not read the XML doc file.** Row 2 is the
measurement that matters — `devcontext-mcp.xml` **was** emitted (10,697 bytes, next to the exe) and
the wire did not change by one byte. The backlog's candidate root cause is REFUTED as a fix. Row 3
is the positive control on the same build: one `[Description]` attribute, one described tool.

The csproj now carries that verdict as a comment so nobody re-tries the XML route, and
`<GenerateDocumentationFile>` was reverted — it costs an IDE0005 build break under
warnings-as-errors and buys nothing on the wire.

## 2. What shipped

- 22 `/// <summary>` XML summaries on the tool methods → 22 `[Description]` attributes carrying the
  same text (sharpened where the summary predated a fix). The summaries were **deleted, not kept
  alongside**: two spellings of one sentence, one of which never reaches the wire, is exactly how
  this defect survived a year unnoticed.
- 68 parameter `[Description]`s — new text; none existed before. `handle` (21 tools) and `nodeId`
  (7 tools) are single-sourced `const`s so the sentence cannot fork.
- `eval/mcp-qa/wire-truth.js` — the instrument, which exits non-zero on any undescribed tool or
  parameter. T1.4 lifts it into the battery; it was RED on the pre-fix build (see §1 row 1) before
  it was green, which is the "proven red first" condition.

## 3. Schema tax, re-measured against the P1.2 baseline

Re-run of `eval/agent-probe/measure-tax.mjs` (same script, same arms, same trivial prompt
`reply with the word ok`, same imported argv), written to
`eval/agent-probe/results/p1.2-tool-schema-tax-post-t1.1.md`. The baseline file is untouched — the
script grew a `--label` flag so a re-measurement is a comparison rather than an overwrite.

| reading | P1.2 baseline (pre-fix) | post-T1.1 | change |
|---|---|---|---|
| turn-1 prefix delta, arm B − arm G | **2540** tok | **6549** tok | **+4009 (2.58×)** |
| DESIGN 4.4 statistic as written | 9 / 231 (prefix was **warm**) | 6549 (prefix was **cold**) | — |
| cold cross-check from recorded pilot runs | 2531 | 2531 (unchanged — those runs carry the old schemas) | — |
| cold cache write, Opus 5 1-hour TTL | $0.0254 | **$0.0655** | +$0.0401 |
| warm re-read per later turn | $0.00127 | **$0.00327** | +$0.0020 |

Both post-fix reps came back with a **cold** prefix, so DESIGN 4.4's statistic and the
cache-invariant reading coincide at 6549 and no cache-state caveat is needed this time. 4 runs,
$0.1575 total.

**The trade, stated plainly:** the tax went up 2.58×, from ~2.5k to ~6.5k turn-1 tokens, or from
4.0% to ~10.3% of a median pilot run's cost on first pay. DEEP-EVAL §4 W1.1 called this in advance
("it will grow, and the trade is deliberate"). The number to hold it to is A1.2's `mcp_call_share`
against the 0.2 floor: 6.5k tokens for a menu an agent *uses* is a better buy than 2.5k for one it
does not, and 22 described tools is the state the adoption gate is supposed to measure — T1.2's
curation is what brings the count, and the tax, back down.

## 4. A second defect found and fixed in the course of measuring

`eval/agent-probe/mcp.json` was a **committed absolute path to `C:/Code/DevContext2`**, while
`run-probe.mjs` resolves `MCP_EXE` from `REPO_ROOT`. Run from a worktree — which is how this whole
program runs — the preflight validated *this* worktree's freshly built binary and then every arm-B
`claude` run was handed the **other checkout's stale one**. Nothing in the output said so.

Left alone, A1.2's $10 adoption gate would have measured the pre-W1 surface and reported it as the
post-W1 result. `mcp.json` is now generated from `MCP_EXE` at module load, git-ignored and
untracked; DESIGN 4.4's `--mcp-config` path and the argv are unchanged.
