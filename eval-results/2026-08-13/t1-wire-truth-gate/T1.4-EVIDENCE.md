## 4. The finding that nearly made this gate a liar

The first post-fix run came back RED on the three graph-side bars — **byte-identical to the pre-fix
run**, on a tree whose fixes had landed and whose binaries were fresh.

Cause, measured (not inferred): `DevContext.Mcp/Program.cs` hardcoded `http://127.0.0.1:5179`, and
`ServerShim.EnsureServerRunning` **reuses whatever already answers `/health` there, whichever
checkout built it**. `Get-CimInstance Win32_Process` named the process serving my probe:

```
ProcessId    : 46160
CreationDate : 13/08/2026 18:25:32
ExecutablePath: C:\Code\DevContext2-desktop\src\DevContext.Server\bin\Debug\net10.0\DevContext.Server.exe
```

The **other conductor run's** engine, started 44 s after my pre-fix probe released the port. Nothing
was wrong with T1.3's fixes; the probe was measuring a different repo and reporting it as this one.
A gate that can do that is worse than no gate.

Two defences landed, both cheap:

1. **Isolate.** `DEVCONTEXT_ENDPOINT` is read by `DevContext.Mcp/Program.cs` and
   `DevContext.Server/Program.cs`; the shim-spawned server inherits the MCP's environment, so one
   variable pins a whole probe run to its own port. Probes use `127.0.0.1:5279` — never 5179, so a
   run cannot join *or* disturb a dev's server or the desktop app.
2. **Verify.** `/health` now returns `baseDirectory`, `pid`, `startedAt` (`version` alone is
   `"1.0.0"` in every checkout and cannot tell two engines apart). `server-identity.js` FAILS the
   probe unless the answer comes from this repo AND the process started *after* the last build of
   the `DevContext.Core.dll` it is about to measure — the stale-binary trap, now caught by the gate
   instead of by a confusing red three sessions later.

A measured trap inside that fix: `ServerOptions.Urls` carries a non-empty **default**
(`http://127.0.0.1:5179`), so the server's pre-existing `if (string.IsNullOrEmpty(serverOptions.Urls))`
fallback is dead code and the first version of the override never fired. The variable has to be
compared against `builder.Configuration["DevContext:Urls"]` — which also keeps explicit config
winning over the environment.

A second one, caught before it shipped: the step's fixture check must test a real FILE inside the
pin (`eval-repos/TodoApi/TodoApp.sln`), not the directory — an uninitialised submodule leaves the
directory there and empty, and the pin has no `TodoApi.csproj` at its root. The guessed name would
have skipped the three graph bars on every machine while printing a green gate.

## 5. How the step behaves in the battery

* Runs in `-Scope full` and `-Scope engine`, after the MCP QA gate, before the eval suite.
* `node` missing or `devcontext-mcp.exe` unbuilt ⇒ **FAIL** (exit 2). Not optional, not skippable.
* Either probe non-zero ⇒ **FAIL** (exit 2), with the probe's own PASS/FAIL lines printed.
* `eval-repos/TodoApi` absent (clean clone, no submodules) ⇒ the graph-side probe prints
  `SKIP … NOT COVERED by this verdict:` naming the three bars it did not check. CI initialises
  submodules, so CI covers them.
* Dumps land in `%TEMP%\devcontext-gate-wire-truth`, path printed on failure — the battery runs
  after every session and these probes write ~800 KB of raw transcript per run.
