## 1. BUG #8 — the filed mechanism is REFUTED; the true one is one token narrower

The backlog asks: *"whether the extractor walks lambda/anonymous-function bodies at all, and if it
does, whether the resulting call is attributed to the enclosing member or dropped."*

**It always walked them.** `BodyFactExtractor.WalkMember` enumerates `body.DescendantNodes()`, so a
lambda body is walked and its ops are attributed to the enclosing member. New fixture
`tests/DevContext.Core.Tests/Graph2/LambdaArgumentEdgeTests.cs` pins it on the SYNTAX tier alone:

| fixture | receiver inside the lambda | tier | edge |
|---|---|---|---|
| `..._on_a_FIELD_receiver_...` | `_store` (type scope) | A | yes |
| `..._on_a_TYPED_lambda_parameter_...` | `(IStore store) => store…` | A | yes |
| `..._UNTYPED_lambda_parameter_..._semantic_tier` | `ctx => ctx…` | B | yes |
| `..._untyped_lambda_parameter_of_a_GENERIC_helper_` | `static (_, ctx) => ctx…` | B | yes |
| `Tier_A_alone_cannot_type_an_untyped_lambda_parameter` | `ctx => ctx…` | A | **no** (the residual) |

Every fixture makes the lambda-body call the ONLY reference to its target, per the bug's own note.

**True mechanism:** a receiver rooted at an **untyped lambda parameter** is in no syntactic scope —
`ResolveFromScope`/`GetEnclosingParamType` can answer from the member's parameters, the type's fields
and a lambda's *typed* parameters, and from nothing else. Hangfire's site is worse than a
delegate-signature lookup could fix: `RetryOnException<TContext>(ref int, Action<int,TContext>,
TContext)` infers the lambda parameter's type from a **later argument**.

### What E1.3 adds: the refusal is no longer silent

A refusal deletes the node **and every edge that wanted it**. Silently, that hides a producer
regression and the lost edges together — which is exactly how `Type:…::Type(1)` lived for months.

* `CodeGraphBuilder.RefusedNodes` records distinct refused keys in first-seen order (deterministic,
  bounded by offending keys rather than by producer retries).
* `GraphBuilder.ReportInvariantRefusals` reports the tally as a `GraphInvariants` diagnostic:
  INV-A count, INV-B count, first five keys.
* **Positive control is a test, not a hope** —
  `GraphInvariantTests.The_refusal_tally_reaches_the_DIAGNOSTICS_of_a_real_build` hands a producer a
  member-keyed type and reads the line back off the *same* `DiscoveryModel` the pipeline prints from.
  Without it, "0 refusals" and "dead instrument" are the same observation.

## 4. One new defect, found by attributing that delta rather than waving at it (filed, not fixed)

Three of the eight new DevContext edges are fiction:
`GraphBuilder::ReportInvariantRefusals → Member:CodeGraphBuilder::Count` (also `::Select`, `::Take`).
Those are LINQ extension calls on `g.RefusedNodes` — an `IReadOnlyList` property — and the binder
attributed them to the **receiver ROOT's** type, minting member nodes for members that do not exist.

**Measured class size on the engine's own pole: 126 of 2453 Calls edges (5.1%) target a LINQ-verb
member id — 66 distinct phantom member nodes** (`IFileSystem::ToList`, `ProjectInfo::Select`,
`CodeGraph::Count`, …). This is the **member-side sibling of #7 and larger than #7 ever was** (4.2% of
Hangfire), and V1.3's INV-A cannot see it: a *Member* node carrying a member id is legal by
construction. Tracked bug #6; likely locus is the receiver-chain hop (`SplitReceiver` keeps the
trailing segment while the resolved type is the root's) — measure `HopThroughProperty` and
`CallGraphBinder.ResolveCallee` before touching anything.
