# T7.4 — Page-render RPC budget (audit B11) — 2026-07-17

**Checkpoint:** rendering home+atlas fired ~150 `GetTrace` + dozens of `GetNode` in ~2s (client-side
flow/hub-radar recompute per visit). Add a server-side session memo for flows/facets; drive asserts
≤15 RPCs per page navigation; a fresh page load shows <20 UI-origin calls.

## Root cause

`AtlasStore.start()` (fired on every analyze AND every boot reattach via `session.store`)
background-traced up to 100 entries with individual `getTrace` RPCs (4 workers), then a degree
-enrichment effect fired ~10 more `getNode` calls for the hub radar. The server recomputed every
trace; nothing was memoized; every app boot re-ran the whole storm.

## Fix — one memoized RPC

- **Proto:** `rpc GetFlowIndex(FlowIndexRequest) returns (FlowIndexResponse)` — per-entry
  `FlowStatRow` (focus/title/kind/found, node/depth/boundary/data counts, verifiedPct,
  touched/emitted, nodeIds/hubIds, score) + `HubDegreeRow` for the radar's top hubs (on >1 flow,
  top 10 by flow count) so no per-hub `GetNode` is needed. One regen (buf + Contracts).
- **Core:** `FlowIndexBuilder.Build(query, entries)` — ≤100 deduped entries × `Trace(focus, depth 3)`,
  DFS stat walk mirroring the retired client math (hub-vs-data split, `score = nodes × (1+boundary)`,
  focus key `"VERB route"`). Pinned by `FlowIndexBuilderTests` (3).
- **Server:** `AnalysisSession.FlowIndex()` — `??=` memo, same pattern as T3.4's ConfigBindings;
  `GetFlowIndex` rides `WrapT` so it lands in the MCP feed with `origin=ui` like every UI call.
- **App:** `AtlasStore.start()` = ONE `getFlowIndex` call (abortable, supersede-safe); worker queue,
  pause/park machinery and the getNode enrichment effect deleted; `pause()/resume()` kept as no-ops
  for callers. Hub degrees seed from the response. `atlas.store.spec.ts` (4 specs: one-call mapping,
  degree seeding, failure state, supersede).
- **Drive:** ui-audit-drive assertion **M-rpc-budget** — counts `POST /devcontext.v1.DevContextService/*`
  network calls: fresh page load < 20, then single-key SPA navigations (atlas/explore/home) ≤ 15 each.

## Deliberate behavior delta (documented, not silent)

The client's `BOUNDARY_SEAMS` compared lowercased seam names `'consumes'/'raises'/'handler'` against
the wire's `'consume'/'raise'/'handle'` — **only `'send'` ever matched**, so boundary crossings (and
flow scores, `nodes × (1+boundary)`) undercounted every non-send hop. The server counts the real
`SeamKind` set (Send/Handle/Consume/Raise/CrossService): deep cross-service flows now rank as the
plan intended. Top-Flows ordering can change on messaging-heavy repos — that is the bug fix.
