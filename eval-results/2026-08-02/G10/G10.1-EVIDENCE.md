### 1 — START HERE's depth filter ran in front of the rule it was under · CORRECTED

`rankFlows(flows.filter((f) => f.nodeCount >= 4))[0] ?? rankFlows(flows)[0]`. The filter runs
**before** D-E's band rule, so it can delete the entire request-shaped band and then rank what is
left. The 4 is the last live number from the same starved-graph calibration E-2 uncovered — the
`>=3-hop gate` the retired checkout special case leaned on — and it inverts the same way, reached
through depth instead of a title.

**Proved red before the fix** (`flow-ranking-RED.txt`): the new spec fails on the old body with

```
AssertionError: expected 'CheckoutViewModel.CheckoutAsync' to be 'POST /api/orders/draft'
```

which is the E-2 regression **verbatim**, produced without any checkout title in play. Green after:
`flow-ranking-GREEN.txt`, 8/8.

The filter is also redundant — `compareFlows` already prefers the deeper flow *within* a band and
the caller has already dropped 1-node flows — so depth still decides every comparison it should.
Landed as `pickHeroFlow` in `core/flow-ranking.ts` (which shipped with no spec at all) @ `06fcae5`.

Relevance on current data: the entry-kind mix is what the rule arbitrates, and top-band and deepest
are different populations on every multi-kind pole — eShop 46 request-shaped / 42 UiEntry / 21
internal, DntSite 70 / 0 / 24, wolverine 22 / 0 / 29.

### 2 — the dead-code claim's coverage floor is unreachable · JUSTIFIED + BUG

`graph.orphans` clears **none** of the 11 poles, so it has emitted nothing on any of them. The
clause that shuts it is `verifiedRatio < 0.5`: the Semantic share column above runs 0.010 … 0.259 on
every application, and the only poles above 0.4 are libraries, which line 35 already excludes, or
sit under the 30-call floor. Counting `Join` as verified as well (finding 5) lifts eShop 0.057 →
0.21 and still clears nothing.

The other two clauses **do** still discriminate and were left alone: `wiredRatio` spans 0.294
(wolverine) → 0.933 (self); `calls.Count` spans 26 (MediatR) → 4023 (DntSite).

Deliberately **not** recalibrated. This is the one claim in the product that gets live code deleted
when it is wrong (the audit's podcasts round: 3/5 orphans FALSE), and lowering a floor to make a
destructive claim start firing is not a threshold correction — it is a product decision with no
evidence behind it. The measurement is now in the comment; the keep-or-retire call is a filed bug.

### 3 — L3.4's sparse broadening never fires · JUSTIFIED + BUG

`sparseGraph=false` and `hubScopeNodes=0` on **all 11 poles**, including the four this method exists
for (Dapper, Serilog, MahApps.Metro, MediatR — 0–1 entries, edge/node ratio 0.30–0.45, so they pass
the `entries>=5 && ratio>=0.1` gate and *should* come out sparse). Its one UI surface,
`identity-strip.ts`'s hub-scope line, has therefore never rendered on a measured pole.

The gate at line 199 is not what shuts it, and `k < 5` should not either: on Dapper the Calls edges
alone span 32 distinct types, which puts `k` at 16. Something between the two eats it. Not chased
here on purpose — making it fire adds up to 500 synthesised Calls edges to every library-shaped
repo, which is a product change with a matrix behind it, not a threshold correction.

### 4 — the deep-spine ratio is saturated · JUSTIFIED + BUG

1.000 on 5 of 11 poles, 0.982 on eShop, 0.961 on wolverine. A `>=2`-step spine means "the entry
reaches one thing" — a real distinction when entries routinely resolved to nothing, and now true of
very nearly every entry that exists. `ReportRenderer` prints it as a coverage row
(`Deep spine (>=2) | 107/109 (98%)`) that reads the same on every repo. The bar is **not** raised
here: where a useful one sits is a question about the step distribution, which no surface exposes,
and inventing a 3 or a 4 by eye is re-calibrating a shipped metric to look interesting.

### 5 — "1 of 1 entries have no resolved target", as a WARNING · CORRECTED

`unwired / s.entries > 0.2` was read as a rate on any repo with at least one entry. Measured:
GitVersion and MediatR each have exactly **one** entry, unwired, so both raised a warning that says
100% of one. Now gated on `s.entries >= 5` — already the engine's own bar for "enough entries to
judge a graph by" (`GraphBuilder.Seams`). Effect across the 11 poles, exactly two rows move:
GitVersion and MediatR drop warning → notable. CleanArchitecture 2/7, DntSite 24/94, eShop 45/109,
wolverine 36/51 stay warnings; podcasts 3/24 and self 2/30 stay notable.

### 6, 7, 8 — not calibrated thresholds

- **Seats (`resolveCount >= 2`)**: only sizes the candidate pool. `InterestingPoints` orders by
  `Score` (degree) *before* `Take(20)`, so a seat with 26 implementations cannot be pushed out by
  one with 2. Measured seat counts 0–7 on ten poles, 34 on wolverine — ranked, not truncated by
  arrival order. (This is the opposite of G1.4's find, where the filter ran *below* the truncation;
  checked precisely because of it.)
- **Wiring hubs**: `Take(5)` then `Where(Degree >= 5)` — output is bounded before the bar applies.
- **Confidence tiers 0.8/0.5**: read detector confidence, not graph richness, and deliberately
  mirror `MapRenderer.AppendStyle`.
