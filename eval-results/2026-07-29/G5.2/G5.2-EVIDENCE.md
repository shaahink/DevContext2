## 1. What was actually wrong, and where the brief was wrong about it

G5.1 §3 named two defects correctly. Its §5 then prescribed the **wrong locus** for the first one, and
its own §3 contains the disproof.

> §5: *"It is the existing `HopThroughProperty` hop, applied to the one case its own comment does not
> argue against."*

`HopThroughProperty` reads `SymbolTable._propertyTypesByType`, built from `TypeDiscovery.Properties`.
GitVersion's collaborators are **fields**:

```csharp
// eval-repos/GitVersion/new-cli/GitVersion.Output/OutputCommand.cs
public class OutputCommand(ILogger<OutputCommand> logger, IService service) : ICommand<OutputSettings>
{
    private readonly IService service = service.NotNull();          // a FIELD
    public Task<int> InvokeAsync(OutputSettings settings, CancellationToken ct = default)
    {
        var value = this.service.Call();                            // the call that never bound
```

`TypeDiscovery` has no `Fields` member at all (`src/DevContext.Core/Models/TypeDiscovery.cs`), so the
prescribed route needs a whole new field-type map plumbed from the extractors through `SymbolTable`.

G5.1's own fixture already showed where the defect lives. Case **A** `widget.Do()` binds; case **B**
`this.widget.Do()` binds nothing. Same field, same method, same line. The difference is entirely
upstream of the binder — in `BodyFactExtractor`, which is where **`BuildTypeScope` already maps every
field, property and primary-constructor parameter to its declared type**. It is the exact map case A
resolves through. The only defect is that `RootIdentifier` walks a member-access chain down to the
`this` **token**, and `"this"` is not a key in that map.

So the fix is a **normalisation, not a new inference**: one call, one fact, whichever way it is spelled.

## 2. The two edits

### Fix 1 — `src/DevContext.Core/Graph2/BodyFactExtractor.cs` (new `SplitReceiver`)

A receiver chain rooted at `this` reports the member declared directly on `this`:

| written | root (`ReceiverText`) | chain segment (`ReceiverMember`) |
|---|---|---|
| `x.M()` | `x` | — |
| `this.x.M()` | `x` | — *(same fact as the line above)* |
| `x.y.M()` | `x` | `y` |
| `this.x.y.M()` | `x` | `y` *(same fact as the line above)* |
| `this.M()` | `this` | — *(unchanged: the binder's self-call arm needs it)* |
| `this.Make().Do()` | `this` | — *(unchanged: the segment is a call result, not a declared member)* |

Two structural conditions, no name list: the walk must reach `ThisExpressionSyntax` **through member
accesses only**, and there must be a segment to unwrap. Both guards have a test (§4).

### Fix 2 — `src/DevContext.Core/Graph/EntryPoints/CliCommandEntryPointBuilder.cs`

The entry joined the command **type**, and `ResolveEntryTarget`'s Type arm reads only `Sends` edges,
while a verb's call edges hang off its execute **member**. So all five verbs had a `Calls[Join]` edge,
an existing target Type node, and no target — and `ResolveOwningTypeFallback` then blanked the type as
self-evident, because the entry title already says `output (OutputCommand)`.

The builder now joins the execute member, identified **by shape**: the one method the command type
declares whose parameter types carry the detected settings type, where that settings type resolves to a
known declared FQN. That last condition is also what rejects `CliCommandDetection`'s `"object"` sentinel
for a command with no settings generic. 0 or >1 matches → the type join stands, unchanged.

`CliCommandDetection.ExecuteMethod` was **not** used: it is a method-name list
(`"Execute"/"ExecuteAsync"/"Invoke"/"InvokeAsync"`, `CliCommandExtractor.cs:116`) defaulting to
`"Execute"`. The shape rule survives a rename of `InvokeAsync`; the name list does not.

**Ordering trap, recorded because it silently defeats the obvious implementation:** entry builders run
at `GraphBuilder.cs:67`, `AddCallEdges` at `:90`. `g.HasNode(memberId)` is therefore **always false** at
entry-build time. The builder must *create* the member node — which is exactly what
`HttpEntryPointBuilder` already does for a controller action.

### 5b. A new gate, and it was watched going red

`entryTargets.maxDiInterfacePct` is a **quality ratio over the entries that resolved**, so a pole where
*nothing* resolves scores a perfect 0% — GitVersion sat at 0-of-5-wired and passed this check for
months. That is the blind spot this checkpoint just walked out of, so it now has a floor:

- `eval/graph-truth.ps1` — new `entryTargets.minWithTarget`, default **0**, so every other pole is
  bit-for-bit unchanged. Ratchet only: raise it when a pole improves, never lower it to get green.
- `eval/expectations/graph-truth/gitversion.json` — `minWithTarget: 4`, with the per-verb source
  citation in the `note` field (R-T7).

**Watched failing on demand** (`canary-minwithtarget.ps1`, output in `canary-OUTPUT.txt`): raise the
floor to 6, and

```
entry-target=FAIL : 4 of 5 entries reach a target, expected at least 6 (handler join lost -- D-3)
  metrics: entries=5 withTarget=4 minWithTarget=6
```

then restored to 4 and re-run → `entry-target=PASS`. A driver check nobody has seen go red is vacuous.
