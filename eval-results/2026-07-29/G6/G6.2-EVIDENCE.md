# G6.2 — Raw metadata arity never reaches the UI

**Checkpoint:** G6.2 (stage G6, R3 D-4 arity half) · **Session** #21, 2026-07-29 · branch `feat/graph-v2`

> **Claim:** no rendered surface — CLI markdown, the shared Core renderers, or the desktop app's DOM —
> shows a raw metadata arity marker, while canonical node **ids** keep theirs.

---

## 1. Where the leak was — measured before touching anything

The checkpoint title names one symptom (``Logging.ILogger`1`` in Atlas's hub radar, which G6.1 already
removed). The first job was finding out whether that was the *only* one. It was not, and it was not
where the strand doc implied.

### 1a. The engine is clean — `arity-sweep-before.txt`

`eval-results/2026-07-29/G6/arity-sweep.ps1`, five poles (eShop · FluentValidation · AutoMapper ·
MediatR · CleanArchitecture), every surface the engine renders:

| measurement | result |
|---|---|
| `graphdump` node **titles** carrying arity | **0** |
| `query map/entrypoints/stats --format md` | **0** |
| the `analyze` markdown context pack | **0** |
| `graphdump` node **ids** carrying arity *(control — must be non-zero)* | **248** |

Measured title algebra, one sample per node kind on eShop:

```
Type    id=Type:Microsoft.Extensions.Logging.ILogger`1        title="ILogger"
Member  id=Member:eShop.…ObservableCollectionEx`1::Remove     title="ObservableCollectionEx.Remove"
Service id=Service:Basket.API                                 title="Basket.API"
```

`SymbolCanon`'s doc comment claims exactly this, and per the program's standing rule it was measured
rather than believed. **It is true.**

### 1b. The leak is entirely client-side, and it is one defect class with eight instances

The app labels a node from its **raw canonical id** whenever a title is missing or simply not threaded,
and every site had invented its own rule:

| # | site | shape |
|---|---|---|
| 1 | `workbench-page.ts:426` `shortNodeTitle` | `split(/[./:]/).slice(-2).join('.')` → trail crumbs |
| 2 | `stage.ts:218` | `trace.nodeDetail()?.title ?? nodeId` → canvas centre |
| 3 | `stage.ts:227` | `{{ nodeId }}` → neighbours header |
| 4 | `stage.ts:239` | `edge.otherTitle \|\| edge.to` |
| 5 | `graph-canvas.ts:384` | `e.otherTitle \|\| other` |
| 6·7 | `node-card.ts:69,76` | `e.otherTitle \|\| e.from/e.to` |
| 8 | `node-peek.ts:31` | `{{ id }}` → peek header |

Site 1 is **the same function G6.1 deleted from the hub radar**, alive in a second file:
`Type:Microsoft.Extensions.Logging.ILogger`1` → ``Logging.ILogger`1`` — the literal D-4 string — and
`Service:WebApp` → `Service.WebApp`, the node **kind** posing as a namespace.

Sites 1, 2, 3 and 8 are reachable today. Sites 4–7 are defensive fallbacks that were measured **never
to fire**: `dangling-edge-probe.txt` shows **0 edge endpoints without a node** across six poles, so
`GraphQuery.NeighborsView`'s own `?? otherId.Key` fallback never fires either. They were fixed anyway —
eight rules for one job *is* the defect.

### 1c. A client-side derivation cannot be made faithful — `label-mirror-fidelity.txt`

Before replacing eight rules with one derivation, the derivation was tested against the engine's own
titles on six poles. It does **not** reproduce them, because the engine's titles are not one algebra:

```
Member  343 owner-qualified ("CatalogApi.GetAllItemsV1")  /  627 bare ("MapCore", "Send", "Validate")
```

**This changed the design.** The fix is not "teach the client a better derivation" — it is *never
derive when a title exists*. The two engine-side vocabularies this uncovered are filed as tracked
bugs (#17 member titles, #18 Type nodes built from lambda text) rather than scope-crept into G6.2.

## 2. What landed

**One rule, one place.** `src/DevContext.App/src/app/core/format.ts` gains `nodeIdLabel(nodeId)` —
the only sanctioned way an id reaches the screen. It drops the **kind** prefix (a kind is not part of
a name) and spells generic arity the way C# spells an unbound generic (`ILogger<>`, `IDictionary<,>`),
never the metadata marker. Nothing else is removed: shortening is what made a Service look like a
Type. Its doc comment states, in the code, that it is a **fallback** and must never be preferred to a
title the graph gave you.

**Where a title exists, it is now threaded.** `TraceStore.titleFor(nodeId)` reads the graph's own
title out of the loaded trace tree (a walk, no RPC), and the trail crumb uses it. `shortNodeTitle`
is deleted.

**The rule is a gate.** `scripts/loom-guards.ps1` rule 8 bans three shapes across the app's 112
TypeScript sources: node-id surgery, a bare id interpolated into a template, and a title falling back
to a bare id. One allowance, with its reason stated: `atlas.store.ts`'s `normalizeEventName`, which is
a **matcher** (it lowercases and strips every non-alphanumeric, so a marker cannot survive it), not a
label.

## 3. Verification

### 3a. Red-then-green on the guard — `g62-red-proof.txt`

`git stash push` the seven app files (rule 8 itself stays in place), run the guard, restore, run again:

```
LEG 1 — PRE-FIX SOURCES:   rule-8 violations: 8      <- all eight sites, by file and line
LEG 2 — FIXED SOURCES:     rule-8 violations: 0
                           PASSED: 0 truth failures
                           == PASSED: no banned patterns ==
VERDICT: RED THEN GREEN
```

The guard was watched go red before it was trusted. Its **first two drafts were wrong and reported
zero** — once because `Get-ChildItem -Include` let directories through and `Select-String` killed the
script under `$ErrorActionPreference = 'Stop'` (a guard that dies reports no violations), once because
the `.ps1` would not parse. Both are in the ledger.

### 3b. The live app — `g62-arity-dom-eShop.txt` · `g62-arity-dom-FluentValidation.txt`

`src/DevContext.App/scripts/g62-arity-dom.mts` walks the real app and greps **every text node and
every `title=` attribute** (the tooltip is UI too, and two leaks lived there) across `/`, `/explore`,
`/atlas`, `/insights`, `/context`, then deliberately exercises the three surfaces whose only label
source is an id.

- **eShop** (37 arity-bearing ids): **0 text hits, 0 title hits** on every route, after clicking 8
  stage nodes, and with the peek card open.
  - **Site 1 (trail crumbs) positively exercised:** the crumbs now read the graph's own titles —
    `CatalogApi.UpdateItemV1 | ProductPriceChangedIntegrationEvent | CatalogServices |
    CatalogContext | ICatalogAI | CatalogAI` — instead of id carvings.
  - **Site 8 (peek header) positively exercised:** the card reads
    `PUT /api/catalog/items` (header, from `nodeIdLabel` — the `EntryPoint:` kind prefix correctly
    dropped) then the same as the title below it.
- **FluentValidation** (128 arity-bearing ids — the densest pole): **0 / 0**. Being a library it
  draws no trace, so its interactive surfaces do not render there; eShop is the pole that covers them.

**Stated limitation, not glossed:** the probe did **not** reach the stage's *node-altitude* branch
(sites 2, 3, 4 — `@case ('node')`); its `[neighbours] first rows` came back empty and the header it
read was the project topology line, so those three lines are **not** covered by the live measurement.
They are covered by §3a — the red leg names `stage.ts:218`, `:227` and `:239` individually — and by
`format.spec.ts`, which pins the function all three now call. Reaching that branch needs a specific
altitude+selection state the probe does not yet drive; worth adding before the next UI claim that
depends on it.

### 3c. Identity not weakened — `arity-sweep-after.txt`

Re-run of §1a after the change: titles **0**, rendered text **0**, and the control — node **ids**
carrying arity — still **248**. G6.2 makes no engine change, so this is a check that nothing drifted,
and that the fix is not "strip arity everywhere".
