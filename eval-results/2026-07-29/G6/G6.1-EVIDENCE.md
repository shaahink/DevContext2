# G6.1 — one vocabulary for "service" on Atlas (R3 D-4)

**Checkpoint:** *One vocabulary for "service" on Atlas — the canvas, the per-service breakdown and
Hub radar stop disagreeing about what a service is.*
**Date:** 2026-07-29 · session #20 · branch `feat/graph-v2`

---

## 0. The definition adopted, stated once

> **A service is a project the engine judged RUNNABLE and PRODUCTION** —
> `ServiceBoundaryInference.RunnableProjects`, the same list `GraphBuilder.AddServiceNodes` turns into
> `NodeKind.Service` nodes. Every Atlas surface that says "service" means exactly that set.

It already existed and the canvas already obeyed it. The other two surfaces re-derived their own.
The definition is now written into `ArchitectureStyleDetector.DetectPerServiceStyles`'s doc comment,
`NODE_KIND_LABELS` in `models/view-models.ts`, and `DECISIONS.md` §D-4.

`before-atlas-eShop.txt` (+ `.png`), produced by `src/DevContext.App/scripts/g6-atlas-vocabulary.mts`.
The probe reads the **drawn cytoscape nodes** through the container's `_cyreg` registry — canvas

             TRAY: "in no relationship · 2  ClientApp · HybridApp"
[2] BREAKDOWN 12 flat cards

[CAPTION] Architecture: "19 projects · 36 dependency edges · 23 transport links"   (never says "service")

### One correction to DECISIONS.md's premise

D-H said "the canvas **excludes** ClientApp/HybridApp, the per-service breakdown lists them as
services". Measured, the two lists are **set-identical** — canvas 9 boxes + 1 frame + 2 trayed = 12 =
the 12 cards. The canvas does not exclude them, it **trays** them. So D-4's "service" half is a
rendering/vocabulary defect: one set, three stories, and no surface reconciling its count with the
others.

### The hub-radar find is bigger than "mixes services with types"

**Seven of the ten rows ARE Service nodes**, and the same node kind rendered two different ways.
`atlas.store.ts`'s `shortTitle()` split the node id on `[./:]` and joined the last two segments:

| node id | rendered | what the reader sees |
|---|---|---|
| `Service:Webhooks.API` | `Webhooks.API` | kind token dropped — looks like a type |
| `Service:WebApp` | `Service.WebApp` | kind token KEPT — reads like a namespace |
| `Type:…Logging.ILogger\`1` | ``Logging.ILogger`1`` | a type, with raw metadata arity |

One string-surgery line produced all three symptoms.

### And a latent engine divergence the coincidence was hiding

Two independent membership predicates existed:

| surface | predicate |
|---|---|
| canvas | `RunnableProjects` = `IsProduction(p) && IsRunnableService(p)` |
| breakdown | `IsRunnableService` **+ its own skip list**: holder · build-tooling · benchmark · sample path · **`IsInfrastructureProject(NAME)`** (contains `.servicedefaults`/`.apphost`/`shared`/`common`/`.eventbus`) · `IsInTestProject(FILE PATH)` rather than `IsTestProject(PROJECT)` |

They agreed on eShop by luck. `red-proof-RAW.log` shows the new invariant test failing on the
pre-G6.1 code:

```
Expected: ["Shop.Api", "Shop.Common", "Shop.EventBus", "Shop.SharedHost", "Shop.Worker"]
Actual:   ["Shop.Api", "Shop.Worker"]
```

Three runnable production projects the canvas draws and the breakdown silently dropped, purely
because of their NAME.

## 2. What landed

### Engine — one membership predicate
`src/DevContext.Core/Extractors/Generic/ArchitectureStyleDetector.cs` — `DetectPerServiceStyles`
iterates `ServiceBoundaryInference.RunnableProjects(scope, model.SamplesAreTheProduct)` and answers
only *what style is each of those*. Its second skip list is gone; the private `IsRunnableService`
shim is gone; the Aspire AppHost keeps its orchestrator **style**, not a membership exemption.

### Engine — the flag the predicate reads is now decided before it is read
`src/DevContext.Core/Pipeline/DiscoveryPipeline.cs` — **found by the real-repo sweep, and it is a
fourth instance of D-4's defect class.** `model.SamplesAreTheProduct` was assigned only at
graph-assembly time (lines 191 / 262), i.e. **after** line 128 where the rollup runs, so the rollup
has always read the default `false` on every repo ever analysed. On a samples-only repo the canvas
drew services the breakdown said did not exist. Measured on `aspire-samples`: **2 Service nodes, 0
breakdown rows**. Proven pre-existing, not a regression — `aspire-before-after.log` stashes the
detector change, rebuilds the CLI `--no-incremental`, and gets BEFORE 0 / AFTER 0.

### Engine → app — the hub radar's rows are the graph's facts
`FlowIndexBuilder.HubDegree` gains `Title`, `Kind`, `FlowCount`, `Project`; `HubDegreeRow` in the
proto gains the same four; `ProtoMapper` carries them. `AtlasStore.hubs` is now the server's list
verbatim — the client's duplicate top-10 ranking (a different tie-break from the server's, so the
two could disagree and a row could render with no degree) and `shortTitle()` are both deleted.

### App — the picture and the list reconcile
`classifyServiceRoles` / `orchestratorMembership` move out of `graph-canvas.ts` into
`ui/graph-canvas/semantics.ts`, so the canvas and the breakdown read ONE role rule. The Architecture
caption leads with the service count and accounts for every member; the breakdown states the same
count and each card names its canvas state; hub rows carry a kind chip (`NODE_KIND_LABELS`).
