## 2. Root cause — a POPULATION change hidden inside a PREDICATE change

G6.1 (`2fdd4cf`) replaced the per-service rollup's home-grown skip list with the one membership
predicate. That was right. But the two lines are not equivalent in the way the commit assumed:

```csharp
// before G6.1
foreach (var proj in model.Projects)              // EVERY csproj discovery found
// after G6.1
foreach (var proj in RunnableProjects(scope, …))  // scope = SolutionScope.FromModel(model)
```

`SolutionScope.FromModel` keeps **only the csprojs listed in the resolved `.sln`** when one resolves.
So the change swapped the *predicate* and, silently, the *population*.

dotnet-podcasts declares **five solutions**. The analysis picks `NetPodcast.sln` (13 projects) and
says so on its own front line:

```
MAP    NetPodcast     (13 projects)
SCOPE  analyzed NetPodcast.sln — 1 of 5 solutions in this repo; analyze another by naming
       its solution — style/topology are local to this slice, not the whole system
```

The two MAUI clients live in sibling solutions:

| csproj | in `NetPodcast.sln`? | in `model.Projects`? |
|---|---|---|
| `src/Mobile/Microsoft.NetConf2021.Maui.csproj` | no | yes |
| `src/MobileBlazor/mauiapp/NetPodsMauiBlazor.csproj` | no | yes |

The engine parses those csprojs — that is where `MauiEvidence.HasMauiTfm` reads the mobile TFM triple
from — but the analysed solution does not list them. The per-service rollup was the **only** surface
that had ever named them (`MAUI App [.NET MAUI]` ×2, the exact mechanism the expectation's note has
described since Prism D1.2b). It went silent, and with it the repo's MAUI truth.

### Why G6.1's own gate could not see it

G6.1 proved its claim with a real-repo invariant on five poles: *breakdown rows == the graph's Service
nodes* → 5/5 SAME SET. That invariant is still true. It is also **blind by construction**: after the
edit both sides read the same scope-narrowed list, so a shrink that moves both surfaces together
measures as agreement. podcasts read `5 = 5` before and after — what changed is that the 5 used to
be 7.

> **An equality invariant between two surfaces cannot see a shared shrink.** Pair it with an absolute
> count or a content ratchet. `eval/expectations/dotnet-podcasts.json` was that ratchet.

## 3. The fix — name the boundary, do not re-admit non-services

Two fixes were considered and rejected in the ledger before any edit:

- **Revert the population** (iterate `model.Projects` again). Green gate, dead decision: the breakdown
  would again list projects the canvas does not draw, indistinguishable from the ones it does. That is
  exactly the defect D-4 exists to kill.
- **Widen the scope / draw the MAUI apps.** The map declares its boundary and obeys it everywhere —
  13 projects in the header, 13 topology rows, 13 in the `.sln`. Widening contradicts `SolutionScope`'s
  stated design ("one system per scope; multi-solution later is a loop, not a refactor") and moves
  every multi-solution pole at once.

**Taken instead:** `SolutionScopeNote`'s own doc already states the rule this completes — *"The pick
itself is legitimate; hiding it is not."* The note said which solution and how many exist. It never
said that **runnable apps** were among the ones you are not seeing.

So: a second, differently-named population, from the same style detector, disjoint by construction.

| list | population | who draws it |
|---|---|---|
| `service_styles` | `RunnableProjects(scope)` | the Atlas canvas |
| `outside_scope_apps` | runnable production projects **not in the analysed solution** | nobody — named, not drawn |

Nothing calls the second list services. D-4's definition of "service" is untouched.

### What landed

- `ServiceBoundaryInference.RunnableProjectsOutsideScope` — same production+runnable predicate, the
  complement population. The classifier reads the **whole** project set (build-tooling exclusion is
  transitive, so handing it only the leftovers would classify a Cake bootstrapper as production).
- `ArchitectureStyleDetector` — the style ladder became `DetectStyles(model, scope, population)`;
  `DetectPerServiceStyles` and the new `DetectOutsideScopeApps` are its two callers. Membership is
  still never decided there.
- `DiscoveryModel.OutsideScopeApps` → `MapModel` → `MapRenderer` (under `SCOPE`) →
  `MapResponse.outside_scope_apps` (proto 19) → `ProtoMapper` → MCP `map` → the Atlas page.
- Snapshot persistence carries it, so a rehydrated analysis says the same thing as a cold one.

## 4. The ratchet

`tests/DevContext.Core.Tests/ServiceVocabularyTests.cs` gains three tests over a dotnet-podcasts
miniature (one resolved solution holding the web service; a package-free MAUI client, its library and
its test host discovered on disk but listed elsewhere):

1. `A_runnable_app_outside_the_analysed_solution_is_named_but_never_called_a_service` — both halves:
   the service list is unchanged **and** the app is named with style `MAUI App`.
2. `The_two_populations_never_overlap_and_share_one_production_rule` — disjoint, and the out-of-scope
   test host is in neither list.
3. `A_repo_whose_solution_holds_everything_reports_no_outside_apps` — no section that says "nothing".

**On the red-proof, stated plainly:** the watched red for this checkpoint is the **eval gate**, not a
synthetic unit red — Conductor's battery, then reproduced locally in 6s at `1b1b119` before any edit
(§1). The unit tests above could not have gone red on the old code in the useful sense: two of them
call an API that did not exist, so the "red" would have been a compile error. They are the ratchet
that keeps the eval green, not a second proof of the defect.

## 5b. The live page, not the markdown

`src/DevContext.App/scripts/g63-outside-scope-dom.mts` drives the real app (analyse
dotnet-podcasts → `/atlas`) and reads the DOM. It tests **two** things, because a text grep for
"MAUI" would also pass if the fix had simply re-listed the apps as services — the exact defect D-4
closed. Artifact `g63-outside-scope-dom.txt` (+ `.png`):

```
[1] OUTSIDE-SCOPE BLOCK
    NOT ANALYZED — 2 RUNNABLE APPS OUTSIDE THIS SOLUTION
    Discovered on disk, listed in another solution. Not services — switch solutions to analyze them.
    Microsoft.NetConf2021.Maui / MAUI App / .NET MAUI
    NetPodsMauiBlazor        / MAUI App / .NET MAUI

[2] SERVICE CARD TEXT — Podcast.Server · ListenTogether.Hub · Podcast.API ·
    Podcast.Ingestion.Worker · Podcast.Updater.Worker   (5 cards, each naming its canvas state)

[3] VERDICT — of the names in [1], 0 also appear on a service card.  PASS
```

Stated rather than hidden: the probe's name extraction in [3] is a loose heuristic (it counts
`MAUI` and `.NET` as names, so "6" over-counts 2 apps). The load-bearing number is the second one —
**0 leaked into the service cards** — and the raw block and card text are printed so a reader can
check the claim rather than trust the counter.
