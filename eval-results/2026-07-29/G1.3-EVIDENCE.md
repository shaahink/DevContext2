## Item 3 — seam glyphs

### [audit] ref re-verified, and it was understated

`DevContextTools.cs:782-792` (now :888) matched `"Sends"` / `"Raises"` / `"Consumes"` / `"Handles"`.
Core's `SeamKind` (`src/DevContext.Core/Graph/TraceBuilder.cs:8`) is
`{Entry, Call, Send, Handle, Raise, Consume, Data, Resolve, Pipeline, CrossService}` and the server
sends `Seam = step.Seam.ToString()` (`ProtoMapper.cs:654`) — so those four plurals cannot occur.
The audit called it "plurals". It is plurals **and three missing arms**: `Data`, `Resolve` and
`Pipeline` had no case at all. **Seven of ten seam kinds rendered the mute `·`.**

### BEFORE — `trace(eShop, "POST /api/orders/", format:"compact")`

`mcp-r4-g13-before/glyphs-trace-eshop.json`:

```
▼ EntryPoint: POST /api/orders/
  → Member: OrdersApi.CreateOrderAsync
    · Type: IdentifiedCommand              <-- the MediatR dispatch
      · Type: IdentifiedCommandHandler     <-- the handler that receives it
        ⇛ Service: Basket.API ...
```

`glyphs used: ▼ → · ⇛ · fallback rows: 3`. The two mute rows are the Send and the Handle at the top
of the flow this program cites more than any other. An agent reading that cannot tell a dispatch
from a handler from a database write — all three were `·`.

### AFTER — same call, same repo (`mcp-r4-g13-after/glyphs-trace-eshop.json`)

```
▼ EntryPoint: POST /api/orders/                    src/Ordering.API/Apis/OrdersApi.cs:17
  → Member: OrdersApi.CreateOrderAsync             …
    ⇒ Type: IdentifiedCommand                      src/Ordering.API/Apis/OrdersApi.cs:155
```

`legend: ▼ entry · → call · ⇒ send · ◉ handler · ◇ di · ⇛ cross-service` · **fallback rows: 0**.

The structured form of the same trace (`glyphs-trace-eshop-tree.json`) carries six distinct seam
kinds — `Call CrossService Entry Handle Resolve Send` — so **three of the six** this one flow
produces (`Send`, `Handle`, `Resolve`) were mute before, and `Resolve` is one of the three that had
no arm at all.

**The driver's own check passed on the before-state** and had to be tightened: "at least one
non-Call glyph renders" was satisfied by `⇛` alone — the vacuous-pass shape again, one checkpoint
after G1.2 paid for it. It now asserts **zero** mute rows, pulls the same trace in structured form
to print the seam vocabulary the repo actually produced, and requires the legend.

### What changed

- `DevContextTools.SeamGlyph` — one table keyed on the wire spelling, all ten kinds, distinct
  glyphs. An unmapped seam now renders `[Name]` instead of disappearing into a dot.
- `DevContextTools.SeamLegend` — compact `trace`/`flow` responses carry a key for the glyphs they
  actually used. Ten symbols with no legend are not readable by the agent on the other end.
  Label words are `TraceRenderer.SeamLabel`'s, so the CLI tree and the MCP text say the same word
  for the same edge. **No proto change** — it rides the existing anonymous JSON, so the S9 contract
  sweep needs no allow-list entry.
- **Core had the same hole**: `TraceRenderer.SeamLabel` had no arm for `CrossService`, so every
  cross-service hop in a CLI trace printed a bare `?`. Fixed with it. No golden or eval expectation
  contains a seam label, so nothing needed regenerating.

## Item 4 — handle-less calls retarget across repos

### Root cause (two lines, in the server)

`AnalysisSessionManager.Get()` bumps `LastAccess` on **every** access (`Sessions/AnalysisSessionManager.cs:60`)
and `ListSessions()` orders by `LastAccess` descending (`:76`), while `DevContextTools.ResolveHandle`
took `list.Sessions[0]` (`DevContextTools.cs:36-41`). So a handle-less MCP call resolved to
"whatever repo **anyone** touched most recently" — the desktop app opening repo A silently
retargeted an agent's next call about repo B.

### BEFORE / AFTER — `drive-r4.js retarget`

analyze(TodoApi)=A, analyze(FluentValidation)=B, an explicit-handle `stats(A)` (what another client
does), then a handle-less `overview()`:

| | verdict |
|---|---|
| BEFORE (`mcp-r4-g13-before/retarget.txt`) | **FAIL** — went to `bb4f725a` (A), expected B `f9370847` |
| AFTER (`mcp-r4-g13-after/retarget.txt`) | **PASS** — went to `e77ddb1c` (B) |

### What changed

`DevContextTools` remembers the handle **this process analyzed** and prefers it, if the server still
has it. With nothing of our own: one open session is unambiguous and still resolves (attaching to a
session the desktop app made is a real workflow); two or more, and the tools **name the open
sessions and ask for a handle** rather than guessing. `close_session` gives the memory up.
Pinned by `McpHandleScopeTests` (5 tests). `docs/product/mcp-reference.md` updated in the same commit.

## Item 5 — RpcException past the error envelope

### [audit] ref re-verified, and the real set is wider

The audit named five tools. A sweep of all 24 found **eight** unguarded: the idiom in this file is
`try { handle = ResolveHandle(handle); } catch { return FromRpc(…) }` and it is easy to guard the
handle lookup and leave the actual RPC bare. `Analyze`, `TopFlows` and `InterestingPoints` were the
three the audit missed; `Status` was worse than listed (its `ResolveHandle` was not wrapped at all,
and its body caught only `NotFound`).

### BEFORE / AFTER — `drive-r4.js envelope` (every tool called with a bogus handle)

| tool | BEFORE | AFTER |
|---|---|---|
| `status` | PASS | PASS |
| `map` | PASS | PASS |
| `entrypoints` | **FAIL** — MCP `isError`, raw exception | PASS |
| `insights` | **FAIL** — MCP `isError` | PASS |
| `top_flows` | **FAIL** — MCP `isError` | PASS |
| `interesting_points` | **FAIL** — MCP `isError` | PASS |
| `close_session` | **FAIL** — `{"closed":false}` and nothing else | PASS |

3/7 → **7/7**. Artifacts: `mcp-r4-g13-{before,after}/envelope.txt` + `envelope-bogus-handle.json`.

`close_session` was not an exception leak but a silent lie: closing a handle that was never open
answered `{"closed":false}`, indistinguishable from a successful no-op. It now says
`found:false` with a note, and stays idempotent.

### The fix is a test, not eight more try blocks

Eight of twenty-four drifted because the guard is hand-written per method.
`McpErrorEnvelopeTests.Every_tool_answers_an_envelope_when_the_server_fails` walks **every**
`[McpServerTool]` method with a `CallInvoker` that fails every RPC and asserts each returns a JSON
envelope naming the error — with a `Count >= 24` precondition so it cannot pass vacuously (G1.2's
lesson). A new tool that forgets the guard fails the day it lands.

## Collateral: the MCP QA gate red (open bug #1)

The G1.3 fast suite went red on `McpQaGateTests` with a **new** signature — not bug #1's documented
"0/12 with `? nodes`", but no `QA Score:` line at all. Re-running the harness directly on the same
binaries: **12/12, exit 0** (`g1.3-mcpqa-repro.txt`). Same race, second face.

**My change exposed it.** `eval/mcp-qa/run.js` had a last-resort branch calling `status(handle: "")`
— an empty handle, i.e. "server, pick a session for me". That is exactly the ambiguous global
default this checkpoint removes: it used to answer `Sessions[0]` and the harness sailed on. The
harness was leaning on the defect.

Fixed at the root, in the harness, per bug #1's own filed text — nothing relaxed:

1. `analyze` gets its own 600s budget instead of the shared 45s. A cold analyse always exceeded 45s,
   so the call **always** rejected and the code below invented a result.
2. The poll accepted a session whose `status` was `"ready"` — a field `list_sessions` does not
   return, so it could never match, and 240 iterations were spent proving it. It now accepts a
   session only when `nodes > 0`, i.e. one that has actually produced a graph.
3. The `status(handle: "")` branch is deleted. A harness must not grade a repo it did not name.
4. The artifact's transport line was a hard-coded `[x] analyze returned via polling workaround`,
   printed on every report whether or not any polling happened. It now reports what occurred.

Verified: the fixed harness scores **12/12, both gates PASS** on the dogfood repo
(`g1.3-mcpqa-dogfood.txt`).

### And the fix had a bug of its own, caught here rather than in the gate

Raising a timeout in a node harness is not a local change. Both harnesses register a per-request
`setTimeout` and never cleared it, so **the timeout value is the process's minimum lifetime**. At a
uniform 45s that cost 45 idle seconds; with `analyze` on its own 600s budget it became ten minutes
of hang after the work was done:

- `drive-r4.js` — the `retarget` case printed its final PASS and then sat there, so the `glyphs`
  case queued behind it in the same script never started. (This is also what truncated the
  interrupted before-state run, which had looked like the orchestrator kill.)
- `run.js` — `main()` ends with `finally { client.close() }` and no `process.exit`, so the process
  would linger the same ten minutes. `McpQaGateTests` waits for exit with a 300s cap: **a harness
  scoring a clean 12/12 would still have failed the gate on a hung process.**

Both now store `{resolve, timer}` in the pending map and `clearTimeout` on response.

**Bug #1 is left OPEN**, and deliberately: I could not force a cold analysis of the dogfood repo to
re-measure the failing path directly, and its filed root-cause text contains a claim I could not
confirm (it says snapshots are MVID-keyed so every Core edit invalidates them; the cache's own
`meta.json` version keys carry an `-opt-372C9FDCC0AB` suffix that is identical across entries last
used on 07-28 and today, across my Core rebuild). The three defects above are real and fixed on
their own evidence; whether that fully closes the bug wants one cold measurement.

## The red that was not a red — and the command that caused it

Every fast-suite run this session went red on `McpQaGateTests`, and it took an instrumented failure
message to find out why. It is **a verification-command artefact**, and it explains why the
conductor's own battery is green while sessions keep seeing red.

`eval/gates.ps1:136` runs Step 2 as
`--filter "Category!=Eval&Category!=CliSmoke&Category!=McpQa"`, and runs the MCP QA drive as its
**own Step 2b, alone** (`:152`), because — its comment says so — it is a 3-minute external `node`
drive against a machine-local repo. G1 sessions have been verifying with a bare
`--filter "Category!=Eval"`, which pulls that drive into a **674-test parallel run**. Under that
load the `DevContext.Server` the MCP spawns never binds: with the log field added here it reads
`did not become ready within 120s (exited=-1)` — the child **exits**, it is not merely slow. The MCP
then returns 1, so `initialize` is never answered and node dies with `FATAL: Timeout: initialize`
before scoring a single question.

Discriminator, same binaries, same minute: the same test **alone passes 2/2** and its harness scores
12/12 in 0.5s.

**Use the battery's own two commands to verify a G1 change**, not `Category!=Eval`.
