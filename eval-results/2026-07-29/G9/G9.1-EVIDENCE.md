## 2. Root cause — TWO causes, not one, and neither is the one the stage note predicted

The stage framing was "a demo/sample executable that is not under a `samples/` path outranks the packable
library it demonstrates". That is half right for one pole and wrong for the other.

### MahApps.Metro — a PATH SHAPE

`raw/MahApps.Metro/entries.json`, before: `count=25`, `byKind={"UiEntry":25}`. **Every one** of them:

```
UiEntry | ButtonsExample | .../src/MahApps.Metro.Samples/MahApps.Metro.Demo/ExampleViews/ButtonsExample.xaml.cs:16
UiEntry | App            | .../src/MahApps.Metro.Samples/MahApps.Metro.Demo/App.xaml.cs:16
...  (25 of 25, zero from src/MahApps.Metro)
```

`ProjectClassifier.IsSamplePath` matched `samples` only as a whole slash-delimited segment
(`p.Contains("/samples/")`). The directory here is `MahApps.Metro.Samples` — the character before
`Samples` is `.`, not `/` — so the demo counted as **production**, its 25 entries fired the entries rung,
and `DetectAppSubtype` + the `desktop-ui` signal returned `Desktop`.

### CLI (dotnet/command-line-api) — LADDER ORDER, no sample path anywhere

`src/System.CommandLine.Suggest/dotnet-suggest.csproj` is a **real, shipped dotnet tool** under a
production path:

```xml
<OutputType>Exe</OutputType>
<IsPackable>true</IsPackable>
<PackAsTool>true</PackAsTool>
<ToolCommandName>dotnet-suggest</ToolCommandName>
<ProjectReference Include="..\System.CommandLine\System.CommandLine.csproj" />
```

So the CliTool rung saw `prodConsoleExes=[dotnet-suggest]`, `IsCliToolCandidate=true`, no web/desktop
surface — and **returned**. The detector already owned the test that answers this correctly: the bottom
rung's `allExeAreAuxiliary` + `packable` check would have found that `dotnet-suggest` merely *consumes*
`System.CommandLine`, which declares `<IsPackable>true</IsPackable>`. **It was simply never consulted,
because the CliTool rung sits above it.**

## 3. The fix, and why each guard is there

**A. `ProjectClassifier.IsSamplePath` learns the dotted-compound sample COLLECTION** — a segment
delimited by `/` on both sides whose name ends `.samples` / `.examples` / `.snippets` / `.demos`.

*Plural only, deliberately.* The blast radius was measured across all 47 eval-repos before choosing:
the singular form appears on **shipped** projects — `OrchardCore/src/OrchardCore.Modules/OrchardCore.Demo`
(a real module in a repo whose truth is `App`) and `AzureFunctions/.../Worker.Extensions.Sample`. A
`*.Samples` *directory* is a container of samples by construction; a `*.Demo` *project* may well be
product. Pinned both ways in `TopologyNoiseTests`.

**B. `ArchetypeDetector` — the bottom rung's computation is extracted verbatim into
`DescribeLibraryShape()` and runs ONCE, above the CliTool and entries rungs.** A new rung returns
`Library` when `IsPackableLibraryWithOnlyAuxiliaryExes`. Three guards, each with a pole behind it:

| guard | the pole that needs it |
|---|---|
| `Packable` = an **explicit** `IsPackable`/`GeneratePackageOnBuild` (`CsprojReader.ResolveIsPackable`), **not** `hasPublicSurface` | **GitVersion.** Its shape is identical to command-line-api's — a `PackAsTool` exe referencing an in-solution library with a public API. One fact separates them: `System.CommandLine` declares `<IsPackable>true</IsPackable>`; `GitVersion.Core` (both `src/` and `new-cli/`) declares nothing, and GitVersion's root `Directory.Build.props` does not exist. `hasPublicSurface` would flip GitVersion out of CliTool. This is **symmetric declaration evidence**: `PackAsTool` on the exe loses only to `IsPackable` on the library it references. |
| `HasExecutables` | **eShop / OrchardCore / bitwarden-server.** A Web SDK host declares no `OutputType`, so an ordinary web app has an *empty* exe set and `All()` over it is vacuously true. Without this guard such a repo could reach Library the day any of its projects declared packability. |
| `!model.SamplesAreTheProduct` | **aspire-samples.** In a samples-only repo the samples *are* the product, so no executable in it is auxiliary to anything. |

### A design alternative that is measurably wrong — do not revisit it

"Suppress entries whose provenance lies under an auxiliary exe project" (the entries rung's sample-path
rule, generalised from sample PATH to auxiliary PROJECT) **would not have fixed CLI**. From
`after/raw/CLI/entries.json`, only one of the two entries belongs to the tool:

```
CliCommand | dotnet-suggest (Main)         | src/System.CommandLine.Suggest/Program.cs:14
CliCommand | RootCommand —settings object  | src/System.CommandLine/RootCommand.cs:21   <-- THE LIBRARY
```

The second is declared inside the packable library itself, so a provenance filter leaves it standing, the
entries rung still fires, and the archetype lands on `App` — a different wrong answer. Returning `Library`
from a rung *above* both rungs is what answers the question.

### Poles not in the sweep are inert by construction

`YARP`, `Ocelot`, `AzureFunctions`, `Functions`, `functions-app`, `company-functions`, `Blazor`,
`blazor-samples`, `signalr-app`, `TodoApi`, `VerticalSlice` and the dogfood repo are not in the sweep.
Two facts make them provably unreachable by this change, both measured rather than reasoned:

1. **Fix B is inert without a packability declaration.** Grepping every eval-repo for
   `<IsPackable>true>` / `<GeneratePackageOnBuild>true>` in any `.csproj`/`.props`/`.targets` returns
   exactly twelve repos: `CLI`, `CommunityToolkit.Mvvm`, `HotChocolate`, `Orleans`, `PowerToys`,
   `Quartz.NET`, `SignalR`, `Spectre.Console`, `StackExchange.Redis`, `YARP`, `wolverine`, `xUnit`.
   Eleven of the twelve are in the sweep; `YARP` is decided by the gateway rung, which sits above
   everything this change touched. **Not one repo whose declared truth is `App` declares packability
   anywhere**, and the one `Desktop`-truth repo that does (`PowerToys`) is protected by the WinExe clause.
2. **Fix A is inert without a dotted sample-collection directory.** Scanning every `.csproj` path in
   `eval-repos/` for a segment matching `*.{samples,examples,snippets,demos}` returns only
   `MahApps.Metro.Samples`, `Desktop/src/Avalonia.Samples`, `Quartz.NET/src/Quartz.Examples`,
   `MediatR/samples/MediatR.Examples` (already under `/samples/`) and the HotChocolate / Polly / refit /
   StackExchange.Redis benchmark dirs (already benchmark-classified by name). The dogfood repo has none.

### The one non-target movement, and why it is not a regression

`Desktop` (which is `AvaloniaUI/Avalonia.Samples`, not a WPF app) moves
`Desktop/Unknown` → `Desktop/SampleCollection`. Its archetype is unchanged. **Its style is deliberately
UNDECLARED** in `eval/expectations/graph-truth/Desktop.json`, whose note says: *"whether the honest
archetype for a samples-only desktop repo is Desktop or a sample collection is exactly the open
question, and inventing an answer here would be the 'right for the wrong reason' failure S4 recorded."*
Every project in that repo lives under `src/Avalonia.Samples/`, so Fix A makes
`ProjectClassifier.SamplesAreTheProduct` true for it and the T8 machinery renders it as what it is. No
declared cell moves; the open question now has a measured answer to consider, not a decision taken for
the owner.
