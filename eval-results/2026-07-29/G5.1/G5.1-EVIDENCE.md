## 2. The join code, and the predicate

"Wired" is one expression: `Insights/GraphOrphansSource.cs:45` — `entries.Count(e => e.Target is not null)`
(the app reads the same fact as `entriesWithTarget`, `features/shared/home-tiles.ts:233`).
`EntryPoint.Target` is assigned in exactly one place, `Graph/GraphBuilder.Entries.cs:24-26`:

```csharp
var target = ResolveEntryTarget(graph, e) ?? ResolveOwningTypeFallback(graph, e);
```

Three structural facts about that path, all of which independently produce `null` here:

**(A) The builder joins the TYPE, not the execute member.**
`Extractors/Specific/CliCommandExtractor.cs:112-121` *correctly* detects the execute method —
`InvokeAsync` is in its list and all five GitVersion verbs use exactly that name — and stores it on
`CliCommandDetection.ExecuteMethod`. `Graph/EntryPoints/CliCommandEntryPointBuilder.cs:29-40`
never reads that field: it computes `typeId = NodeId.ForType(...)` and sets `HandlerNode = typeId`.
The detected member name is dropped on the floor.

**(B) The resolver has no Calls arm for a Type-kind handler.**
`Graph/GraphBuilder.Entries.cs:111-118` — the `case NodeKind.Type:` arm reads **only** `Sends`
edges. `ResolvePrimaryCall`, the arm that takes a controller action from 0 to a target, is reachable
only from `case NodeKind.Member:`. A Type-kind handler with Calls edges and no Sends edges resolves
to `null` by construction, and `ResolveEntryTarget` does not roll a type's member edges up.

**(C) The last-resort fallback is blanked, for this entry kind only.**
`ResolveOwningTypeFallback` (`Entries.cs:37-63`) would return the handler's own title, but
`IsSelfEvident` kills it: `CliCommandEntryPointBuilder.cs:22` builds the entry title as
`"{verb} ({CommandType})"`, so the type name is **always** a whole-word substring of the entry's own
title. Every `[Command]`-attribute verb is self-evident by construction.

### Defect 1 — `this.<field>.<Method>()` never binds

`Graph2/BodyFactExtractor.cs:337-352` (`RootIdentifier`) walks a member access down to its root, and
for `this.service.Call()` the root is the `this` token. So `ReceiverText="this"`,
`ReceiverMember="service"`, and `ResolveFromScope("this")` finds no field/param/local →
`ReceiverType=null`. `Graph2/CallGraphBinder.cs:250-255` then hits

```csharp
if (inv.ReceiverText is null or "this")
    return symbols.TypeDeclaresMember(callerType, inv.MethodName) ? (callerType, Syntactic) : null;
```

`OutputCommand` does not declare `Call`, so the edge is dropped. **The `this` arm never looks at
`ReceiverMember`, so a genuine self-call `this.Method()` and a call through a field
`this.field.Method()` are indistinguishable to it.** `SymbolTable.HopThroughProperty`
(`SymbolTable.cs:299`) already performs exactly the required hop, but is properties-only by an
explicit decision whose stated reason is *cross-type* chaining ("a field is not part of the surface a
caller can chain through **in another type**", `SymbolTable.cs:283`) — a reason that does not apply
to a type's own `this.`-qualified field.

### Defect 2 — the semantic receiver upgrade fires by accident of formatting

Second probe (`DC_G51_PROBE2`, since reverted) inside `SemanticLitePopulator.TryBindReceiverType`.
Raw: `raw/probe-semantic.txt`, all 16 sites it reached:

```
BIND|ConfigCommand.cs   |L17|call=LogInformation|foundNodeKind=ExpressionStatement    |invocationAncestorFound=False
BIND|CalculateCommand.cs|L23|call=LogInformation|foundNodeKind=InvocationExpression   |invocationAncestorFound=True
BIND|CalculateCommand.cs|L25|call=LogInformation|foundNodeKind=ExpressionStatement    |invocationAncestorFound=False
```

`SemanticLitePopulator.cs:776-794` relocates the op by the **whole line's span** and then walks
**ancestors** for an `InvocationExpressionSyntax`. When the statement fits on one line, `FindNode`
returns the *statement* — and the invocation is a **descendant**, so it is never found. 15 of 16
sites report a statement kind; the one that binds is the one whose argument list wraps onto the next
line.

## 4. The controlled experiment — proof, not inference

Four classes, one interface, one field, one DI-resolved implementation, four spellings of the same
call. Sources: `fixture/Program.cs.txt`, `fixture/Fx.csproj.txt`. Dump: `raw/fixture-graph.json`.

| case | shape | out-edges from `Run` |
|---|---|---|
| **A** `WithoutThis` | `widget.Do();` — no `this.`, one line | **2** `[Syntactic]` → `Fx.IWidget`, `Fx.Widget::Do` |
| **B** `WithThis` | `this.widget.Do();` — one line | **0** |
| **C** `WithThisMultiLine` | `var v = this.widget.Do(⏎);` — statement starts at `var` | **0** |
| **D** `WithThisStatementSpans` | `this.widget.Do(⏎);` — statement **starts at the call** | **2** `[Semantic]` → `Fx.IWidget`, `Fx.Widget::Do` |

Two paths, two failure modes, and the resolution tag is the fingerprint: A is `Syntactic` (scope
resolution), D is `Semantic` (the upgrade). C proves multi-line is *not* sufficient — the statement
must begin at the invocation for `FindNode` to land on it.

## 5. What G5.2 must do, and what it must not

**Minimum sufficient set: Defect 1 + (A).** With Defect 1 fixed, `this.service.Call()` resolves its
receiver to `GitVersion.IService`, and the graph **already holds the DI answer** —
`Resolves[Join] Type:GitVersion.IService → Type:GitVersion.Service` is in the dump today — so
`ResolveCallee`'s `diImpl` route lands the edge on `GitVersion.Service`. With (A) fixed, the entry's
handler is the `InvokeAsync` member, `ResolveEntryTarget` reaches `ResolvePrimaryCall`, and
`GitVersion.Service` is the one in-scope non-framework callee. Target resolves; `0/5 → 5/5` for the
four verbs that call a collaborator. **`test` has none** (its body is `Console.WriteLine` +
`Task.FromResult`), so the honest outcome there is 4/5 with `test` explicitly unwired — a verb that
genuinely calls nothing must not be given a fabricated target.

**Two structural facts, no name list** (Batch E's CleanArchitecture precedent):

- *Defect 1's rule:* (i) the receiver root is `this`, and (ii) `ReceiverMember` names a member
  **declared on the caller type**. Both are read off the graph; neither is a name, a framework, or a
  repo. It is the existing `HopThroughProperty` hop, applied to the one case its own comment does not
  argue against.
- *(A)'s rule:* (i) the class is a detected command (a verb-bearing attribute — already established),
  and (ii) it declares a member whose parameter type is the detected **settings type**. That names the
  execute member structurally and would survive a rename of `InvokeAsync`. If the settings-type join
  proves impractical, `ExecuteMethod` is already detected and can carry it — but that one *is* a
  method-name convention list, and should be stated as such rather than presented as shape evidence.

**Out of scope for G5.2, deliberately:** Defect 2 (filed as bug #12). It is the correct fix for the
underlying mechanism, it is the reason 15 of 16 sites here have no semantic receiver type at all, and
it will move call-edge counts on **every** pole — it belongs in a batch that runs the full matrix,
not in a checkpoint whose acceptance is "the CleanArchitecture canary unmoved".
