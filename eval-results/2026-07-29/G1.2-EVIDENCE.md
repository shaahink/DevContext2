## 1. The [audit] premise was partly stale — re-measured before editing (PLAN §5 rule 2)

R4 §1 item 2 says *"`get_context` is structurally entry-only — libraries get nothing"*. That is **not**
what the code did. `EntryPointResolver.ResolveFromNode` already resolved a TYPE name to a synthetic
`PublicApi` entry, so a type focus on a library already produced a real pack:

| focus (FluentValidation, budget 4000) | BEFORE | verdict |
|---|---|---|
| `AbstractValidator` (type, 7 out-edges) | 1739 tok / **43% fill**, sections `identity,trace,signatures,di_wiring,bodies` | already worked |
| `InlineValidator` (type, leaf) | 349 tok / **8% fill**, trace is ONE line | thin |
| `RuleFor` (bare member name) | **envelope** — "No context could be built for 'RuleFor'.", zero suggestions | broken |

Artifacts: `g1.2-before-getctx-library.txt`, `mcp-r4-before/getctx-library-*.json`.

So the honest content of item 2 is two different defects:

**(1) A bare SYMBOL root resolved to nothing.** `get_context(focus:"RuleFor")` returned an envelope while
`resolve(query:"RuleFor")` **on the same handle** returned `Member:FluentValidation.AbstractValidator`1::RuleFor`
as its first candidate — and that member is printed in `AbstractValidator`'s own signatures section three
lines above. Two tools in one menu disagreeing about one name.

**(2) Every pack section was built from a TRACE, and a trace walks OUT-edges.** Right direction for an
HTTP endpoint, wrong one for a library symbol. Measured degrees (`neighbors` / `usages`,
`mcp-r4-before/symbol-probe-fluentvalidation.json`):

| symbol | in | out | consequence |
|---|---|---|---|
| `IValidator` — the library's central abstraction | **9** | 0 | pack was structurally empty |
| `InlineValidator` | 1 | 1 | 8% fill; the one user it has was not in the pack |
| `AbstractValidator` | 0 | 7 | fine — it is the outbound case |

## 2. What landed

1. **`EntryPointResolver` gains a member tier** (`ResolveFromMember`) that runs **last**, after
   Type/EntryPoint. Running last is what makes it additive: no focus that already resolved can move.
2. **`GraphQuery.ResolveEntry(focus)`** exposes the resolved entry, so `ContextPackBuilder` resolves the
   root **once**, through the same inventory it traces with, and knows whether the root is a declared
   entry or a symbol.
3. **A `usage` section** on symbol-rooted packs: the in-edges, rolled up so a Type root answers with the
   member that carries the collaboration, each row carrying the **call site's** repo-relative `file:line`
   (falling back to the caller's declaration line, *labelled differently* — a declaration is not a call site).
4. **An identity line that names the resolved symbol** — its node key, its file, "not a declared entry
   point", and how many symbols share the name. A symbol focus is a NAME; the pack now says which symbol
   it landed on.
5. **One candidate-ranking rule, on ROLLED degree** — see §4, found by the evidence run itself.

No proto change: the new sections ride the existing repeated `Section(key, tokens, content)`, so the S9
contract sweep needs no allow-list entry.

## 4. The second defect — found BY the evidence, not by reading code

The first after-run passed **every declared row** and still exposed something wrong, because the new
identity line prints the node key the tool resolved to:

> `get_context(focus:"IValidator")` rooted on `Type:FluentValidation.IValidator` (3 users) while
> `resolve(query:"IValidator")` on the same handle answered `Type:FluentValidation.IValidator`1` (9 users).
> Same name, two tools, different symbols — and `get_context` picked the emptier one.

**Root cause: two ranking rules for one question.** `GraphQuery.ResolveNodeId` has ranked on **rolled**
degree since C3 (a type's collaborations hang off its MEMBERS). `EntryPointResolver` ranked on the type's
**own** out-edges with no tie-break — and since the Type+tags collapse a type usually has none, so the
comparison was 0 against 0 and the winner was whichever node the graph enumerated first. That was also a
latent determinism hole: enumeration order is stable today, but nothing pinned it.

**Fix:** one `PickMostConnected` ranking on rolled (out, in) degree, tie-broken on the ordinal-least key.
Out-degree stays primary, so the "lands on the one that actually goes somewhere" rule is untouched — pinned
by `Resolve_still_prefers_out_degree_over_in_degree`. Rolling costs one graph pass and only runs when a
name is genuinely contested.

**Method worth reusing for the rest of G1:** make the evidence artifact print the **identity** of what the
tool resolved, not just whether it succeeded. A PASS/FAIL-only driver would have shipped this.
