## 1. The change

`src/DevContext.Core/Extractors/Generic/SyntaxStructureExtractor.cs` (+57 / −19).

`ResolveTypeDeclaration` used to walk the file's whole syntax tree **per base-list entry**:

```csharp
root.DescendantNodes().OfType<BaseTypeDeclarationSyntax>()
    .FirstOrDefault(t => t.Identifier.ValueText == typeName
        || typeName.StartsWith(t.Identifier.ValueText + "<", StringComparison.Ordinal));
```

It now consults an index built **once per file**:

```csharp
foreach (var decl in root.DescendantNodes().OfType<BaseTypeDeclarationSyntax>())
    index.TryAdd(decl.Identifier.ValueText, decl);      // first in document order wins
…
var generic = typeName.IndexOf('<');
var key = generic >= 0 ? typeName[..generic] : typeName;
return declIndex.TryGetValue(key, out var candidate) ? candidate : null;
```

`O(baseEntries × nodes)` → `O(nodes + baseEntries)`, per file.

**Why the lookup is equivalent rather than merely similar.** A declaration's `Identifier.ValueText`
is a single token and can never contain `<`. So the old predicate's two branches are mutually
exclusive: if `typeName` contains `<`, only the `StartsWith` branch can fire, and it fires exactly
when the identifier equals `typeName` truncated at the first `<`; if it does not, only the equality
branch can fire. "First node in document order satisfying either" is therefore exactly "the
first-declared type whose identifier equals that truncated key" — which is what the index holds.
Both call sites are covered (the per-file loop and the Blazor `@code` virtual trees).

## 3. What the second-biggest file taught — the trigger is base lists, not bytes

While choosing differential poles, a comparably huge generated file turned up in a repo **already in
the matrix**:

```
SignalR/src/Http/Routing/perf/Microbenchmarks/Matching/MatcherAzureBenchmarkBase.generated.cs
   3,085,317 bytes / 30,989 lines
```

The obvious guess is that SignalR was quietly paying the same cost. **It is not** — measured, its
`query graphdump --no-cache` went **121 s → 113 s**, about 7 %. (An earlier first-touch capture of
that repo read 196 s; a cold file cache over 10,508 files, not the extractor. The 121 s figure is the
warm one, taken back-to-back with the 113 s.)

The reason is worth more than the fix: that file holds **one** type declaration and **one** base
list. Cost is `baseEntriesInFile × nodesInFile`, so 3 MB with one base entry is two tree walks —
nothing. HotChocolate's file is 11.3 MB with **4,598** base lists.

So the class is sharper than "a big generated file":

> **A single file that is both large AND base-list dense makes analysis unbounded.** Either alone is
> harmless. Size sets the cost of one walk; the base-list count sets how many walks happen; the
> product is what has no bound. Nothing at repo level — file count, byte count, project count —
> predicts it, which is why HotChocolate looked like "a big repo" and bitwarden-server (more C# by
> bytes) finishes in 214 s.
