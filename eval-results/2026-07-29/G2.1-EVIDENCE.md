## 1. The measurement, in three states

Every number below is a live MCP call over stdio against the built `devcontext-mcp.exe`
(`eval/mcp-qa/drive-r4.js menu`, a new case). Raw responses are beside this file.

| | `tools/list` | `availableTools` (did-you-mean) | verdict |
|---|---|---|---|
| **BEFORE** — `mcp-r4-g21-before/` | 24 | 24, identical set | equality PASSES |
| **MID** — fold landed, hand list untouched — `mcp-r4-g21-mid/` | 21 | 24 | equality **FAILS** |
| **AFTER** — `mcp-r4-g21-after/` | 21 | 21, identical set | equality PASSES |

The BEFORE row is the point of this table. The hand-maintained array **was correct** — 24 literal
names beside 24 `[McpServerTool]` methods, in exact agreement — so a spot check ("does it list
`map`?") passes on the broken design, and so does the equality check. Nothing about the before-state
looks wrong. What the array could not do was *stay* correct.

One commit later, with the array untouched:

```
tools/list      (21): analyze close_session config entrypoints find get_context impact ...
availableTools  (24): ... flow ... insights ... interesting_points ...
FAIL  did-you-mean advertises exactly the real tool list
      — only-in-didyoumean=[flow,insights,interesting_points] only-in-tools/list=[]
```

**This is the red the program's standing rule asks for** (`mcp-r4-g21-mid/RUN.txt`). It is the third
checkpoint in a row where a check that looked reasonable would have passed on the broken state; the
one that discriminates is again an *invariant* (two answers to "what tools exist" cannot disagree),
not a threshold.

### The failure mode was worse than a stale list

The nearest-name search runs over that same array, so on the mid-state:

| call | reply |
|---|---|
| `insights` | *"Did you mean **'insights'**? See availableTools."* |
| `interesting_points` | *"Did you mean **'interesting_points'**?"* |
| `flow` | *"Did you mean **'top_flows'**?"* |

The first two point an agent at the tool that had just stopped existing — an infinite loop with a
helpful tone. The third is not a fold artefact and needs no fold to happen: `Closest()` returns on
the first **substring** match, and `"flow"` is a substring of `"top_flows"`. Any retired or
mistyped name that happens to be a substring of an unrelated tool gets a confident wrong redirect.

Hence a small fold-redirect table (retired → replacement + the literal call). It is not a second
menu, and the test asserts exactly that: **every row names a tool that is NOT in the registered
collection**, and every replacement **is**.

field, on a live TodoApi analysis (`mcp-r4-g21-after/`):

Its envelope carried `steps`/`touches`/`emits`. | compact trace now returns `steps=5 touches=0 emits=0` on `GET /`, text unchanged (`Entry: EntryPoint: GET /`) |

And the R4 §3 bar — no reply may point at a surface that no longer exists — is checked mechanically:
`no reply points at a folded tool — clean`.

## 4. Rider found while folding: the app's sandbox listed a tool that never existed

`mcp-page.ts` labels its "Try a tool" gRPC prober with MCP tool names, from its own literal array.
Two of nine rows were wrong, and one of them was wrong **independently of this checkpoint**:

- `search` — **there is no MCP tool called `search`.** The MCP names it `find`. That row has never
  matched the menu it claims to show.
- `insights` — mapped to `getStats` in the switch *already*, i.e. the app had independently
  discovered that `insights` and `stats` are the same call. Now folded away.

Corrected to `find` (same RPC) and `insights` dropped. The deeper problem — the app cannot check its
labels against the MCP's menu, because it speaks gRPC and not MCP — is filed as a tracked bug rather
than fixed here.

## 6. Traps re-paid

- The MCP spawns a `DevContext.Server` that **outlives the driver** and locks
  `Core/Cli/Contracts.dll`; the next `dotnet build` then reports 6 errors + 30 warnings that read
  like a code break. Killed by PID (34340), rebuilt clean. Second session in a row.
- `InternalsVisibleTo` is **not available** for `DevContext.Mcp`: this project and
  `DevContext.Server` both compile a top-level `Program` into the global namespace, so opening
  internals to the shared test assembly makes `WebApplicationFactory<Program>` ambiguous (CS0433).
  `UnknownToolHandler` is public instead, with the reason recorded at the type.
