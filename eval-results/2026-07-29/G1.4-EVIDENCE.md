## 0. The driver had to be fixed before it could judge anything

The `find-kind` case **passed on the broken before-state**. Its two checks were "every returned row
has kind Type" — true, because the MCP did filter, just in the wrong place — and "total ≥ page
length" (22 ≥ 5). This is the third time in this program a case has been satisfied by the defect it
was written to catch (G1.3's glyphs case, G1.2's entry canary, this).

What actually separates a true total from a windowed one is that **a true total does not move when
the page size moves**. That, plus five more, is what the case asserts now.

## 1. Item 6 — `find(kind:)` server-side

### What the before-state measured (eShop, query `Order`)

```
find(limit:100)             -> total=120    <- limit+20 EXACTLY: the MCP's own fetch window
find(kind:"Type", limit:5)  -> total=22     <- "Types among the first 25 matches"
```

`DevContextTools.cs:1245` fetched `limit + cursor + 20` rows, filtered *those* by kind in LINQ, and
reported the survivors as `total`. A filter downstream of a truncation can only ever describe the
window it was handed, so both numbers were facts about the page size.

### After

```
  PASS  total does not move with the page size — limit100 -> 354 · limit5 -> 354
  PASS  total is not the fetch window — 354 vs limit+20=120
  PASS  kind filter applied — Type,Type,Type,Type,Type
  PASS  kind total is the whole kind-filtered set — total=174 · everything-in-one-page=174
  PASS  kind total does not move with the page size — limit5 -> 174 · limit1000 -> 174
  PASS  filtering can only narrow — 174 <= 354
  PASS  hasMore true when the page is short of the total — hasMore=true page=5 total=174
  PASS  hasMore false when one page holds everything — hasMore=false of 174
  PASS  cursor pages forward — page1=5 page2=5 overlap=0
  PASS  an unknown kind matches nothing — error=No nodes match 'Order' of kind 'NoSuchKind'. results=0
```

**The size of the lie:** eShop has **354** nodes matching `Order`, of which **174** are Types. The
tool reported **120** and **22**. An agent asking "how much of this repo is about orders" was told
a third of the truth, and a seventh of it once it filtered.

### Canary — the unfiltered page must not move

Only the counts were wrong; the rows were right, and they had to stay right.

```
before rows 100, after rows 100
identical order+contents: true
typed page identical: true (5, 5)
before total 120 -> after 354 · before typed total 22 -> after typed total 174
```

### Where the fix lives

- `proto`: `SearchRequest.kind` (4), `SearchResponse.total_matches` (2).
- `GraphQuery.FindPage(query, kind, limit)` — kind applied **above** the truncation, returns the
  uncapped match count. `Find(query, limit)` is now its page, so resolve/usages/impact are untouched
  (pinned by `Find_still_returns_the_same_page_it_always_did`).
- `DevContextGrpcService.SearchNodes` passes the kind down and the total back.
- `DevContextTools.Find` puts the kind on the **request** and reads `TotalMatches`. The over-fetch
  (`+20`) is gone — it existed only to make a client-side total look plausible.

## 2. Item 7 — `analyze` honesty

### Before — the same eleven words whatever happened

```json
{ "handle": "81b550e2dc79...", "status": "ready", "hint": "Analysis complete. Omit 'handle' ..." }
```

Identical for a call that spent eight minutes analysing and one that reused an open session in 12ms.
The `AnalysisSummary` the server had already computed was read off the stream and dropped.

### After — cold, then the same repo again

```json
{ "handle": "6096e3f8...", "status": "ready", "cached": false,
  "note": "Analyzed now. A first analysis of a large repo can take minutes; the result is snapshotted, so the same repo+HEAD+solution re-opens in seconds.",
  "summary": { "label": "TodoApp", "archetype": "App", "isLibrary": false, "projects": 6,
               "nodes": 129, "edges": 80, "entries": 12, "entriesWithTarget": 12,
               "elapsedMs": 1709, "explanation": "Overview map (no focus)." }, "hint": "..." }
```

```json
{ "handle": "6096e3f8...", "status": "ready", "cached": true,
  "note": "Served from cache — no analysis ran, and the numbers below describe the run that produced this session.", ... }
```

```
  PASS  summary returned
  PASS  summary carries a real graph, not zeros — nodes=129 edges=80 entries=12 projects=6
  PASS  summary names the archetype — archetype="App"
  PASS  note present
  PASS  cold call answers the cached question at all — cached=false in 1.8s
  PASS  re-analyze reports cached — cached=true in 0.0s
  PASS  cached agrees with the clock — cached=true elapsed=12ms
  PASS  the note changes when the answer does — cold.cached=false again.cached=true
```

The cold leg is genuinely cold: the Core edit changed the MVID, which invalidates every snapshot
(PLAN §4), so the first call really analysed — 1.8s, `cached:false` — and the second was served in
12ms with `cached:true`. The flag is corroborated by the clock, not by its own say-so.

### Two defects the [audit] ref did not name, both found by re-verifying it

1. **`AnalysisSummary.archetype` was assigned nowhere.** `ProtoMapper.ToSummary` set `IsLibrary` and
   skipped `Archetype`, so every analyze the server has ever answered carried `archetype: ""`.
   `ToMapResponse` has filled the same fact correctly, from the same source, all along. One line.
2. **The MCP dropped the `Error` event too.** A failed analysis fell through to the generic
   "Analysis did not return a handle", so `AnalysisException`'s own reason — "Git is not installed",
   "Repository not found" — never reached the agent. Same class as the discarded Progress events,
   sharper consequence. Pinned by `A_streamed_error_surfaces_the_servers_reason`.

### Where `cached` comes from (measured, not inferred)

Three paths return an analysis without analysing, and before this checkpoint only one of them said
so — to a progress event nobody read:

| path | before | now |
|---|---|---|
| session reuse (repo+HEAD+sln open) | progress `"cached"`, discarded | `AnalysisOutcome.Cached = true` |
| snapshot hit via clone registry (`EngineRunner:36-57`) | silent | `EngineResult.FromSnapshotCache = true` |
| snapshot hit on a local path (`EngineRunner:70-85`) | silent | `EngineResult.FromSnapshotCache = true` |

`AnalyzeResult.cached` is a fact about the **call**, which is why it rides there and not on
`AnalysisSummary`: a reused session hands back the original analysis's summary, `elapsed_ms` and all,
so a flag stored there would describe the wrong run. This is deliberately **not** R4 item 10 /
G3.3's session-level provenance (`analyzed_at` / `git_head` on `SessionInfo`) — G3.3 should extend
this field rather than add a second spelling of it.

Test counts are the discovery proof: a passing test is not named in the log, so the only way to know

Server 43 → 58 (**+15**: `McpFindTotalsTests` 7, `McpAnalyzeEnvelopeTests` 6, `AnalyzeCacheTruthTests` 2).

New tests, and what each one would have caught:

- `GraphQueryTests.FindPage_*` (5) — the total counts every match; the kind runs above the limit; an
  unknown kind is a true zero; `Find` returns the page it always did.
- `McpFindTotalsTests` (7) — the total comes from the server; `hasMore` derives from it; the kind
  goes out **on the request** (the whole item); no kind stays absent, not empty-string; a cursor past
  the end says so instead of denying the matches.
- `McpAnalyzeEnvelopeTests` (6) — the summary reaches the agent; `cached` is passed through, not
  guessed; the note moves with it; a streamed error surfaces the server's reason.
- `AnalyzeCacheTruthTests` (2) — all three cache paths report themselves, against a redirected
  cache root so "cold" is actually cold; a second repo is not answered from the first's cache.

`eval/contract-sweep.ps1` is the mechanical half of R-T1 here: three proto fields were added and all
three have readers, so none shipped dead.
