## 2. The discriminator, watched RED → GREEN

The check that proves nothing is "the filter returned only ReadsWrites edges" — an implementation
filtering the WRONG SET passes that. The one that discriminates is the **C3 roll-up**: after Batch A
a Type node carries almost no edges of its own, so a filter applied to `_graph.OutEdges(type, kind)`
answers "nothing here" about wiring that runs on every request.

Probe: swapped `RolledEdges(id, direction)` for `_graph.OutEdges(id)` in `NeighborsView`, ran, reverted.
Log: **`g32/RED-direct-edges.txt`**.

```
Failed 4, Passed 16, Total 20
  The_kind_filter_sees_the_edges_that_hang_off_the_members   Expected: 2  Actual: 0
  An_intra_type_call_is_not_a_neighbour...                   Assert.Single: the collection was empty
```

`Expected 2, Actual 0` is the shipped defect in one line: a type that writes one table from two
different members reports that it writes **none**.

**16 of the 20 passed on the broken implementation.** The whole kind vocabulary, the leaf case, the
delegation, `FindUsages` — all green while the primitive answered 0 to its headline question. A
suite made of the plausible 16 ships this.

The end-to-end file exists because neither of the others can reach
`DevContextGrpcService.GetNeighbors`, and that method makes the two decisions this item is actually
about: what `"usages"` means now that it takes a kind, and whether an unparseable kind is refused or
falls through. A mapper test cannot see either — in both cases the mapper is handed a view that has
already had the decision applied.

Equivalence is **measured, not asserted from the comment**: the rewrite moved the filter from inside
`RolledEdges` to above it, and `Filtering_above_the_roll_up_equals_filtering_inside_it` compares the
two orders over every node × both directions × every kind (144 comparisons) via reflection on the
private overload — comparing against a re-implementation would only prove the test agrees with itself.

## 6. Said out loud

- **`Neighbors()` now costs a histogram it may not need.** It delegates to `NeighborsView`, which
  counts every kind even for a caller that only wants filtered rows. The repo has exactly one such
  caller (`ContextPackBuilder.cs:462`, `EdgeKind.Resolves`). One dictionary bump per edge on a walk
  that already allocates an `EdgeRef` per row — real, small, and stated rather than hidden.
- **The CLI does not render the server's `note`.** It refuses an unknown kind with its own
  `{error, validKinds}` object and otherwise lets `kindsPresent` speak. The information is there;
  the sentence is not. If the CLI ever needs to read like the MCP does, that is the gap.
- **Not in scope, deliberately:** no `kind` on `seam` (G3.1 left it out for the same reason — one
  contract change per proto edit), and no app UI for the filter (the app is a reader of the same
  contract and is unaffected by an optional request field).
- **Still open from G2.2 §6**, and NOT folded in here despite this being a proto edit:
  `TraceResponse.applied_budget_tokens`. Coupling it to this change would have put a field nobody
  asked for into the same commit as a contract this checkpoint owns.
