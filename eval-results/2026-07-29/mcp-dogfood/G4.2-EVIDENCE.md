## Task 2 — a real change in Hangfire, oriented by MCP only

The change: `LogJobDurationAttribute`, an `IServerFilter` that times each background job and logs the
elapsed milliseconds with the job id and the method that ran. Hangfire is a `Library` with **0 entry
points**, so R4 §2's first suggestion ("add an endpoint") does not exist here; the filter pipeline is
the extension point the product is actually built around.

Six facts were declared in `CHANGE-SPEC.md` and committed **before the first call**, so the
orientation could not be graded against a target moved afterwards.

The difference is not that the tool got better between Monday and Tuesday. **Task 1 asked for
behaviour** ("where does X get persisted"), which lives in edges, and edges are this graph's weak
half. **Task 2 asked for declarations** — a namespace, a signature, a base class, a state bag, a
logging convention, a file to copy — and declarations are exactly what `get_context`'s
`signatures`/`bodies` sections and `read_source` carry verbatim. *The MCP is markedly better at "what
does this look like" than at "what happens next", and a development task is mostly the former.*

F5 was chosen as the trap: general .NET knowledge says `ILogger<T>`, and that code does not compile
here. The tool gave the right answer.

### The reusable trick this drive found

`IServerFilter` has **inDegree 0 and outDegree 0**, and `usages(nodeId)` returns `count: 0`. The
interface that every filter in the repo implements has no edges at all — G4.1's "no inheritance edge
kind" gap, hit head-on in a development task.

The way through: **ask about the type the interface's method takes as a parameter.**
`get_context(focus:"PerformingContext")`'s `usage` section named three implementors with `file:line` —
`CaptureCultureAttribute::OnPerforming @:112`, `DisableConcurrentExecutionAttribute::OnPerforming
@:51`, `JobParameterInjectionFilter::OnPerforming @:35`. That works today, with no engine change, and
it is the most useful workaround this strand has found for its biggest structural gap. Note also that
`find(query:"ServerFilter", kind:"Type")` returns **only the interface** — the three implementors
carry no matching name, so name search cannot substitute.

### The change compiles — and the green was not believed until it went red

`eval-repos/Hangfire` **does not build out of the box**, and that is not the change:
`src/Hangfire.Core/Razor.build` imports `RazorGenerator.MsBuild.2.5.0` from an old-style `packages/`
directory that was never restored. Proven by removing the new file and rebuilding — identical 2 errors
(`build-baseline-unchanged.txt`, MSB4019 + MSB3073).

Bypassed **without editing the repo** by making both `Exec` conditions in the `GenerateRazorClasses`
target false: `-p:MSBuildCurrentFullPath=Z:\nope\MSBuild.exe -p:MSBuild14FullPath=Z:\nope\MSBuild.exe`.
The target then degrades to its own `Warning`. Baseline green (`build-baseline-norazor.txt`, exit 0);
with the new file, green (`build.txt`, **EXITCODE=0**, 1 warning / 0 errors).

That green took 1.19 s on a ~350-file project, which is the exact shape of *nothing was compiled*. So
`stopwatch.Stop()` was replaced with `stopwatch.ThisMemberDoesNotExist()` and the build was re-run:
**CS1061 at `LogJobDurationAttribute.cs(57,23)`, exit 1** (`build-red-canary.txt`), then restored and
re-run green. The file is compiled; the verdict is real.

`eval-repos/Hangfire` was returned to a clean working tree — it is a graph-truth matrix pole, and the
change lives only as `task2/CHANGE.patch`.

## Task 3 — DevContext on itself

### A5: the `devcontext.json` claim, measured (full detail in `task3/DEVCONTEXT-JSON-SCOPE.md`)

R4 §2 warns that the server ignores `devcontext.json` so "CLI/MCP see different file sets on this
repo". **True in mechanism, wrong about the consequence, and it names the wrong cause for a real
divergence.**

| run | reads the config | files | projects | nodes | edges |
|---|---|---|---|---|---|
| CLI from the repo root | yes | 385 | 8 | **1254** | **1383** |
| CLI from a config-free cwd | no | 442 | 29 | **1254** | **1383** |
| MCP `analyze` | no | — | 5 | **1260** | **1398** |

- The server genuinely never reads it: `DevContextConfig` is a **CLI project type**, and
  `DevContext.Server` has *no* reference to `DevContextConfig` or `ExcludePatterns`.
- But `DefaultExcludePatterns` already contains `eval-repos` and `analysis-repos`, so this repo's
  config adds only **`fixtures`** and **`goldens`** — not the 47-eval-repo swallow the note implies.
- And those two patterns move **no nodes and no edges**: dropping the config leaves the graph
  byte-identical at 1254/1383, because Batch C's solution scoping already excludes the 21 fixture
  projects from `DevContext.slnx`.
- **So the +6 node / +15 edge CLI↔MCP divergence is not caused by the config** — the config-free CLI
  run still produces the *CLI* number. A real two-surfaces-one-repo disagreement, now isolated away
  from the thing that was blamed for it.

Turned up on the way: `DevContextConfig.DefaultPath` is `Path.Combine(Environment.CurrentDirectory,
"devcontext.json")` — the **working directory, not the analysed repo root**. So analysing another repo
from here applies this repo's exclusions to it, silently.

### A6: the maintenance question — and the tool's blind spot was the question

The question was live work, not a probe: **bug #8's own "what to measure first" — does call-edge
extraction walk lambda bodies, and where is that code?**

MCP got me to `CallGraphBinder` and `BodyFactsExtractor` quickly. Then it stopped being able to help,
in a way that is itself the answer. `neighbors(BodyFactsExtractor, out)` returns **3 edges** — a cache,
a context and a logger — which cannot be the whole story for a class whose job is walking method
bodies. `read_source` gave the six real call sites:

| line | call | in a lambda? | edge? |
|---|---|---|---|
| :51 | `context.Analysis.GetOrBuildBodyFactsAsync(…)` | yes | **yes** |
| :54 | `context.Cache.GetSyntaxTreeAsync(…)` | yes, **nested** | **yes** |
| :56 | `BodyFactExtractor.Extract(root, filePath, project)` | yes, nested | **no** |
| :62 | `context.Logger.LogWarning(…)` | yes (catch) | **yes** |
| :74 | `Utilities.RazorCodeVirtualizer.EnumerateVirtualTreesAsync(…)` | **no** | **no** |
| :80 | `BodyFactExtractor.Extract(…)` | no | **no** |

**This refutes bug #8's stated cause in both directions at once.** Calls inside lambda arguments *do*
bind here — including one nested two deep — and the call that binds *nothing* at line 74 is not inside
a lambda at all.

What the three missing edges share is that they are **static calls with a type-name receiver**, while
all three that bound are instance calls through a receiver chain. Tested on two further types, 3-for-3:

```
neighbors(Type:DevContext.Core.Graph2.BodyFactExtractor,        in) -> count 0
neighbors(Type:DevContext.Core.Utilities.RazorCodeVirtualizer,  in) -> count 0
neighbors(Type:DevContext.Core.Utilities.ExtractorHelpers,      in) -> count 0
```

All three are real, well-formed nodes (`BodyFactExtractor` carries `Extract` / `WalkMember` /
`SplitName` and has 3 `Semantic` out-edges) that **nothing in the graph points at**. I checked the
missing-node hypothesis first; it was wrong. Filed as **bug #11**, with bug #8 flagged for
re-measurement against this counter-example before anyone fixes it as written.

Context for the size of it: `stats` reports Calls `verified 280 / approx 1103` — **80% of this repo's
own call edges are approximate**, and the entire static-utility layer of the engine is invisible to
its own graph.

**The self-referential result is the finding.** The MCP could not lead me to `BodyFactExtractor` —
the body walker, the literal subject of the question — because nothing points at it. I reached it by
reading line 56. *The tool's blind spot was exactly the thing being asked about, and the reply that
concealed it (`count: 0`) is shaped identically to a true zero.*

not emptiness and not an error, but **a confident, incomplete answer with nothing on the wire saying
which**. That is now the most common defect shape R4 has found — three in G4.1, three more here.
