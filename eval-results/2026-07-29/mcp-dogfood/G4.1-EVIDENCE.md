## The token question, answered honestly

R4 §3 asks for fewer tokens than a grep-based session. **The MCP drive cost 44,712 tokens. The
ground-truth phase that verified all ten answers cost three shell calls and roughly 4,000 tokens.**
On raw token count, grep wins by an order of magnitude, and no amount of framing changes that.

The comparison is not the whole truth in either direction:

- It flatters grep, because those greps were *seeded by the drive* — I grepped for `CreateExpiredJob`,
  `FetchNextJob`, `InvokeServerFilter` because the MCP had already handed me those names. A cold grep
  session starts with `grep -r "Enqueue"` on 357 files and pays for the noise.
- It flatters the MCP too little on one axis and too much on another: 12.9 s of tool wall time for
  the whole drive is genuinely excellent, but **two calls are 46% of the bill** — `map` at 17,105
  tokens (38%) and `tools/list` at 3,468 (8%). `map` has one parameter, `handle`; there is no way to
  ask for less of it. Cut those two and the drive is 24k tokens for 41 calls.

The defensible statement: **on this repo the MCP's value was not token economy, it was that it
produced the right symbol names, with file:line provenance, from zero prior knowledge, in 13 seconds
of tool time.** Grep cannot do that — it needs the name first. The right posture for an agent is
therefore MCP to find the names, then read the source; which is close to what `read_source` is for,
and it is telling that the drive never needed it.

### Bug #5's fix, measured both ways (and my own candidate cause was wrong)

Raw dumps: `probe-descriptions/raw/{001,002}-tools_list.json`. All edits reverted; `src/` is clean and
the bins were rebuilt from the reverted source.

- **`<GenerateDocumentationFile>true</GenerateDocumentationFile>` does NOT fix it.** With
  `devcontext-mcp.xml` (10,697 bytes) generated next to the dll, `tools/list` came back at 3,468
  tokens — byte-identical — with `description: ""` on all 22 tools. ModelContextProtocol 1.4.0 does
  not read XML doc comments.
- **`[System.ComponentModel.Description(…)]` does.** Spiked on one tool: `{"name":"top_flows",
  "description":"SPIKE: Top 20 entry points ranked by importance score."}`, 3,481 tokens (+13).
- Rider: enabling the doc file turns IDE0005 into an error here (warnings are errors) and it found a
  real dead `using System.Net.Http.Json;` at `ServerShim.cs:2`.

So the fix is 22 attributes carrying the text the 31 `///` summaries already hold. The bug report
filed an hour earlier named the wrong remedy and said to measure it rather than believe it; measuring
took four minutes.

## Structural gaps (not bugs — things the tool does not have)

1. **No inheritance edge kind exists.** `SeamKind` is `Entry, Call, Send, Handle, Raise, Consume, Data,
   Resolve, Pipeline, CrossService` — and `stats` on Hangfire reports `Calls 596 · Resolves 19` and
   nothing else. So *"who implements this interface"* and *"what does this class derive from"* — the
   two questions a library forces on you — cannot be asked. `map`'s ABSTRACTIONS section knows
   implementor **counts** for its top ten, but names none and cannot be queried. This is the single
   biggest gap for the `Library` archetype, which S10's E3 decision made a first-class citizen.
2. **The call graph fragments at every interface, and `seam` calls that "unconnected".** Calls 36/37:
   `BackgroundJobClient` → `IStorageConnection` is reported as unconnected within 8 hops. A library has
   no DI container of its own (19 `Resolves` edges for 51 interfaces), so the walk dies at the first
   abstraction. The note honestly describes the *method* ("the walk exhausted everything reachable…"),
   but the sentence it leads with — `'X' and 'Y' are unconnected` — is a claim about the code.
3. **`map` is all-or-nothing.** 17,105 tokens, one parameter.
4. **Dead ends still do not name a next step that works** (R4 §3 bullet 3), outside the kind-filter
   path G3.2 fixed. Measured: `entrypoints` → `{count:0,byKind:{},entries:[]}` (12 tokens, no word
   about the archetype that guarantees it); `neighbors(RouteCollection,out)` → bare zero; `tests_for` →
   an honest method note that still does not say *no test project is in the analysed scope*; and the
   sharpest one — call 38's envelope recommends `usages(nodeId:…)`, call 41 runs exactly that and gets
   `{count:0,usages:[]}`, i.e. **taking the tool's advice returned strictly less than ignoring it**.

## What worked, and should not be lost

The G1–G3 work is visible all over this drive and it carried it:

- `analyze` returned the honest envelope G1.4 built (`cached:false`, `analyzedAt`, `gitHead`,
  archetype) — the frame for everything after it.
- Every edge in every `neighbors`/`usages` answer arrived with `file:line` provenance and a
  `resolution` (`Syntactic` / `[approx]`). That provenance is what made the post-drive verification
  three shell calls instead of a hunt.
- The compact-trace legend and the `di` glyph (G1.3) are what made `IStorageConnection ◇
  JobStorageConnection` readable as *the implementation the interface resolves to*.
- `get_context` on a symbol root (G1.2) produced a real pack on a library with zero entries — the
  case that used to return nothing.
- Error envelopes are, in shape, good: they say what resolved, offer candidates, and give an example.
  The failures above are about *where they point*, not about their form.
