# G2.2 — one trace policy across MCP / CLI / server

**Checkpoint:** G2.2 (R4 §1 item 12) · **Branch:** `feat/graph-v2` · **Date:** 2026-07-29

> The divergence was not three numbers. It was that **every client restated the policy's dials as its
> own literals**, so the policy's defaults never reached the engine — and one of its rules had
> therefore never run at all.

---

## 1. The before-state, read from source

| surface | trace dials it sent | where |
|---|---|---|
| MCP `trace` | `depth = 6` **and** `budgetTokens = 4000`, **both always assigned** | `DevContextTools.cs` signature |
| MCP `flow` | no budget at all → unlimited | folded away by G2.1 |
| CLI `query --op trace` | depth, **no budget → unlimited** | `QueryCommand.cs:365` |
| CLI render path | `MaxTokens 8000` → `TracePolicy.TreeBudget(8000)` = 6800 | `DiscoveryPipeline.cs:543` |
| server `GetTrace` | absent budget → `0` = unlimited | `DevContextGrpcService.cs:149` |
| desktop | always a depth, never a budget → unlimited | `trace.store.ts:165` |

**A C# parameter default is not an unset field.** Assigning a proto3 `optional` sets its presence
bit even when the value equals the server's own default, so `request.HasDepth` and
`request.HasBudgetTokens` were unconditionally true for every gRPC caller.

### What that cost, beyond the numbers

`TracePolicy.ElasticDepth` — Batch E's budget-elastic deepening — is gated on
`explicitDepth: request.HasDepth`, which has exactly **one** caller in the solution
(`DevContextGrpcService.cs:156`). Since no client ever left `depth` unset, **that rule had never
executed on a request the product has served.** Dead by construction; the fourth such find in this
program and the first in the graph layer rather than the render layer.

## 2. Two corrections I made to my own reasoning, because I measured

Both are recorded because each would otherwise have shipped as a claim.

**(a) The 4000-token default is not the observable half of item 12 on this pole.** Measured on
eShop `POST /api/orders/`: `budgetTokens: 0` and `budgetTokens: 4000` return the **identical** tree
at depth 6 (59 steps), 9 and 12 (72). The default cuts nothing there. A check asserting "the default
cut something" would have been theatre. (Shaping does work: a 300-token budget cuts 59 → 6. That is
the anti-vacuity guard the driver now runs *first*.)

**(b) My diagnosis of ElasticDepth's silence was wrong, and the code was right — again.** I read
`TraceStep.Truncated` as fan-out-only, which would make `HitDepthLimit` unreachable.
`TraceBuilder.cs:331` takes the same branch for `depth >= opts.MaxDepth` as for a revisit, computes
`omittedTargets` and sets `Truncated` from it: a depth stop with unexplored children **is** marked.
The real reason is the other half of the rule — `usedTokens * 2 > treeBudget` → stay. eShop's
59-step tree is ~2950 tokens (extrapolated from budget 300 → 6 steps), most of 4000, so the rule
**correctly declines**. Give it room and it fires.

### The red is isolated, not incidental

The middle column is the strong part. With the `TracePolicy` constant, the server default and the
CLI alignment **all in place**, and *only* `DevContextTools.cs` reverted to the previous commit

moment the file returns. That pins the cause on the MCP's restated literal rather than on any of
the other three edits.

## 4. What changed

| file | change |
|---|---|
| `Core/Graph/TracePolicy.cs` | **`DefaultBudgetTokens = 4000`** — the one default, with a doc comment stating the measurement it came from (the only trace-*specific* default the product has shipped; the CLI's 8000 is a whole-*document* budget out of which `TreeBudget` already carves the tree's share) |
| `Core/Graph/GraphQuery.cs` | the focus overload of `Trace` takes `explicitDepth` and passes it through, so a caller that resolves a focus by name can still leave the depth to the policy |
| `Server/Endpoints/DevContextGrpcService.cs` | an **absent** budget is now `TracePolicy.DefaultBudgetTokens`, not "unlimited"; an explicit `0` still means the full tree |
| `Mcp/DevContextTools.cs` | `depth`/`budgetTokens` become **nullable**, and an unnamed dial is **not put on the wire**; the reply carries `budgetSource`; `BudgetHint` stops quoting a number it did not send |
| `Cli/Commands/QueryCommand.cs` | the trace op reads the same default and passes the nullable depth through instead of collapsing it |
| `App/data-access/devcontext-api.ts` | the desktop **states** `budgetTokens: 0`. Without this it would silently start truncating its trace tree — a product regression smuggled in under a defaults cleanup. A GUI does not pay tokens; saying so is better than resting on a rule this checkpoint changes |
| `tests/.../TraceBudgetPolicyTests.cs` | **new, 11 tests**: an unnamed dial is absent on the wire, a named one is sent exactly, `0` is an explicit full tree, `budgetSource` names the owner, `ElasticDepth`'s five branches, and the default is a real budget whose tree share clears the floor |
| `docs/product/mcp-reference.md` | the `trace` row and the budget note say what omitting a dial now means |

## 6. Left open, deliberately

- The MCP cannot report the *number* it was shaped by, only its source, because `TraceResponse`
  carries no applied-budget field. `budgetSource` is the honest form without a proto change; a
  one-field addition (`applied_budget_tokens`, read by the MCP so the contract sweep stays green)
  would be strictly better and is the obvious follow-up.
- `get_context` / `verify_context` still carry their own `budgetTokens = 8000` literals. That is a
  *document* budget for a different artifact, not the trace contract, so it was left alone rather
  than folded in on a guess — but it is the same shape of hazard and deserves the same treatment.
