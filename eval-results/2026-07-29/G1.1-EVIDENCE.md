## What was actually wrong — the leak was wider than the [audit] ref

Item 1's `[audit] DevContextTools.cs:543-553` re-verified (the tool now starts at `:539`, same
code). But the flags are emitted by **Core renderers every surface shares**, so the honest
inventory comes from sweeping Core, not from reading the MCP tool:

| Site | Text | Reaches MCP? |
|---|---|---|
| `MapRenderer.cs` ×4 | console backstop NOTE · "N more projects (use `--focus`…)" · "N more entries (use `--focus`…)" · footer "drill in: `--focus`" | yes |
| `DiscoveryModel.cs` `SolutionScopeNote.Text` | "; analyze another with `--sln <name>`" — stamped into the map's SCOPE line | yes |
| `LibrarySurfaceRenderer.cs:122,125` | "use `--format json` for the full surface" | **yes — and missed by session #1** |
| `MarkdownRenderer.cs:304,1123` | "`--around TypeName`" | **no** — registered only at `src/DevContext.Cli/Services/ServiceRegistration.cs:35`, CLI-only, so naming a CLI flag there is correct. Left alone. |

The two `LibrarySurfaceRenderer` sites are the sharpest case: they fire on exactly the library
archetype item 1 is about, and they pointed an MCP caller at a fuller answer that — until the
structured surface landed in the same checkpoint — MCP genuinely could not reach.

Design call recorded: the phrasing is **surface-neutral**, not per-surface. `RenderRequest`
(`src/DevContext.Core/Pipeline/RenderRequest.cs`) carries no surface/client field, so a
surface-aware hint would mean a new Core field threaded through CLI + Server + App — scope creep
past G1.1. "trace" is a verb all three surfaces have; `--focus` is true on exactly one. The
pointers are all still present — this is a no-flags change, not a no-pointers change.

## The one red, and why it is not G1.1's

`McpQaGateTests.McpQaHarness_Passes_Against_Dogfood` failed: score **0/12**, header
`Baseline: ? nodes, ? edges, ? entries`, every question shaped like an empty analysis
("resolve returned 0 candidates", "config returned 0 keys", "byKind=undefined"). It has scored
12/12 on every dated report since 2026-07-16.

It was not read off a doc comment or waved away — it was measured in both directions, same
binaries, no code change between the two runs:

| run | snapshot | baseline | score |
|---|---|---|---|
| 1 — inside the test suite, first run after the Core edit | cold | `? nodes, ? edges, ? entries` | **0/12** |
| 2 — `node eval/mcp-qa/run.js`, minutes later | warm | `426 nodes, 328 edges, 34 entries` | **12/12** |

Run 2's baseline is identical to 2026-07-28's 12/12 run. Artifacts: `mcp-qa-rerun-warm.txt`,
`mcp-qa.md`.

Root cause is in the harness, `eval/mcp-qa/run.js` `analyzeRepo` (~line 166): it polls
`list_sessions` and takes the first session whose status is `ready`/`done` — a row that exists
before its graph is populated — while the `analyze` call itself has only the file's shared 45s
timeout, whose catch substitutes `{ handle, status: "ready" }`. So it interrogates a live but
empty session and still ticks "[x] Unprompted flush". Snapshots are MVID-keyed, so every Core
edit invalidates all of them (PLAN.md §4 says cold re-analyses after a batch are expected) —
which means this fires on the **first battery run of every session that touches Core**, and a
genuine 0/12 regression would be indistinguishable from it.

Filed as tracked bug #1 with the fix (gate the poll on a graph actually existing, and give the
cold `analyze` its own timeout). **Not fixed here** — it is a gate, outside G1.1's scope, and it
wants its own commit. Explicitly NOT "fixed" by pre-warming the snapshot, which would hide the
race rather than remove it.
