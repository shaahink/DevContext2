Not "the audit says it is missing" — read from source before editing:

| Layer | What existed | What did not |

## 1. What landed

**Engine** — `GraphQuery.Seam(from, to, maxDepth = 8, maxPaths = 3)` (`src/DevContext.Core/Graph/GraphQuery.cs`).
BFS over rolled out-edges collecting every shortest-path predecessor, then the paths are read back
off that DAG. `SeamDirection` / `SeamHop` / `SeamPath` / `SeamResult` are the return types.

**Contract** — `rpc GetSeam(SeamRequest) returns (SeamResponse)` with `SeamPath` / `SeamHop`
(`proto/devcontext/v1/devcontext.proto`), regenerated into `DevContext.Contracts` and the app's
`devcontext_pb.ts` (`pnpm gen:proto`, exit 0).

**Server** — `DevContextGrpcService.GetSeam` resolves both ends through the same `ResolveNode` every
other node-taking RPC uses; `ProtoMapper.ToSeamResponse` maps the result and builds the note.

**Tool** — `seam(handle, from, to, maxDepth, maxPaths)` in `DevContextTools.cs`. Because G2.1 made
the menu and the did-you-mean list one fact, adding the method was the whole registration:
`tools/list` and `UnknownToolHandler` both picked it up with no second edit.

### Three decisions, stated rather than assumed

1. **Shortest paths only**, which is a definition and not a hedge — it is the one answer that is
   well-defined, bounded and stable. `totalPaths` is the **exact** number of shortest paths, counted
   over the search DAG rather than by enumerating them, so "showing 1 of 10" is a fact.
2. **The reverse direction is searched before answering "no".** "B reaches A in 3 hops" and "these
   two are unconnected" are different facts and the second is the one an agent would act on wrongly.
3. **A depth-capped search says so.** "No path within 8 hops" is not "no path", and the note names
   the retry that would work (`maxDepth: 16`).

## 2. The check that discriminates — watched going RED

The vacuous check here is *"seam returned a path"*: a direct-edge BFS returns paths too, and on the
shape that matters it returns the wrong answer confidently. **After Batch A almost no wiring hangs
off a Type node** — it hangs off its members — so a Type→Type seam over direct edges answers
*unconnected* about two types that call each other on every request.

So the implementation was run with `_graph.OutEdges(node)` in place of `RolledEdges(node, Out)` and
the new tests were run against it:

```

  A_connection_that_runs_the_other_way_is_reported_as_reverse  Expected: Reverse  Actual: None
  Every_hop_names_its_seam_kind_resolution_and_site        Assert.Single() Failure: collection was empty
```

**Six of the nine tests passed on the broken implementation.** That is the point of recording it:
those six do not discriminate, and a suite made only of those would have shipped an engine that says
two collaborating types are unconnected.

With the roll-up restored: `eval-results/2026-07-29/g3.1-seam-GREEN-rolled.txt` — **9/9 passed**.

The second invariant, from G1.4's lesson (*a number that moves with the page size is describing the
page*): `The_shortest_path_length_does_not_move_when_maxPaths_moves`, plus the same check on the
real repo below.

## 3. The real-repo drive — three tools have to agree

`eval/mcp-qa/drive-r4.js seam` → `eval-results/2026-07-29/mcp-r4-g31/` (real MCP calls over stdio,
raw responses dumped). Nothing here trusts `seam` on its own:

- the pair is **chosen by `impact`**, which already knows how far apart the two ends are, so seam
  cannot define its own success;
- every hop of the route is then **confirmed against `neighbors`** on that hop's own source node.

```
case: seam
  PASS  tools/list advertises seam — 22 tools
  PASS  analyze eShop
  PASS  found a connected pair via impact — Order -> OrderingContext.FindAsync at 4 hops
  PASS  seam finds the path impact already knew about
  PASS  direction is stated — forward
  PASS  hop count agrees with impact exactly — seam=4 impact=4
  PASS  the path has that many hops — 4 rows for 4 hops
  PASS  the route ends on the requested target
  PASS  every hop is an edge neighbors also reports — 4/4 confirmed
  PASS  every hop carries a seam kind and a resolution — Raises/Semantic Handles/Join Calls/Syntactic Calls/Syntactic
  route: SetAwaitingValidationStatus -[Raises]-> OrderStatusChangedToAwaitingValidationDomainEvent
         OrderStatusChangedToAwaitingValidationDomainEvent -[Handles]-> OrderStatusChangedToAwaitingValidationDomainEventHandler
         Handle -[Calls]-> GetAsync
         GetAsync -[Calls]-> OrderingContext.FindAsync
  PASS  hop count does not move with maxPaths — 4 vs 4
  PASS  totalPaths does not move with maxPaths — 10 vs 10
  PASS  the page says it is a page — totalPaths=10 note=Showing 1 of 10 shortest paths; ...
  PASS  a depth-capped search does not claim there is no path — No path within 1 hop, in either
        direction — the search stopped at the depth limit with unexplored nodes left. Retry with maxDepth: 2.
  PASS  an unresolved end says so instead of denying the path — 'Zzz_NoSuchSymbol_Zzz' did not
        resolve to a node — not the same as no path.
```

That route is the argument for the primitive: **four hops, three different seam kinds, each with a
file:line** — an aggregate raises a domain event, the event is handled, the handler reads the store.
No tool in the product could produce it before.

Artifacts: `seam-eshop.json` · `seam-eshop-maxpaths.json` · `seam-eshop-depthlimit.json` ·
`seam-eshop-unresolved.json` · `seam-drive.txt`.

### The driver was wrong once, and the engine was right

First run: `FAIL hop count agrees with impact exactly — seam=3 impact=4`. Read from the raw
response rather than explained away: the route's last hop landed on
`Member:…OrderingIntegrationEventService::AddAndSaveEventAsync` — a **member** of the requested
Type — at 3 hops, while impact had reached the **bare Type node** at 4. Both are right under their
own question: seam's roll-up says arriving at any member of a target Type is arriving at the type
(which is the only reason a Type→Type seam works at all), and impact reports the distance to
whatever node it reached. **An exact equality between them on a Type target is a wrong premise, not
a defect.** The driver now picks a **Member** target, where there is no roll-up and the equality is
exact — and gained a check the first version lacked: *the route ends on the requested target*.

Fourth occurrence of "my ground truth was wrong and the code was right" in this program.

## 6. Not in scope, deliberately

- **Kind-filtered `neighbors` (G3.2)** and **snapshot-cache truth (G3.3)** are separate checkpoints.
  `seam` takes no kind filter; that is G3.2's question, and pushing it in here would have coupled two
  contract changes.
- **No CLI `query seam` op.** The checkpoint says proto + GraphQuery + tool, and `GraphQuery.Seam` is
  the shared implementation, so a CLI op is a rendering decision that can land whenever it is wanted.
