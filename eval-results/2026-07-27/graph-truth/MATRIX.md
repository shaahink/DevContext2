## Probe answers (S1 step 5)

### DC3 -- eShop gRPC client registration: which detection fires?

**Answer: no gRPC detection fires; the registration is captured only as a junk-shaped generic
DI detection.** Two independent misses:

1. **Registration site is gRPC-blind.** `WebApp/Extensions/Extensions.cs:31` registers
   `AddGrpcClient<Basket.BasketClient>(o => o.Address = new("http://basket-api"))`.
   `GrpcClientExtractor` (`Extractors/Specific/GrpcClientExtractor.cs`) never looks at
   registrations at all -- it only scans **constructor parameters**. The registration falls
   through to `DiRegistrationExtractor`'s generic `Add*` branch
   (`DiRegistrationExtractor.cs:161-188`), producing
   `DiRegistrationDetection(ServiceType: "AddGrpcClient", ImplementationType: "o => o.Address = ...")`
   -- the generic type argument `Basket.BasketClient` is **never read** (the branch prefers
   `args[0]`, the lambda, and only falls back to type args when there are no arguments).
2. **Injection site is alias-blind.** The consumer `WebApp/Services/BasketService.cs:7` primary-ctor
   injects the client as `GrpcBasketClient` via
   `using GrpcBasketClient = eShop.Basket.API.Grpc.Basket.BasketClient;` (line 3).
   `GrpcClientExtractor.IsGrpcClientType` requires a **dotted** `X.XClient` syntax string
   (`GrpcClientExtractor.cs:77-89`); the unqualified alias has no dot and is rejected. Syntax-only
   matching cannot see through the alias -- semantic resolution would.

Net: zero `GrpcClientDetection`s in eShop, so `AddGrpcServiceLinks`
(`GraphBuilder.ServiceLinks.cs:24`) has no client side to join with the detected Basket gRPC
*server* entries -> `grpc=0` ServiceLinks (transport cell RED). Batch B item 1 fix shape: read the
`AddGrpcClient<T>` type argument at the registration site as a first-class client detection, and
resolve injection-site types semantically (rides Batch A's single compilation) instead of by
syntax-string shape.

### DC8 -- GitVersion command framework: why does F10 see 1 command?

**Answer: both of GitVersion's CLIs are invisible to class-based command detection; the 1 command
is the B4 Main-method fallback.**

- The analysis scope swallows both sln trees (36 "projects" incl. both `src/` and `new-cli/` plus
  the Cake build projects -- see DC6 note below).
- **Legacy CLI (`src/GitVersion.App`) has no command classes at all**: verbs are parsed by a
  hand-rolled `ArgumentParser` (`IArgumentParser`/`ArgumentParser.cs`); there is nothing shaped
  like `Command<T>` to detect. Its only detection is the B4 fallback Main entry
  (`CliCommandExtractor.AddMainEntryFallbackAsync`) -- **that is the "1 command"**.
- **New CLI (`new-cli/`) commands exist but are deliberately not matched**: `OutputCommand`,
  `ConfigCommand`, etc. implement GitVersion's **own** `ICommand<T>`
  (`new-cli/GitVersion.Common.Command/ICommand.cs`) and are marked with GitVersion's **own**
  `[Command("output", ...)]` attribute (`CommandAttribute.cs`), with a source generator emitting
  the System.CommandLine wiring at build time. `CliCommandExtractor` E7 policy refuses
  ICommand-ish interfaces (WPF collision) and requires a `using System.CommandLine` for bare
  `Command` bases -- neither holds in these files -> zero detections.

Fix shape (Batch B item 3): detect the `[Command("name", ...)]` **attribute pattern**
(attribute-with-route-string is strong, framework-agnostic evidence, same family as endpoint
attributes), rather than widening the ICommand net (E7's reasons remain valid).
