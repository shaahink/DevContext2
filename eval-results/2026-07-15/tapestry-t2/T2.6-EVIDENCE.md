# T2.6 — One event join to rule them all (audit A10)

**Branch:** feat/tapestry-t2 · **Date:** 2026-07-15

## What shipped

One authoritative publisher→event→consumer projection (`EventWiringProjection`, stored on
`CodeGraph.EventWiring`), built once from the graph's `Raises` (publisher→event) and `Consumes`
(event→consumer) seams. Three surfaces now render from that single projection instead of three
independent joins:

- **(a) Event board** — `EventFlowSource` insight (`wiring.event-flow`) reads `graph.EventWiring`.
- **(b) One-pager / overview** — a new `EVENT WIRING` section in `MapRenderer` + the existing
  `CROSS-SERVICE` ServiceLink section, both fed by the projection.
- **(c) Flow cross-service markers** — the bus `ServiceLink` edges are now **emitted from the
  projection** (`EventWiringProjection.EmitServiceLinks`), with provenance anchored at the
  publishing member (audit A10c), so the flow spine's `ServiceHop`s and the pack `Cross-service:`
  line derive from the same join.

The legacy project-name join (`GraphBuilder.AddBusServiceLinks`, ~65 lines) and its
`_eventPublishers` scratch dictionary are **deleted** — there is exactly one join now.

### The join key (anti-overfit)

eShop declares each integration event **twice** — a publisher copy (`eShop.Ordering.API…OrderStarted`)
and a consumer copy (`eShop.Basket.API…OrderStarted`) in different namespaces — so the two never
share a node id. The projection keys on the **short type name within the model's detected event set**
(events reached by a Raises/Consumes seam), not arbitrary substring text. Base marker types
(`IntegrationEvent`, `DomainEvent`, …) are excluded. Domain events that cross a *layer project*
boundary inside one service (`Ordering.Domain → Ordering.API`) are **not** cross-service — only
integration events cross a service boundary.
