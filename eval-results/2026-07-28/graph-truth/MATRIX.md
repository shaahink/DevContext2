## Batch B scope decisions (what was built, and what was deliberately not)

R2 sec 2.B lists four items. What landed, in its own words, and where a line was drawn:

1. **Transport client links — built.** `AddGrpcClient<T>`, typed `AddHttpClient<T>` (and
   `<TInterface, TImpl>`), `AddRefitClient<T>`, each with the address the registration configured,
   including addresses set on a chained `.ConfigureHttpClient(...)`. Addresses resolve through the
   AppHost resource table first, then a normalized project-name match, so repos with no Aspire still
   join. The injection-site half of the DC3 answer is fixed too: file-local `using` aliases are
   expanded before the `X.XClient` shape test, which is what hid eShop's `GrpcBasketClient`.
   - **External targets are emitted only where the repo names an ADDRESS** that resolves to nothing
     in the solution. A client TYPE name is not evidence of an external deployment, so an injected
     client with no registration and no in-solution server still produces nothing. This matters for
     the gRPC pole: inventing an external node from the client type would have turned its RED
     transport cell green while the actual defect (its examples are out of analysis scope) survived
     untouched. A cell that goes green for the wrong reason is worse than a RED one.
   - **Refit joins by ADDRESS, not by route.** Matching Refit route templates against downstream
     endpoint routes with no gateway config to anchor them is guesswork; the registration's address
     is a fact. Route-based Refit joins stay gateway-only.
2. **Aspire topology — built.** Project-to-project references become ServiceLinks; infrastructure
   resources become Store nodes with `RoleTags.DataStore`, hanging off the services that reference
   them via `DependsOn` edges. Both vocabularies existed and were never produced until now.
   - The relationship DIRECTION was wrong at the source: `WithReference`'s arguments name only the
     TARGET, and the old code read args[0] as the source and args[1] as the target, so every
     relationship pointed at "?". Fixing that is what makes the topology exist at all.
   - **"AppHost = orchestrator grouping" is NOT built.** Whether the AppHost renders as a grouping
     frame or a peer node is a canvas decision, and R3 owns canvas decisions. The facts it would
     need are now in the graph.
3. **CLI command tree — built as flat verbs.** `[Command("output", ...)]`-shaped attributes are
   detected framework-agnostically; the verb leads the entry title ("output (OutputCommand)").
   GitVersion's new-cli declares five flat verbs, so a flat entry list is faithful to it; nested
   subcommand trees are not modelled and no repo in the matrix needs one yet.
4. **`Channel<T>` in-proc seam — NOT built (deferred).** R2 conditions this one on "if cheap".
   It is not: naming the producer and consumer of a channel means tracking writer/reader handles
   through BodyFacts, which is trace-seam work, not a transport link. Deferred to Batch C/D with
   this note rather than half-built.

a per-file whole-tree walk is invisible on fixtures and costs minutes at framework scale -- the
matrix's big poles caught what the unit tests could not.
