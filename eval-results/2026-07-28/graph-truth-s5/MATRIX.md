## Root causes established this session (per-edge evidence, from the raw dumps)

### `dup-name` (SignalR 12 · wolverine 4 · YARP 1 · +3 more the widen set added) — the METRIC is spent

Read from the S4/S5 raw dumps, every flagged pair has **distinct canonical ids**:

| pole | flagged pair | ids |
|---|---|---|
| SignalR | `CryptoUtil` | `Microsoft.AspNetCore.Cryptography.CryptoUtil` vs `Microsoft.AspNetCore.DataProtection.CryptoUtil` |
| SignalR | `HttpConnection` | `…Http.Connections.Client.HttpConnection` vs `…Server.Kestrel.Core.Internal.HttpConnection` |
| SignalR | `FromBodyAttribute` | `Microsoft.AspNetCore.Mvc.FromBodyAttribute` vs `…Routing.IdentityApiEndpointRouteBuilderExtensions.FromBodyAttribute` (a NESTED type — Batch A's nested-chain ids doing their job) |
| wolverine | `Account`, `DebitAccount`, … | `AppWithMiddleware.Account` vs `DocumentationSamples.Account` — each sample app defines its own |
| bitwarden-server | `ApiKeyRepository` ×99 | `Infrastructure.Dapper` vs `Infrastructure.EntityFramework` — TWO persistence implementations of one interface, which is the repo's architecture |
| MassTransit | `ScheduleMessageConsumer` | `MassTransit.HangfireIntegration` vs `MassTransit.QuartzIntegration` |

**Conclusion: the check's premise died in Batch A.** It groups nodes by short TITLE, which was a fair
proxy for identity confusion while node ids were short-name-based. Structural ids made homonyms in
different namespaces genuinely distinct, so what the check now counts is *how many homonyms a repo
has* — a property of the repo (dual persistence, sample apps, framework-wide shared names), not a
defect in the engine. bitwarden's 99 is the proof: no engine is confused, the repo simply ships Dapper
and EF implementations side by side.

The check is therefore RE-POINTED (declared instrument change, applied after the post-Batch-D run so
that run stays internally consistent) at what can still go wrong: **a homonym joined by a
cross-project `ServiceLink`** — the original DC2n complaint, "dup-name CrossService noise". Calls and
Resolves edges between correctly-distinct homonyms are not evidence of anything.

### `wolverine` handler-join (`Envelope`) — ACCEPTED LIMITATION, not relaxed

All six `Sends → Envelope` edges originate inside Wolverine's own transport layer:
`Wolverine.Transports.Sending.InlineSendingAgent::sendWithTracing`,
`…SendingAgent::sendWithCallbackHandlingAsync`,
`Wolverine.AzureServiceBus.Internal.InlineAzureServiceBusListener::MoveToScheduledUntilAsync`,
`Wolverine.Nats.Internal.NatsListener::MoveToErrorsAsync` (+2). Every one is `Semantic`.

In an APPLICATION, `bus.SendAsync(x)` means x is dispatched and something handles it. In the repo that
IMPLEMENTS the bus, the same call is the transport handing an envelope to a wire — and `Envelope` is
the wrapper, not a request. The engine cannot tell those apart without knowing that Wolverine is
Wolverine, and a name deny-list for "Envelope" is exactly the overfit Batch A deleted. Recorded as a
limitation; the expectation stays pinned at `unhandled = 1`.

### `CleanArchitecture` handler-join (5) — ROOT-CAUSED AND FIXED in Batch E

The five unhandled requests are the template's own Create/Delete/Update/Get/List Contributor set.
Their handlers implement `Ardalis.SharedKernel.ICommandHandler<,>`, which derives from MediatR's
`IRequestHandler<,>` **inside a NuGet package**. The transitive interface walk can only follow
declarations that exist in the model, so it stops at the package boundary. Batch E adds a shape-based
fallback that needs TWO independent structural facts — the class implements `…Handler<T, …>` AND has a
`Handle`/`HandleAsync` method whose first parameter is `T` — so no name list is involved.

### NEW from the widen set: archetype loses to an auxiliary executable

- `CLI` (dotnet/command-line-api) reads **CliTool**; it is a LIBRARY for building CLIs whose exes are
  samples and tests.
- `MahApps.Metro` reads **Desktop**; it is a WPF CONTROL LIBRARY whose WinExe is its demo.

One root cause: when a repo ships both a packable library and an auxiliary executable that isn't under
a `samples/` path, the executable decides. Not fixed in S5 — declared as the first item of evidence for
