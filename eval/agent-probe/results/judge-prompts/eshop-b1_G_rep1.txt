## QUESTION PUT TO THE ENGINEER
A customer submits the checkout form in the web storefront. Follow that all the way to the line of code that writes the order to the database, and name the handlers involved in order.

## ANSWER KEY (verified ground truth)
Checkout.razor's HandleSubmitAsync validates and calls HandleValidSubmitAsync, which calls BasketState.CheckoutAsync (src/WebApp/Services/BasketState.cs:78). CheckoutAsync resolves the buyer id and user name, fetches the basket items, builds a CreateOrderRequest and calls OrderingService.CreateOrder (src/WebApp/Services/OrderingService.cs), which POSTs to /api/Orders/ with an x-requestid header - this is the process boundary, WebApp to Ordering.API. In Ordering.API the route is registered in OrdersApi.MapOrdersApiV1 as api.MapPost("/", CreateOrderAsync) on the group "api/orders". OrdersApi.CreateOrderAsync (src/Ordering.API/Apis/OrdersApi.cs:118) builds a CreateOrderCommand, wraps it in IdentifiedCommand<CreateOrderCommand, bool> for idempotency and sends THAT through MediatR. The wrapper is handled by CreateOrderIdentifiedCommandHandler (in CreateOrderCommandHandler.cs), which inherits IdentifiedCommandHandler and, if the request id has not been seen, re-sends the inner CreateOrderCommand through the mediator. That reaches CreateOrderCommandHandler.Handle, which adds an OrderStartedIntegrationEvent to the outbox, builds the Order aggregate (Address, Order ctor, AddOrderItem per line), calls _orderRepository.Add(order) and finally _orderRepository.UnitOfWork.SaveEntitiesAsync - implemented on OrderingContext (src/Ordering.Infrastructure/OrderingContext.cs:47), which is the EF Core save that persists the order. The two grep-hostile hops are the HTTP boundary and the MediatR IdentifiedCommand indirection: nothing textually links CreateOrderAsync to CreateOrderCommandHandler.

Elements a complete answer names: `CheckoutAsync`, `OrderingService`, `CreateOrderAsync`, `CreateOrderIdentifiedCommandHandler`, `CreateOrderCommandHandler`, `IOrderRepository`, `OrderingContext`

## Caveats

- The `CreateOrderCommandHandler` also writes an integration-event row (`OrderStartedIntegrationEvent`) via `_orderingIntegrationEventService.AddAndSaveEventAsync` before the order is built — `src/Ordering.API/Application/Commands/CreateOrderCommandHandler.cs:32-33`. That is a database write, but to the integration event log, not the `Orders` table.
- Because the buyer domain-event handler calls `SaveEntitiesAsync` first (`...WhenOrderStartedDomainEventHandler.cs:47-48`), the physical `SaveChangesAsync` that first flushes the pending `Order` insert is actually the *nested* invocation from that handler; the outer call at `OrderingContext.cs:59` then commits anything remaining. Both go through the same line 59.
- The checkout page is server-rendered with `Enhance`d form posting, so the submit is an HTTP POST back to the same Blazor circuit/endpoint rather than a separate API controller — I found no separate MVC/minimal-API checkout endpoint in `WebApp`.
