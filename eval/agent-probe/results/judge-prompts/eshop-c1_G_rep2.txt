## Answer

**Nothing constructs `CreateOrderCommandHandler` directly except one unit test** — every production path reaches it through MediatR — but its side effects fan out to Basket.API, WebApp, OrderProcessor and the rest of the order saga. Full dependency map below.

### 1. Direct invocation path (in-process)

- The handler is registered only by MediatR assembly scanning: `src/Ordering.API/Extensions/Extensions.cs:35-37`. There is no explicit DI registration and no subclass of it (`CreateOrderIdentifiedCommandHandler` at `src/Ordering.API/Application/Commands/CreateOrderCommandHandler.cs:57` derives from `IdentifiedCommandHandler`, not from it).
- `IdentifiedCommandHandler<CreateOrderCommand,bool>.Handle` re-sends the inner command through the mediator, which is what actually reaches `CreateOrderCommandHandler` (`src/Ordering.API/Application/Commands/IdentifiedCommandHandler.cs:39-104`, dispatch at `:87`; it special-cases `CreateOrderCommand` for logging at `:58-61`). Note `:99-102` swallows *any* exception and returns `default` (false).
- The only sender of that identified command is the HTTP endpoint `POST api/orders`: `src/Ordering.API/Apis/OrdersApi.cs:17` (route), `:141-146` (command construction, incl. the card-number masking at `:140`), `:155` (send). The endpoint returns `Ok()` even when the handler returns false (`:157-166`).
- MediatR pipeline behaviours that wrap every invocation: `LoggingBehavior`, `ValidatorBehavior`, `TransactionBehavior` (`src/Ordering.API/Extensions/Extensions.cs:39-41`). `TransactionBehavior` opens the DB transaction, commits it, and only then publishes the queued integration events (`src/Ordering.API/Application/Behaviors/TransactionBehavior.cs:38-52`) — the handler runs *inside* that transaction.
- `CreateOrderCommandValidator` runs before the handler and enforces address/card/order-item rules (`src/Ordering.API/Application/Validations/CreateOrderCommandValidator.cs:2-32`, registered at `src/Ordering.API/Extensions/Extensions.cs:45`); `IdentifiedCommandValidator` validates the wrapper (`src/Ordering.API/Application/Validations/IdentifiedCommandValidator.cs`).

### 2. HTTP callers of that endpoint (outside Ordering.API)

- **WebApp** checkout: `src/WebApp/Components/Pages/Checkout/Checkout.razor:114` → `BasketState.CheckoutAsync` builds `CreateOrderRequest` and calls `OrderingService.CreateOrder` (`src/WebApp/Services/BasketState.cs:78-108`), which POSTs with the `x-requestid` header (`src/WebApp/Services/OrderingService.cs:12-18`). Its local `CreateOrderRequest` record (`src/WebApp/Services/BasketState.cs:158-172`) must stay shape-compatible with `src/Ordering.API/Apis/OrdersApi.cs:171-185`. Note WebApp deletes the basket itself right after (`BasketState.cs:108`).
- **ClientApp (MAUI)**: `src/ClientApp/Services/Order/OrderService.cs:13,28-40` POSTs to `api/orders` with `x-requestid`; called from `src/ClientApp/ViewModels/CheckoutViewModel.cs:112`.
- **AppHost/YARP** routes `/api/orders/{*any}` to Ordering.API (`src/eShop.AppHost/Extensions.cs:243`), so any gateway client is affected.

### 3. Side effects other services depend on

- **`OrderStartedIntegrationEvent`** is enqueued by the handler (`CreateOrderCommandHandler.cs:32-33`) and published post-commit. **Basket.API subscribes to it and deletes the user's basket** (`src/Basket.API/Extensions/Extensions.cs:19`, `src/Basket.API/IntegrationEvents/EventHandling/OrderStartedIntegrationEventHandler.cs:10-15`). Removing/renaming/changing `UserId` breaks basket clearing.
- **`OrderStartedDomainEvent`** is raised by the `Order` constructor the handler calls (`src/Ordering.Domain/AggregatesModel/OrderAggregate/Order.cs:52-65`) and dispatched by `SaveEntitiesAsync` (`src/Ordering.Infrastructure/OrderingContext.cs:47-62`, called at `CreateOrderCommandHandler.cs:51`). Its handler creates/updates the **Buyer + payment method** and emits `OrderStatusChangedToSubmittedIntegrationEvent` (`src/Ordering.API/Application/DomainEventHandlers/ValidateOrAddBuyerAggregateWhenOrderStartedDomainEventHandler.cs:20-52`). That file already carries a warning (`:31-32`) that the ordering only works "by coincidence" — timing changes here are fragile.
- **WebApp** subscribes to `OrderStatusChangedToSubmittedIntegrationEvent` and pushes a live order-status notification to the buyer (`src/WebApp/Extensions/Extensions.cs:50`, `src/WebApp/Services/OrderStatus/IntegrationEvents/EventHandling/OrderStatusChangedToSubmittedIntegrationEventHandler.cs:10-14`) — it keys off `BuyerIdentityGuid`.
- **OrderProcessor** polls the ordering database directly with raw SQL for rows where `"OrderStatus" = 'Submitted'` and `OrderDate` older than the grace period, then publishes `GracePeriodConfirmedIntegrationEvent` (`src/OrderProcessor/Services/GracePeriodManagerService.cs:63-74`, `:55-59`). If the handler stops persisting orders in `Submitted` state or changes `OrderDate` semantics, orders silently never progress. This is a schema/data coupling, not a code reference.
- Indirect saga continuation (all triggered only because the order exists in `Submitted`): `GracePeriodConfirmedIntegrationEventHandler`, stock confirmed/rejected, payment succeeded/failed handlers in Ordering.API (`src/Ordering.API/Extensions/Extensions.cs:55-59`), Catalog.API stock validation, PaymentProcessor (`src/PaymentProcessor/IntegrationEvents/EventHandling/OrderStatusChangedToStockConfirmedIntegrationEventHandler.cs`), Webhooks.API (`src/Webhooks.API/IntegrationEvents/OrderStatusChangedToPaidIntegrationEventHandler.cs`, `...ToShippedIntegrationEventHandler.cs`), and the remaining WebApp status handlers.

### 4. Tests that will break

- `tests/Ordering.UnitTests/Application/NewOrderCommandHandlerTest.cs:41` constructs the handler with the exact 5-arg constructor `(IMediator, IOrderingIntegrationEventService, IOrderRepository, IIdentityService, ILogger)` and asserts `Handle` returns **false** when persistence is mocked out (`:43-46`). Any constructor or return-semantics change breaks this.
- `tests/Ordering.UnitTests/Application/IdentifiedCommandHandlerTest.cs:22,44,60-62` uses `CreateOrderCommand` as the wrapped command type.
- `tests/Ordering.UnitTests/Application/OrdersWebApiTest.cs:74` stubs `IdentifiedCommand<CreateOrderCommand,bool>`.
- `tests/Ordering.FunctionalTests/OrderingApiTests.cs:135-159` (`AddNewEmptyOrder` expects 400, `AddNewOrder` expects 200 end-to-end through the real handler).

### 5. Most likely breakage points

- **Constructor signature** — only the unit test binds to it; MediatR resolves the rest, so a DI change fails at runtime, not compile time.
- **Return value** — `false` is silently converted to `Ok()` by the API (`OrdersApi.cs:157-166`) and to `true` for duplicate requests (`CreateOrderCommandHandler.cs:67-70`), so a failure change may be invisible to callers.
- **Emitting/removing `OrderStartedIntegrationEvent`** — baskets stop being cleared server-side (WebApp also clears locally, MAUI does not).
- **Not constructing `Order` via its constructor** — no `OrderStartedDomainEvent`, so no Buyer/payment method row, no `OrderStatusChangedToSubmitted`, no WebApp notification.
- **Changing status/date on creation** — OrderProcessor's SQL polling stops picking the order up.
- **Doing work after `SaveEntitiesAsync`, or calling `AddAndSaveEventAsync` outside the transaction** — `AddAndSaveEventAsync` writes to the event log using the current transaction (`src/Ordering.API/Application/IntegrationEvents/OrderingIntegrationEventService.cs:36-41`) and `TransactionBehavior` publishes only events tagged with that transaction id (`TransactionBehavior.cs:52`).

Uncertainty: `IIdentityService` is injected but never used inside `Handle` (`CreateOrderCommandHandler.cs:10,22`), so it looks removable — but the unit test passes it positionally, so removing it requires editing that test.
