## Answer

The checkout submit ends at **`_ = await base.SaveChangesAsync(cancellationToken);`** in `src/Ordering.Infrastructure/OrderingContext.cs:59` — that is the line that writes the order rows to the database.

### The chain, in order

**1. WebApp (Blazor storefront)**
- The checkout form's `EditForm` posts to `HandleSubmitAsync`, which validates then calls `HandleValidSubmitAsync` (`src/WebApp/Components/Pages/Checkout/Checkout.razor:12`, `:101`, `:111`).
- `HandleValidSubmitAsync` calls `Basket.CheckoutAsync(Info)` (`src/WebApp/Components/Pages/Checkout/Checkout.razor:114`).
- `BasketState.CheckoutAsync` builds a `CreateOrderRequest` from the basket items and calls `orderingService.CreateOrder(request, checkoutInfo.RequestId)` (`src/WebApp/Services/BasketState.cs:78`, `:92-107`).
- `OrderingService.CreateOrder` issues `POST /api/Orders/` with an `x-requestid` header (`src/WebApp/Services/OrderingService.cs:13-19`).

**2. Ordering.API — HTTP endpoint**
- `POST api/orders` is mapped to `OrdersApi.CreateOrderAsync` (`src/Ordering.API/Apis/OrdersApi.cs:17`, `:118`).
- It masks the card number, builds a `CreateOrderCommand`, wraps it in `IdentifiedCommand<CreateOrderCommand, bool>` using the request id, and sends it via MediatR (`src/Ordering.API/Apis/OrdersApi.cs:141-155`).

**3. MediatR handlers, in the order they run**

**4. Persistence**
- `CreateOrderCommandHandler.Handle` calls `_orderRepository.Add(order)` → `_context.Orders.Add(order)` (an EF change-tracker add, not yet a DB write) (`src/Ordering.API/Application/Commands/CreateOrderCommandHandler.cs:49`, `src/Ordering.Infrastructure/Repositories/OrderRepository.cs:15-19`).
- Then `_orderRepository.UnitOfWork.SaveEntitiesAsync(cancellationToken)` (`src/Ordering.API/Application/Commands/CreateOrderCommandHandler.cs:51`) → `OrderingContext.SaveEntitiesAsync`, which first dispatches domain events (`src/Ordering.Infrastructure/OrderingContext.cs:55`, `src/Ordering.Infrastructure/MediatorExtension.cs:5-19`) and then **writes to the database at `src/Ordering.Infrastructure/OrderingContext.cs:59`**.
- The surrounding transaction is committed afterwards by `TransactionBehavior` (`src/Ordering.API/Application/Behaviors/TransactionBehavior.cs:47`).

### Caveats
- The `OrderStartedDomainEvent` that triggers handler #6 is raised in the `Order` constructor (`src/Ordering.Domain/AggregatesModel/OrderAggregate/Order.cs:63`, `:170-173`), so it is dispatched as part of the same `SaveEntitiesAsync` call — it runs *before* the write, not after.
- I did not trace the MediatR open-behavior ordering beyond the registration order in `Extensions.cs:39-41`; MediatR executes open behaviors in registration order, so Logging → Validator → Transaction is the expected order, but that is inferred from the library's semantics rather than from code in this repository.
- The mobile client (`src/ClientApp`) has its own separate `CheckoutViewModel.CheckoutAsync`; I ignored it since the question asks about the web storefront.
