## Answer

Nothing calls `CreateOrderCommandHandler` directly — it is reached only through MediatR, from exactly one entry point (HTTP `POST /api/orders/`), but its side effects fan out into Basket.API, WebApp, OrderProcessor and the rest of the ordering saga. Below is everything I found that depends on it.

### 1. How it is invoked (in-process, Ordering.API)

- It is bound to `CreateOrderCommand` purely by the MediatR contract `IRequestHandler<CreateOrderCommand, bool>` — `src/Ordering.API/Application/Commands/CreateOrderCommandHandler.cs:6`. There are no direct `new CreateOrderCommandHandler(...)` call sites; changing the constructor signature only affects DI (registered by MediatR assembly scan at `src/Ordering.API/Extensions/Extensions.cs:35`).
- `CreateOrderIdentifiedCommandHandler` — the idempotency wrapper, declared in the same file at `src/Ordering.API/Application/Commands/CreateOrderCommandHandler.cs:56` (`: IdentifiedCommandHandler<CreateOrderCommand, bool>`). It re-sends the inner command via mediator and, on duplicate `x-requestid`, short-circuits with `CreateResultForDuplicateRequest()` (`src/Ordering.API/Application/Commands/IdentifiedCommandHandler.cs`, idempotency store `src/Ordering.Infrastructure/Idempotency/RequestManager.cs`). If you change the handler's return semantics (`bool`), the duplicate-request result and the API's success/failure mapping change with it.
- `OrdersApi.CreateOrderAsync` — the only sender, wrapping the command in `IdentifiedCommand<CreateOrderCommand, bool>` and returning `Ok`/`BadRequest` based on the `bool` — `src/Ordering.API/Apis/OrdersApi.cs:118` and `src/Ordering.API/Apis/OrdersApi.cs:115` (`services.Mediator.Send(command)`); route `POST /api/orders/`.
- MediatR pipeline behaviours that wrap every send of this command (`src/Ordering.API/Extensions/Extensions.cs:35`): `LoggingBehavior`, `ValidatorBehavior` and `TransactionBehavior` (`src/Ordering.API/Application/Behaviors/TransactionBehavior.cs:5`). `TransactionBehavior` owns the transaction and publishes the integration events the handler queued, so changing where/whether the handler saves (`SaveEntitiesAsync`) can break commit/publish ordering.
- `CreateOrderCommandValidator` — `src/Ordering.API/Application/Validations/CreateOrderCommandValidator.cs:2`; any change to required fields on the command must stay consistent with it.

### 3. Downstream effects outside Ordering.API (the real blast radius)

- **Basket.API** — the handler raises `OrderStartedIntegrationEvent` (`src/Ordering.API/Application/Commands/CreateOrderCommandHandler.cs:32`), consumed by `OrderStartedIntegrationEventHandler`, which **deletes the user's basket** (`src/Basket.API/IntegrationEvents/EventHandling/OrderStartedIntegrationEventHandler.cs:6`, delete at `:15`). If you stop raising it, or change `UserId`, baskets are never cleared after checkout.
- **Ordering.API domain-event chain** — the `new Order(...)` in the handler raises `OrderStartedDomainEvent`, handled by `ValidateOrAddBuyerAggregateWhenOrderStartedDomainEventHandler` (`src/Ordering.API/Application/DomainEventHandlers/ValidateOrAddBuyerAggregateWhenOrderStartedDomainEventHandler.cs:3`), which creates/verifies the `Buyer` and payment method (`:23`, `:34`, `:44`, `:47`) and raises `OrderStatusChangedToSubmittedIntegrationEvent` (`:50`–`:51`). `UpdateOrderWhenBuyerAndPaymentMethodVerifiedDomainEventHandler` (`src/Ordering.API/Application/DomainEventHandlers/UpdateOrderWhenBuyerAndPaymentMethodVerifiedDomainEventHandler.cs:3`, order lookup at `:21`) then updates the order with the buyer/payment method — it fires off `Buyer.VerifyOrAddPaymentMethod`, so it is part of the same create-order transaction.
- **WebApp (real-time order status)** — `OrderStatusChangedToSubmittedIntegrationEventHandler` notifies the user's UI (`src/WebApp/Services/OrderStatus/IntegrationEvents/EventHandling/OrderStatusChangedToSubmittedIntegrationEventHandler.cs:5`, `:13`).
- **OrderProcessor** — `GracePeriodManagerService` polls the ordering database for orders past their grace period and publishes `GracePeriodConfirmedIntegrationEvent` (`src/OrderProcessor/Services/GracePeriodManagerService.cs:8`, publish at `:55` via `CheckConfirmedGracePeriodOrders`). It reads the rows this handler writes over raw SQL/Npgsql, not through Ordering's model, so changes to the order's initial status or to the persisted schema/timestamps break it silently. (I read lines 1–65; the SQL itself is at `:63`–`:95` and I did not read it, so I cannot state its exact predicate.)
- **The rest of the saga is downstream of that**: `GracePeriodConfirmedIntegrationEventHandler` (`src/Ordering.API/Application/IntegrationEvents/EventHandling/GracePeriodConfirmedIntegrationEventHandler.cs:3`) → `OrderStatusChangedToAwaitingValidationIntegrationEvent` → **Catalog.API** stock check (`src/Catalog.API/IntegrationEvents/EventHandling/OrderStatusChangedToAwaitingValidationIntegrationEventHandler.cs:3`) → `OrderStockConfirmed/Rejected` back to Ordering.API → **PaymentProcessor** (`src/PaymentProcessor/IntegrationEvents/EventHandling/OrderStatusChangedToStockConfirmedIntegrationEventHandler.cs:3`) → paid/shipped events consumed by **Webhooks.API** (`src/Webhooks.API/IntegrationEvents/OrderStatusChangedToPaidIntegrationEventHandler.cs`, `.../OrderStatusChangedToShippedIntegrationEventHandler.cs`) and **WebApp**. These only depend on an order existing in the expected initial state, but they are what fails if creation semantics change.
