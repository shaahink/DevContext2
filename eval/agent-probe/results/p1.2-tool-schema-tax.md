## The statistic DESIGN 4.4 names, and why it reads near zero here

Taken literally - turn-1 `input_tokens + cache_creation_input_tokens`, arm B minus arm G -
the answer on rep 1 is **9 tokens**. That number is not the tax.

The prompt cache is server-side and keyed by prefix. These runs carry the same system
prompt and the same tool schemas as the pilot runs recorded half an hour earlier, so the
schemas arrived as `cache_read` (6396 tokens in arm B) rather than as
`cache_creation` (236). The tokens are still being carried and still
being billed - at 0.1x instead of 2x - but the statistic cannot see them. DESIGN 4.4's
quantity measures the tax only when the prefix is cold, and it does not say how to
guarantee that. Reporting 9 tokens would be reporting a cache state, not a cost.

## The headline number

**Tool-schema tax = 2540 tokens of turn-1 context**, arm B minus arm G, measured as
the whole turn-1 prefix (`input + cache_creation + cache_read`), which is what the model was
charged for however it arrived. Same two runs, same trivial prompt, cache-state invariant.
That covers 22 MCP tool schemas plus whatever else the MCP connection adds to
the preamble - about 115 tokens per tool if it is all schema. It is charged to the arm either
way, so the delta is the quantity the experiment needs, not the schema bytes on their own.

Priced on Opus 5 at the 1-hour cache-write rate (2x of $5/MTok): **$0.0254** the
first time a session pays it, then **$0.00127** re-read on every later turn of that session.
Median recorded pilot run cost is $0.6342 (n=3), so the cold write is
**4.0%** of one run and each subsequent turn adds another
0.20%.

It hits short runs hardest, which is where class A and class F questions live - the case
DESIGN 4.4 says not to average away. It is also why the treatment arms start each question
already behind, and it belongs in the headline result, not in a footnote.

## Stability across reps

| rep | prefix state | DESIGN 4.4 stat | whole-prefix delta |
|---|---|---|---|
| 1 | warm (schemas arrived as cache_read) | 9 | 2540 |
| 2 | warm (schemas arrived as cache_read) | 231 | 2535 |

The invariant reading is stable to a handful of tokens across reps while the DESIGN
statistic swings with the cache. Rep 2 is the regime the 54-cell pilot lives in: back-to-back
runs sharing a warm prefix, paying the schemas at 0.1x rather than 2x. The pilot's own cost
numbers therefore include an amortised tax, not a cold one, and that is the honest reading
of them - it makes the treatment look better than a cold-start user would experience.

## Cold-cache cross-check, from the pilot runs already recorded

The three `eshop-a1` rep-1 runs in `results/raw/eShop/` each wrote their whole prefix:
`cache_read` is 0 on all of them, so for those runs DESIGN 4.4's statistic and the invariant
coincide. Their prompt is the eShop class-A question rather than the trivial one, but it is
byte-identical across arms, so the G-to-B delta is still the schema cost.

| arm | tools offered | turn-1 input | cache creation | cache read | in+create |
|---|---|---|---|---|---|
| G | 4 | 2 | 4161 | 0 | **4163** |
| M | 22 | 2 | 3318 | 0 | **3320** |
| B | 26 | 2 | 6692 | 0 | **6694** |

Cold delta B - G = **2531 tokens**, against 2540 from the trivial-prompt runs.
Two prompts, two cache states, one number to within a few tokens.

Arm M's turn-1 prefix is 3320 tokens - smaller than arm G's 4163 despite carrying
22 tool schemas, because arm M gets no `--add-dir` and so no directory preamble. That is why
the tax is measured G against B and not G against M.
