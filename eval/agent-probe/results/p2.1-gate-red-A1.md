# P2 gate RED - `A1-analyze-cached` fails on 9 arm-B runs

`node eval/agent-probe/verify.mjs --tier fast` is **RED** at the end of P2. This file states
exactly what is red, what is not, and why the assertion was **not** edited to make it green.

## What is red

`audit-preflight.mjs` re-derives DESIGN section 8 pre-flight assertions 1-4 from the transcripts,
independently of the harness. Over the 54 recorded runs:

| Assertion | pass | fail | n/a |
|---|---|---|---|

All nine failures are the same assertion, the same arm, and the same message:

## What is NOT red, stated so nobody has to take it on trust

**Arm isolation held on all 54 runs.** A2, A3 and X pass 54/54. Probe rule 4 says a leak voids
every number collected; there was no leak. This red is not that.

**Cost accounting held on all 54 runs.** A4 passes 54/54.

**The MCP was up and offered in every one of the nine runs.** Each carries
`mcpToolsOffered: 22` and `mcpServers: [{name: devcontext, status: connected}]` at init. The
runs did not fail to reach the MCP - they were handed 22 devcontext tools and used none.

**Warmth is separately proven for the whole batch.** The pre-batch warm gate in `run-probe.mjs`
ran before any timed run and refuses to start otherwise
(`.conductor/bg-logs/probe-p2-pilot-20260811-000637128.log`, lines 3-5):

```
warm: analyzing C:\Code\DevContext2\eval-repos\eShop (cold pass may take minutes)
warm: pass 1 cached=true 2467ms
warm: pass 2 cached=true 519ms (fresh mcp process)
```

DESIGN 4.5's actual requirement is that no timed run pays for a cold analysis. A run that made
zero MCP calls made zero analyze calls and therefore cannot have paid for one.

## Why the red is a finding and not a fault

The nine failures are a mechanical consequence of a real, pre-registered check failing:

> DESIGN 3.1 manipulation check - arm B `mcp_call_share` must clear 0.20.
> **Measured: median 0.01, with 17 of 18 runs below 0.20.**

Given both toolsets, the agent reached for the MCP on classes A, B and C (2-4 calls per run
against 3-31 file calls) and **not once** on classes D, E and F - 0/3 reps each, three questions,
nine runs, no exceptions. `A1-analyze-cached` assumed an MCP-capable arm always calls `analyze`.
On half this question set, arm B does not.

## Why the assertion was not edited

Rewriting `A1-analyze-cached` to treat "MCP-capable arm, zero analyze calls" as n/a would turn the
gate green and would arguably be the technically correct predicate, since the cold-cost risk it
guards against is structurally absent in exactly those runs and the batch's warmth is proven above.

It was left alone anyway, for two reasons.

1. The zero-analyze case is not an oversight. Its failure message was written deliberately -
   *"arm has the MCP but the run never called analyze - warmth unproven from this transcript"* -
   by the P1 session, before any pilot data existed. It is a pre-registered bar.
2. Relaxing an assertion after seeing it go red is the one move this experiment cannot afford,
   whatever the justification. The credibility of the number is the product.

## The decision that is needed

Either (a) narrow `A1-analyze-cached` so an MCP-capable run with zero MCP calls is `n/a` with the
same structural reasoning already accepted for arm G, citing the pre-batch warm gate - the gate
then goes green and no recorded number changes; or (b) keep the assertion and treat the nine runs
as unusable, which would require re-running all of classes D, E and F **in all three arms** and
would almost certainly reproduce the same result, since the behaviour repeated 3/3 in every case.

Recommendation is (a), on the evidence above, but it is not this session's call to make.
