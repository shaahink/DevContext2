## Audit defects found and fixed (ratchet-only)

### Fixed
1. **Triple-brace bug in auto-extract fallback.**  
   `AddSeamsFromDetectors` auto-extract path generated synthetic source with 3 closing braces regardless of namespace-wrapping state, producing invalid C# for all cases. The try-catch at line 1352 silently swallowed the parse error, so this path produced zero BodyFacts. Fixed to compute correct closing braces per nsDecl.  
   → `GraphBuilder.cs:1338-1341` · Test: `Auto_extract_fallback_handles_stripped_type_body`

2. **Missing try-catch around detector loop in `AddSeamsFromDetectors`.**  
   The inner loop (`detector.Detect(body, ctx)`) had no exception handling. A single failing detector would crash the entire graph assembly. Added try-catch per detector iteration, consistent with the parse-failure handling already in the same method.  
   → `GraphBuilder.cs:1436-1507` · Test: `Detector_failure_is_isolated_and_does_not_crash_assembly`

3. **Missing try-catch around detector loop in `AddLambdaSeams`.**  
   Same pattern — detector failure inside the lambda-seam post-pass would crash. Outer try-catch at line 1620 only caught parse failures. Added per-detector try-catch parallel to the fix in `AddSeamsFromDetectors`.  
   → `GraphBuilder.cs:1576-1618`

## What is solid and proven

- **BodyFacts extraction** is structurally correct. `BodyFactExtractor.WalkMember` builds a member-local scope from fields, properties, primary-ctor params, member params, lambda params, and local declarations — all from the syntax tree (zero re-parsing). `InferInitializer` handles `new X()`, `.Adapt<T>()`/`.Map<T>()`/etc., awaited variants, and same-type method-return inference. String literals never enter the op stream (proven: `Raw_string_literal_containing_send_pattern_does_not_produce_fabricated_edge` in `PatternZooTests.cs`).
- **5 seam detectors are pure and well-tested.** Each reads `BodyFacts` + `SeamContext` and emits `SeamMatch` without mutating the graph. Verbatim dogfood snippets (`CheckoutEndpoint`, `CheckoutHandler`, `CheckoutConsumer`) exercise the flagship checkout spine E2E in `SeamDetectorTests.Checkout_spine_seams_detected_end_to_end`.
- **Regex funeral is complete.** All 18 body-scan regex methods physically deleted from `GraphBuilder.cs` (AddSends, AddRaises, AddDataEdges, StripStringLiterals, BuildAllMethodSpans, EstimateProvenance, ResolveVariable*, etc.). `loom-guards.ps1` bans `System.Text.RegularExpressions` in `Core/Graph/` — 0 banned patterns.
- **Assembler correctly anchors edges.** Every seam's `Origin` is the member that owns the body, resolved via `ToMemberNodeId` from `BodyFacts.Member`. Edges land on the correct member node by construction — no char-offset estimation.
- **Law R1 (no silent winners) is enforced.** `AddSeamsFromDetectors` skips matches whose `SymbolTable.Resolve` returns `ResolutionTier.Ambiguous`. This is the direct cause of the 396-node dogfood number (fewer fabricated edges) — a documented purity gain, not a regression.
- **Checkout trace depth 6 is proven.** `dogfood-l2-checkout-trace.md` shows: Entry → lambda → send CheckoutBasketCommand → handler → raises BasketCheckoutEvent → consumes BasketCheckoutEventHandler (cross-service hop) → send CreateOrderCommand.
- **BodyFacts cache is content-keyed** (`facts-v1` version tag) and populated once from the shared parse. `BodyFactExtractorTests.Body_facts_cache_builds_once_and_is_reused` proves the factory runs exactly once.
- **All 11 PatternZooTests pass** using the new BodyFacts pipeline (the old regex methods are unreachable). Tests exercise primary constructors, expression-bodied methods, records, local functions, required init properties, collection expressions, preprocessor conditionals, and string-literal exclusion.

## What is shortcut / weak / assumed / not fully covered

| Area | Severity | Detail |
|------|----------|--------|
| Lambda scope pollution in `BodyFactExtractor.WalkMember` | Low | All lambda parameters (including nested lambdas) are added to a single member-level scope dictionary. In methods with multiple lambdas, a parameter `x` in one sub-expression could incorrectly resolve a receiver in a different sub-expression. Typical usage patterns (single-lambda endpoint handlers, single-lambda in controllers) are unaffected. Not fixed — would require per-lambda scoping, proportional to effort. |
| `AddLambdaSeams` duplicates SeamContext building | Low | Lines 1529-1548 rebuild `integrationTypes` and `domainTypes` independently of `AddSeamsFromDetectors` (lines 1358-1423). The two paths could diverge over time. Acceptable — lambda seams are a separate concern with different scope (no entity data). |
| `AddLambdaSeams` doesn't populate `KnownEntities` | Low | The SeamContext for lambdas has `KnownEntities = ImmutableHashSet<string>.Empty` (default). `EntityTouchDetector` never fires for lambda seams. By design — minimal-API lambdas are thin entry handlers that don't touch entities directly. |
| `DomainEventRaiseDetector` allows `"Raise"` without domain event whitelist | Low | When `ctx.DomainEventTypes.IsEmpty`, the bare verb `"Raise"` matches any invocation named `Raise(...)` — could match non-domain-event raise patterns (e.g. `button.Raise(clickEvent)`). Confidence is 0.65f. Not fixed — heuristics are expected to carry confidence scores; the guard only triggers when classification data is available. |
| `BusPublishDetector` name hints include generic names | Low | `NameHints` set includes `"endpoint"` and `"session"` — common names that could match non-bus receivers. Mitigated by the typed-receiver path (`DispatchClassifier.IsBusReceiver`); name-only matches carry 0.5f confidence. |
| Auto-extract fallback never runs in production | Low | `DiscoveryPipeline.AnalyzeAsync` always passes `context.Analysis.AllBodyFacts` (even if empty). The auto-extract code path (lines 1324-1355) is only reached when `Build()` is called with `bodyFacts: null` — unit tests and ad-hoc callers only. The triple-brace bug was in this path; fixed but low production impact. |
| `InferInitializer` doesn't handle `.Result` / `.GetAwaiter().GetResult()` | Low | Synchronous blocking patterns (common in legacy code) are not unwrapped. Only `AwaitExpressionSyntax` is handled. |
| `SeamContext` is built from scratch twice per graph build | Low | `AddSeamsFromDetectors` scans all detections + types + graph nodes to build `SeamContext` (~70 lines), then `AddLambdaSeams` does a similar scan (~16 lines). Both run serially in `Build()`. Total time is negligible on current dogfood (2.3s), but O(n) over types + detections. |
| No test for concurrent `Build()` calls | Low | `_eventPublishers` is an instance field (de-static'd in L1), so concurrent instances are safe. But no test proves two `GraphBuilder.Build()` calls in parallel don't interfere via shared state (model/detections). |
| `SymbolRef.Text` is assumed non-null | Low | Downstream code uses `match.Target.Text` without null checking. `SymbolRef` is a record with `required string Text`, so null is structurally impossible. Fine. |
| `IdentifierUseOp` deduplication per body | Low | `seenIdentifiers` uses `StringComparer.Ordinal`. C# identifiers are case-sensitive, matching the runtime semantics. If a source file has inconsistent casing for entity names (rare), `EntityTouchDetector` could miss touches. |

## Risks the next phase (L3) should watch

1. **Purity gain ≠ correctness.** The dogfood numbers dropped from 493n/316e to 396n/236e — documented as the seam detectors being more conservative (no fabrication of edges for ambiguous/unresolved targets). L3 (SemanticLitePopulator) must recover real edges that the structured approach correctly withheld. The `[TruthPending]` assertions on checkout flow are resolved, but full truth-expectation file (L0.1 + L7.4) isn't wired yet.

2. **Semantic tier must populate `SymbolTable`.** `ResolutionTier.Semantic` exists in the enum but is never returned — only `Declared`, `ProjectScoped`, `GlobalUnique`, `Ambiguous`, and `Unresolved` are used. `SemanticLitePopulator` must add Roslyn-semantic entries to make `Semantic` tier functional.

3. **Lambda scope pollution may surface with complex handlers.** If L3 adds more sophisticated dispatch patterns that exercise multi-lambda methods (e.g., `.Select(x => ...).ForEachAsync(y => ...)`), the single-scope design in `BodyFactExtractor.WalkMember` could produce wrong receiver types. A deliberate test case for multi-lambda methods should be added.

4. **13 advisory `NodeId.ForType(` in `Graph/`** are tracked by `loom-guards.ps1` as L3 cleanup. Don't let them drift higher.

5. **`SeamContext` building may need extraction.** If L3 adds more seam detectors (e.g., for gRPC client dispatch, SignalR hub dispatch), the duplicated context-building logic will accrete. Consider extracting `SeamContext` population into a shared helper.
