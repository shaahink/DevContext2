## What is thin / shortcut / assumed (honest)

| Area | Honesty note |
|------|-------------|
| **F4 multi-exact branch has no unit test** | There is **no MCP test project** in `DevContext.slnx`, so `DevContextTools` (all 23 tools, the envelopes, F4's new branch, `UnknownToolHandler`) has **zero unit tests**. Everything is covered only by the two node QA harnesses driving the live server. F4's new branch is covered by reasoning + no-regression on the gates, not by a dedicated assertion. This is the single biggest coverage gap in L5. |
| **`UnknownToolHandler.ToolNames` is a hardcoded 23-name array** | It duplicates the `[McpServerTool]` methods on `DevContextTools`. Add/remove/rename a tool and the "did you mean" + `availableTools` list silently drifts. No guard test (see above). |
| **`WithCallToolHandler` + `WithTools` interaction is trusted, not asserted in isolation** | Correct behavior (known tools dispatch normally; unknown → fallback handler) is proven **only** empirically by scripted 8/8 + cold B1 under the same wiring. There is no test that pins "adding the fallback handler doesn't swallow real tools". If the SDK (`ModelContextProtocol` 1.4.0) changes this contract on upgrade, only the harnesses would catch it. |
| **Idempotency is check-then-act, unguarded** | `TryGetByRepo` then (on miss) `AnalyzeAsync` is not atomic. Two concurrent analyses of the same repo+HEAD both miss, both run the full analysis, both create sessions; the second wins the repo index and the first session lingers until eviction. Low probability under stdio/desktop (calls are serial), but idempotency is **not** concurrency-safe. Not fixed: a correct fix needs per-repoKey async locking, which is not a low-risk change on this hot path. |
| **`graph.Find` scans all nodes per query** | O(N) title/key contains + degree lookups for matched nodes only. Fine on dogfood (422n) and even MassTransit (24.8k n) at query time, but it is a linear scan, not an index. `IsWordBoundary` runs per matched node. No perf gate on Find specifically. |
| **`graph.Find` key-only matches get rank 3 with a title that doesn't contain the term** | `MatchRank(title, term)` is computed against the title even when the match was on `Id.Key`. Harmless (they sort last), but the rank label is technically wrong for key-only hits. |
| **Empty-query SearchNodes behavior changed** | Routing SearchNodes through `graph.Find` means an **empty query now returns 0 results** (previously the first N nodes). No live caller depends on the old behavior (omnibox guards ≥2 chars; mcp-page is a dev playground) and returning nothing for an empty search is arguably more correct — but it is an unannounced behavior change. |
| **CLI `query` command still uses the old degree-only `GraphQuery.Search`** | `DevContext.Cli/Commands/QueryCommand.cs:205`. L5.3's unified ranking is MCP-only; the CLI search path was out of L5 scope and was not migrated. Minor inconsistency between surfaces. |
| **`read_source` member mode uses naive brace counting** (`FindMethodScope`) | Counts `{`/`}` in raw text including strings/comments/interpolations — a method body containing `"}"` in a literal can mis-scope. Pre-existing (M4.5), untouched by L5, but it lives in the L5 tool set. |
| **Token accounting is `(len+3)/4`** | ~4 chars/token heuristic across every tool's `approxTokens`/`tokens`. The tools/list ≤1.5k and flow ≤150 budgets are measured with this estimate, not a real tokenizer. |

## Risks for L6+ and concrete follow-ups

| Risk / follow-up | Suggested action |
|------------------|------------------|
| No unit tests for the MCP surface (23 tools + handler) | Add a `DevContext.Mcp.Tests` project. First tests worth writing: (1) reflection guard that `UnknownToolHandler.ToolNames` == the set of `[McpServerTool]` methods; (2) a fake `DevContextServiceClient` exercising the envelope paths (missing param, unknown symbol → candidates, F4 multi-exact ambiguity). |
| `UnknownToolHandler` name-list drift | Either derive the list at runtime from the registered tool collection, or add the reflection guard test above. |
| Concurrent same-repo analyze races (duplicate work + lingering session) | Guard with a `ConcurrentDictionary<repoKey, SemaphoreSlim>` (or `Lazy<Task<AnalysisSession>>`) so the second caller awaits the first. Only worthwhile if the server ever serves concurrent clients. |
| **Test-infra: cold/scripted QA leaves a `DevContext.Server` process running** | The node harness hard-kills the MCP proc, so the server it spawned via `ServerShim` is orphaned (its `AppDomain.ProcessExit` cleanup never runs). This locked build DLLs during this audit (had to `Stop-Process`). Consider having the harness kill the spawned server, or `ServerShim` register an OS job-object. This is harness hygiene, not product. |
| `graph.Find` is a linear scan | If Find becomes hot (e.g., every keystroke), add a title index. Not needed today. |
| CLI vs MCP resolution divergence | If the CLI `query` result quality matters, migrate `QueryCommand` to `graph.Find`. |
